# P3 · fmax 还债 — 实验 C: load 结果改由 MEM/WB 寄存器给出

**日期**：2026-10-05  **tag**：`p3g-default-final`  **结论：保留，已设为默认。这是本轮最大的一次改善。**

## 靶子：根因终于落到具体信号上

实验 B 把取指路径彻底移出关键路径后，关键路径变成：

```
Slack 4.697ns (fmax 65.3)   Source: u_core/u_dmem/mem_reg_2/CLKBWRCLK
Destination: u_core/u_id_ex/rs2_data_reg[2]/D
Data Path: 15.216ns  (logic 5.498 = 36.1% | route 9.718 = 63.9%),  19 级
路径归属: u_id_ex 30 | u_ex_mem 6 | u_lsu 6 | u_dmem 4 | u_mem_wb 4
```

读 RTL 后定位到具体成因（`core.sv`）：

```systemverilog
// u_mem_wb 的 load_data_in 原本硬接 32'h0 —— load 结果没走这个寄存器
.load_data_in (32'h0),
...
WB_MEM:  wb_data = mem_load_data;   // 直接从 LSU 的"组合"输出取
```

于是关键路径是：

```
dmem 输出寄存器 ─► LSU 字节提取/符号扩展 ─► wb_data mux ─► 前递 mux ─► ID/EX
```

**根因**：同一个时钟沿上，"组合读出的数据"既要被 MEM/WB 锁存、又要穿过
`wb_data` mux 去前递与写回 —— **两跳压在一条路径上**。

> 这是 `dmam.sv` 当初"把字节提取挪到 WB 拍吸收延迟"那个决定的必然结果：
> 提取逻辑落在 BRAM 输出寄存器**之后**，于是它就进了前递路径。
> `HANDOFF.md` 的 P3 描述早就指出了这一点，本轮才真正量化并修掉。

## 改动：让它走那个本来就存在的寄存器

**不新增任何寄存器** —— 用的就是 `mem_wb_reg`：

```systemverilog
`ifdef LOAD_RESULT_REG
  .load_data_in (mem_load_data),      // 真正寄存提取结果
`else
  .load_data_in (32'h0),              // 旧行为
`endif
...
`ifdef LOAD_RESULT_REG
  WB_MEM:  wb_data = mem_wb_load_data;   // 从前递寄存器取, 而不是从组合输出取
`else
  WB_MEM:  wb_data = mem_load_data;
`endif
```

这样 `wb_data` 从**寄存器**出发，砍掉了 `dmem → 提取 → mux` 那一段长走线。

## 【最重要】我原本以为要付"停顿 1→2 拍"，实测**不需要**

`HANDOFF.md` 的 P3 方案 1 写着"代价：load-use 停顿 1→2 拍，约 +7% 周期"。
我先按这个理解给 `hazard_unit` 加了第二拍停顿（`load_use_wb`），
**结果实测 ticks 与 load-use 停顿完全没变**：

| | ticks | cycles | load-use 停顿 |
|---|---|---|---|
| 默认（组合） | 423,527 | 468,659 | 30,645 |
| 加了第二拍停顿 | 423,527 | 468,659 | 30,645 |

原因：**dmem 的寄存读已经提供了那一拍**。消费者在 EX 时看到的 MEM/WB 值，
本来就是"上一拍末锁存好的"，MEM/WB 只是把同一个值再接一次，**没有额外延迟**。

于是我把 `hazard_unit` 的改动**整个回退**（连新加的端口也删了），只保留
`core.sv` 的改动——更干净，且不需要动流水线控制。

> 教训：**"预期代价"必须实测**。这个方案被 `HANDOFF.md` 标注为"高收益高代价"
> 而搁置了很久，实际上它是**零代价**的。若照文档的悲观假设行事，这个
> +14.8% fmax 就永远拿不到。
