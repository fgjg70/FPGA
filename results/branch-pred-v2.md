## 试过并**否决**的方案 (附数据)

### RAS (返回地址栈) + BTB 扩容到 128 项

| 指标 | 无 RAS | +RAS/BTB128 | +RAS/BTB64 |
|---|---|---|---|
| CoreMark/MHz | 2.3614 | 2.3856 (+1.0%) | ~2.3856 |
| fmax | **74.6** | 71.2 (−4.6%) | 70.8 (−5.1%) |
| LUT | **4551** | 4809 | 4633 |
| CoreMark/LUTs | **5.189e-4** | 4.961e-4 (−4.4%) | ~ |
| **绝对吞吐** | **176.2** | 169.9 (−3.6%) | 169.0 |

RAS 本身是生效的: 预测精度 89%→**92%**, JALR 误判 4,364→**2,823** (−35%)。
**但代价更大**: `pred_target = pred_is_ret ? ras_top : btb_target` 多一级 mux,
且 RAS 读与 BTB 的输出 mux 树都压在 pc 关键路径上。

**赛题记三项指标, 改一项要同时看三项。** 这个改动赢 1 项输 2 项, 绝对吞吐 −3.6%, 回退。

### 保留下来的: BTB 目标位宽压缩 (纯赚)
PC 恒在 imem 窗口内, 目标只需存低 14 位, 高位由 IMEM_BASE 补回。
每项从 41 位压到 23 位 → **LUT 4551→4494**, CoreMark/LUTs 反而改善。

## RV32M 实现 (本轮的净胜项)

| 指标 | rv32i | **rv32im** |
|---|---|---|
| CoreMark/MHz | 1.0274 | **2.3614** |
| ticks | 973,352 | **423,486** |
| redirects | 59,466 | **11,501** |

收益远超"把软件乘除换成单条指令"本身: libgcc 的 `__mulsi3/__udivsi3/__umodsi3`
是**函数调用 + 循环**, 分支密集。启用 M 后 **redirect 掉 81%**, 那部分分支流量整个消失。

### 除法器的三个坑 (全是真踩的)
1. **余数必须 33 位**。恢复余数法要左移一位再补被除数最高位; 32 位时若除数 > 2^31 会丢位。
2. **`busy` 必须覆盖启动那一拍**。否则 DIV 在结果出来前就离开 EX。
3. **单周期的除零/溢出同样要占一拍**。它们也要先寄存结果再放行流水线, 否则 EX/MEM
   捕获到的是上一次的 `div_result`。统一判据: `busy = 迭代中 || (是除法 && 结果尚未寄存)`。

### MULHSU 只要两个乘法器
```
signed(a)*unsigned(b) = signed(a)*signed(b) + signed(a)*(b[31] ? 2^32 : 0)
=> high32(MULHSU) = high32(prod_ss) + (b[31] ? a : 0)
```
`(a<<32)` 低 32 位为 0, 不向高位进位, 所以一个 32 位加法即可。

## fmax: 把乘积寄存进 DSP

组合乘法直达写回时关键路径是
`hazard/前递 → DSP48E1×2 → 13 级 CARRY4 (64位加法) → EX/MEM` = **15.5ns**, fmax 64.7。
写成 `always @(posedge clk) p <= a*b;` 让 Vivado 塞进 DSP 的 MREG/PREG 后:
**fmax 74.6 (+15%), CoreMark/MHz 只让 2.2%** (每次乘法 +1 拍)。净赚。

## 一个静默配置错误 (值得单独记)

`build_sw.py` 里把 `-march=rv32i` **硬编码**了。我用 `-D FLAGS_STR=-march=rv32im`
以为切过去了 —— 那只改了 CoreMark **打印出来的字符串**, 生成的镜像逐字节相同。
**暴露它的是"两次 ticks 都是 973352, 过于一致"**。现在有 `--march` 参数。

> 教训: 构建脚本里的"报告性"参数和"生效性"参数必须分清; 指标异常一致时先怀疑没生效。
