## 1. 体系结构

### 1.1 流水线组织

```
        ┌────┐  ┌────┐  ┌────┐  ┌─────┐  ┌────┐
        │ IF │─▶│ ID │─▶│ EX │─▶│ MEM │─▶│ WB │
        └────┘  └────┘  └────┘  └─────┘  └────┘
          │       │       │       │        │
        imem   control   ALU    dmem    regfile
      (BRAM)    imm_gen  muldiv  LSU
                 regfile  BTB
```

**哈佛结构**：imem `0x8000_0000`（16 KB）与 dmem `0x9000_0000`（16 KB）是两个
独立地址空间，`load/store` 只能到达 dmem。这个约束贯穿整个软件构建流程（第 3.3 节）。

### 1.2 关键设计决策

| 决策 | 理由 |
|---|---|
| **`redirect` = 「预测错误」而非「分支 taken」** | 预测正确时若仍冲刷，两条正确路径被白丢、收益归零。这是分支预测能否见效的**前提** |
| 跳转目标取**独立加法器**而非 ALU 输出 | BR/JAL/JALR 的 `alu_op` 恒为 ADD，操作数确定；省掉 ALU 的 3:1 + 2:1 操作数 mux（第 4.2 节实验 A）|
| 乘法乘积**寄存进 DSP** 的 MREG/PREG | 组合乘法路径 15.5 ns 拖垮 fmax；寄存后用 2.2% CoreMark 换回 15% fmax |
| 除法 `busy` **覆盖启动拍** + 单周期特例也占一拍 | 否则 DIV 在结果出前离开 EX，或 EX/MEM 捕获上一次的结果 |
| dmem 用**寄存读**以推断 BRAM | 组合读只能落分布式 RAM（2131 LUT，占全核 47%）；行为级推断才能零成本迁移 PDS |
| load 结果改由 **MEM/WB 寄存器**给出 | 切断 `BRAM → 提取 → mux → 前递` 这条长组合路径（第 4.2 节实验 C）|
| FENCE 译成**合法 NOP** 而非 illegal | 编译器/运行库会插 fence，误判非法会让正常程序一上来就掉陷阱 |
| `mepc` 取 `trap_pc` **不 +4** | 异常与中断都在指令提交前裁决，被抢占的指令必须重新执行 |
| MMIO 需要**读选通 `ext_re`** | 只靠 `we` 时外设的粘滞"数据就绪"标志软件永远清不掉 |

### 1.3 分支预测

64 项直接映射 BTB，每项 `{valid, tag, target, pc[13:8], 2 位饱和计数器}`。

- **预测结果随流水线传递**（IF/ID → ID/EX）。EX 时 PC 已跑到前面，无法重新查表；
  没有这一步就判断不了预测对错。
- **目标位宽压缩**：PC 恒在 imem 窗口内，目标只需存低 14 位，高位由 `IMEM_BASE` 补回。
  64 项时每项 41 位 → 23 位，LUT 4551 → 4494。
- 实测精度 **88.7%**（101,971 条控制流指令，11,535 次误判）。

### 1.4 异常与中断（M-mode）

`csr_file.sv` 实现 `mstatus / mie / mtvec / mscratch / mepc / mcause / mtval / mip`
与进陷阱 / MRET 状态机。**陷阱在 EX 段、指令提交之前裁决**，与分支预测错误**共用同一套
冲刷机制** —— 因此陷阱是**精确的**：触发指令被冲成气泡，不写寄存器、不写存储器，
而它之前的指令全部已提交。

中断源：`mtimecmp` 定时器（`mtime >= mtimecmp` 电平 → `mip.MTIP`）。

### 2.2 CoreMark 正确性证据

CRC 全部匹配官方 2K PERFORMANCE_RUN 期望值：

| 项 | 实测 | 官方 |
|---|---|---|
| seedcrc | 0xe9f5 | 0xe9f5 |
| crclist | 0xe714 | 0xe714 |
| crcmatrix | 0x1fd7 | 0x1fd7 |
| crcstate | 0x8e3a | 0x8e3a |
| crcfinal | 0xe714 | 0xe714 |

> **为什么用 crclist/crcmatrix/crcstate 而非 crcfinal 做上板判据**：前三者与
> **迭代次数无关**（实测 1 次与 3 次完全一致），只有跨迭代累积的 `crcfinal` 会变。
> 所以赛题要求的 10 秒改了迭代次数后，判据依然成立。

### 2.3 上板闭环（无人值守）

本板**串口不可用**（FT2232H 只有 D2XX 驱动、无 COM 口），因此走：

```
软件 --(MMIO 上报)--> 硬件 --(ILA)--> JTAG --> PC
```

一个 32 位寄存器打包两件事（上板只能回读一个数）：
`bit31 = CRC 判定`，`bit30:0 = tick 数`。

抓取脚本自动完成 **烧录 → 按构建清单等待（105 MHz 档：18 s，CoreMark 跑 13.15 s；`wait_seconds`
由 `mk_cm_hw.py` 随档位写）→ arm ILA → 读回 → 写 CSV
→ 写采集清单 `ila_done.capture.json`**，
不依赖人看 LED。

### 3.2 关键路径分析

> ⚠️ **先读当前值（2026-10-11 现查）**：
> **当前设计目标档 131.25 MHz（`sys_clk_core` @7.619 ns）—— 时序未收敛**：
> `fpga/timing.rpt`：`Timing constraints are not met.`、`sys_clk_core` WNS **−0.963**（1141/4437 失败端点）。
> **最近一次收敛档是 105 MHz**（`metrics.json` 的 `20261011-151614-cm_hw`，`path` 段）：
> ```
> fmax 106.30 MHz  sys_clk_core @9.524ns, 运行 105.00 MHz; WNS +0.117ns -> fmax=1000/(9.524 - 0.117)
> Source:      u_core/u_ex_mem/ctrl_reg[wb_src][0]/C
> Destination: u_core/u_id_ex/rs2_data_reg[25]/D
> Data Path:   9.351 ns  (logic 3.199 = 34.2% | route 6.152 = 65.8%)
> Logic Levels: 17
> ```
> 下面这一节是**历史快照（2026-10-07，宏全关、LUT 4079）**，保留是因为它的
> **分析方法与结论（布线受限、单靠改 RTL 收益有限）依然成立**；
> 注意 2026-10-08 删冗余 `if_id_reg`、2026-10-11 C-1 之后路径**已经移动多次**。
> **别再拿下面的 61.2 MHz 当"当前值"引用。**

2026-10-07 配置（宏全关 = 当时代码）**历史快照**：

```
Slack (MET) :  3.783 ns          fmax = 61.2 MHz
Source:      u_core/u_dmem/mem_reg_3/CLKBWRCLK     (dmem 的 BRAM 输出寄存器)
Destination: u_core/u_pc/pc_reg[8]/D               (PC 寄存器)
Data Path:   15.907 ns  (logic 5.379 = 33.8% | route 10.528 = 66.2%)
Logic Levels: 19  (CARRY4=5 LUT3=3 LUT5=5 LUT6=6)
```

**这条路径是「load 出来的值直接当跳转目标」** —— 典型场景是从栈上恢复 `ra`
后 `ret`，在函数调用密集的代码里极常见。完整链路：

```
dmem BRAM 输出 -> LSU 字节提取/符号扩展 -> 写回 mux -> 前递 mux
                -> ALU 加法器 -> 目标选择 mux -> PC
```

全部压在一拍内。**布线占 66.2%、逻辑 5.379 ns** —— 关键路径长度由
**布局与扇出**决定，不是逻辑深度。这意味着：

1. 单靠 RTL 改写的收益已经很小；
2. `phys_opt_design` 单用几乎无效，必须配
   `place_design -directive ExtraTimingOpt` + `route_design -directive AggressiveExplore`
   （本项目 `build.tcl` 已采用这套组合）；
3. 要进一步提 fmax，必须**减少这条路径上的组合级数** —— 也就是把
   "load 结果"与"取指/重定向"解耦，这正是 `IMEM_REG_READ` / `LOAD_RESULT_REG`
   两轮尝试的目标，而它们都需要**取指流水重排**（见第 6.3 节）。

### 3.3 哈佛结构带来的软件构建约束

`.data/.rodata` 的初值**不能**靠 crt0 从 imem 搬运（那条 `lw` 读 imem 读不到，
会把整段搬成 0 —— 真实踩过的故障）。正解是**双镜像**：

- `.text` → imem 镜像（`IMEM_INIT_FILE`）
- `.data/.rodata` 的 VMA 就放在 DMEM，初值由 **dmem 自己的镜像**装入（`DMEM_INIT_FILE`）

`crt0` 只需清 `.bss`（`__data_lma == __data_vma` 时搬运循环自然空转）。

## 4. 优化过程（10+ 轮迭代）

### 4.1 度量纪律

**赛题记三项指标，改一项必须同时量三项 + 绝对吞吐**，否则会误判。真实反例：

| 配置 | CM/MHz | fmax | CM/LUTs | 绝对吞吐 | 结论 |
|---|---|---|---|---|---|
| 分布式 RAM dmem | 2.3614 | 74.6 | 5.254e-4 | 176.2 | — |
| BRAM dmem | 2.3614 | 63.9 | **9.518e-4** | 150.8 | 赢 1 输 1 |
| **RAS + BTB128** | 2.3856 | 71.2 | 4.961e-4 | 169.9 | **赢 1 输 2 → 回退** |

> 没有"绝对吞吐"这一列，就看不出 RAS 那个改动其实**三项里输了两项**。

**先测量再优化**：第 1 轮靠剖析发现「分支惩罚吃掉 29% 的周期」，才决定先做分支预测
而不是 M 扩展。若拍脑袋做 M 扩展，收益会小得多。

### 4.3 三个关键优化的原理

**实验 A · 跳转目标专用加法器（fmax +4.9%，零周期代价）**

原写法已取 ALU 的原始加法器输出（绕过结果 mux），但**操作数 mux 仍在路径上**：
`ex_a` 是 3:1、`ex_b` 是 2:1。而 BR/JAL/JALR 的操作数是确定的（`pc+imm` / `rs1+imm`），
于是给它们一条只有 1 级 mux 的专用加法器。

**实验 B · 取指存储器进 BRAM（LUT −32.7%，零周期代价）**

`imem` 原本是**组合读**，而 BRAM 做不了组合读 → Vivado 只能把它摊成
**1228 个纯 LUT 的组合 ROM**（占全核 31%）。普通 `report_utilization` **完全看不出**
这个问题：imem 在 Block RAM 表和 Distributed RAM 表里**都不出现**，
必须按层次报告才看得到。

改寄存读后：`u_imem` **1228 → 36 LUT**，全核 3945 → 2656。
**而 CoreMark ticks 逐位不变** —— `if_pc` 与 `if_instr` 由同一个寄存器锁存、
永远配对，寄存读只是把整个前端**相位平移一拍**，稳态下每拍仍出一条指令。

**实验 C · load 结果走 MEM/WB 寄存器（fmax +14.8%，零周期代价）**

`core.sv` 里 `mem_wb_reg` 的 `load_data_in` 原本**硬接 `32'h0`**，load 结果直接从
LSU 的**组合**输出进 `wb_data` mux → 前递 mux → ID/EX —— 同一个时钟沿上，
"组合读出的数据"既要被 MEM/WB 锁存、又要穿过 mux 去前递/写回，**两跳压在一拍**。

改成真正走 MEM/WB 寄存器后路径从寄存器出发。**零代价**：`dmem` 的寄存读
已经提供了那一拍，MEM/WB 只是把同一个值再接一次。

> ⚠️ **这一项曾被长期搁置**：文档把它标注为"代价：load-use 停顿 1→2 拍，约 +7% 周期"。
> 实测那个代价**根本不存在**。**文档里的"预期代价"必须重新实测再据此决策。**

### 4.4 失败与弯路（同样是有价值的资产）

| 尝试 | 结果 | 教训 |
|---|---|---|
| RAS + BTB128 | 净亏回退（赢 1 输 2）| 单看 CM/MHz 会误判成改进 |
| 缩容 imem 16KB → 12KB | **负收益**：`u_imem` 1228 → **2111 LUT** | 不要凭"用了多少"推断"能省多少" —— 未初始化区填 NOP 让 Vivado 能折叠常量，而 **2 的幂阵列折叠得更彻底** |
| 用恒 NOP 桩测 imem 的 fmax 代价 | **实验失效**：全核塌成 3 LUT | 想量某模块的 fmax 代价，**不能把它变常量** —— 会把消费者一起折叠掉 |
| `imem` 组合读推断 BRAM | 不可能（BRAM 必须同步读）| 见实验 B |

## 5.4 应用场景：神经网络推理核心（AI 相关维度）

赛题里有"应用场景构建"与"AI 模型性能"两项，所以本节说明本核在 AI 场景下的
落地形态与实测数据。**选择 GEMM 作为切入点**的理由：神经网络推理里耗时占比
绝对主导的算子就是矩阵乘（全连接层就是它，卷积 im2col 化之后也是它），
它同时满足"计算密集可量化""结果可逐元素校验""有明确的软件/加速对比基准"三条。

### 5.5.1 软件基线（可信、可复现）

`sw/nn_demo.c` 实现一个两层 MLP 的前向传播核心，**纯软件跑在本核上**：

| 项 | 实测 |
|---|---|
| 规模 | 16×16 三重矩阵乘（4096 MAC）|
| `gemm_cycles` | **196,264** |
| `cycles_per_mac` | **47.91** |
| `checksum` | `0x9d5de1c5` |
| `checksum_ref`（**独立参考实现**）| `0x9d5de1c5` ✅ |
| `mismatch`（逐元素比对）| **0** ✅ |

校验和与主机端 Python 独立计算的结果完全一致 —— 这是该基线的可信依据。

> **这里踩过一个值得写进报告的坑**：第一版 `checksum_ref` 我错写成"再对 C 求
> 一次校验和"，于是两个校验和恒等、`match` 永远是 1 —— 一个**永远为真、
> 什么也证明不了**的检查。改成"独立累加器 + 独立乘法路径"之后差异才暴露。
> **参考实现必须走独立计算路径，否则只是自证清白。**

顺带定位了一个**编译器代码生成问题**：同一份源码只改 `-O0`/`-Os`/`-O2`，
GEMM 结果就不同（`-O0` 与主机一致，`-Os`/`-O2` 不一致）。已用一组独立自检
（32 位乘走 M 扩展、64 位乘走 libgcc、普通赋值循环）把**核**摘干净，
确认是优化通道的问题；基线因此用 `-O0` 构建以保证数值正确。
复现探针保留在 `sw/opt_probe.c`，详见 `results/p5-compiler-bug.md`。

### 5.5.2 硬件加速单元：机制已验证，但判定不采用

实现了 `gemm_accel.sv`（int8 输入 / int32 累加的本地缓冲式加速单元），
并在总线上跑通：

| 项 | 实测 |
|---|---|
| 加速单元在总线上 | 软件写 `0xDEADBEEF` 读回同值 → `alive=1` ✅ |
| 寻址 / 取数 | `A_off` 连最后一拍都正确；该拍操作数非 0 ✅ |
| 写回计数 / 下标 | 256 次（= M×N）、末次下标 255 ✅ |
| **计算加速（自报周期）** | **4,608 拍 vs 软件 196,264 拍 → 42.59×** |
| 端到端（含软件搬运数据）| **5.38×** |

**但两项原因使它被门控默认关闭（`GEMM_EN`）**：

1. **面积代价不可接受**：三个缓冲落成了**触发器阵列**（约 1.3 万 FF）
   而不是 BRAM —— LUT 4079→9984（+145%）、FF 1377→**14097**（+924%）、
   fmax 61.7→53.6（−13%）、CoreMark/LUTs −60%。
2. **功能未完成**：C 矩阵只有前 16 个字读回正确。

按本项目的判定纪律（赢 1 输 3 即回退），这必须移出评分版。
**保留完整实现、诊断寄存器（`MMIO_GEMM_DBGA/DBGV/DBGW/DBGK`）与复现开关
（`--gemm`）**，并把"改成 BRAM + 修 C 读回"列为后续工作，
详见 `results/p5-ai-accelerator.md`。

> **这一节的诚实结论**：应用场景的**基线**是可信且可复现的（这是"应用场景
> 构建"的落点）；硬件加速的**机制**已被验证可行（42.59×），但因面积与正确性
> 两项未达标而**不计入成绩**。**把"验证过的机制"与"可交付的功能"分开陈述**，
> 比把它们混在一起说更有价值。

当前 **106.30 MHz**（最新已上板档 105 MHz，`sys_clk_core` @9.524 ns，WNS +0.117）；
**设计目标 131.25 MHz 尚未收敛**（WNS −0.963），
关键路径的形态见第 3.2 节
（该节历史快照是 2026-10-07 的 `load 结果 → 跳转目标 → PC`，route 占 66.2%；
当前两端都是 BRAM，route 占 67.8%）。
**靠改 RTL 的收益已明显变小**，建议：

1. **减少关键路径的组合级数**：把 "load 结果" 与 "取指/重定向" 解耦 ——
   这正是 P8 去掉冗余 `if_id_reg` 与建立"IMEM 输出寄存器充当 IF/ID"所走的方向，
   已把 fmax 从 61.2 → **69.5 MHz（当时口径）**；2026-10-09 MMCM 提频（70 MHz）+
   物理约束后到 **74.4 MHz**；2026-10-11 **C-1（两级流水 gshare）+ 逐档提频** ⇒
   最新已上板档 **106.30 MHz**（`sys_clk_core` @9.524 ns，WNS +0.117，见 3.2 节）。
   后续同类重排记录见 `results/p4-macro-failure.md` 5.1、`results/p4-c1-2stage-gshare.md`
   与 PITFALLS **R47**（top-N 是墙时逻辑重排期望≈0）、**R50**（提频本身也会抬高 fmax）。
   **下一步目标：把 131.25 MHz 收下来**（当前 WNS −0.963）。
2. **物理手段**：floorplan / 位置约束 / congestion 分析。
3. **减少寄存器数量与总线扇出**：`ctrl_s` 控制束有 20+ 字段随流水线传递，
   可考虑对不常变的字段做编码压缩。
4. **load-use 停顿**是最大周期开销（6.5%），但它**不在关键路径上**，
   优化它只对 CPI 有益、不影响 fmax。
