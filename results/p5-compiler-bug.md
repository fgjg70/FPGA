# P5 · 编译器代码生成 bug —— `gemm_sw` 循环形状在 `-Os`/`-O2` 下被编错

**日期**：2026-10-05  **严重性：高（影响数值类程序的可信度）**  **状态：已定位并隔离**

## 现象

写应用场景的 GEMM 程序（`sw/nn_demo.c`）时，软件实现与参考实现的结果对不上
（256 个元素里 255 个不同）。逐步排查后定位到：

**同一份源码、同一个核，只改优化级别，结果就不同。**

最小复刻（`sw/opt_probe.c`，其中"构造 5"逐字节复刻 `nn_demo` 的 `gemm_sw`）：

| 优化级别 | C(0,0) | C(0,1) | C(15,15) | 全表 FNV-1a | 与主机端计算 |
|---|---|---|---|---|---|
| **`-O0`** | **104** | **224** | **−40** | **0x9d5de1c5** | ✅ **完全一致** |
| `-Os` | −9 | 6 | −48 | 0x71fe58e5 | ❌ |
| `-O2` | 88 | −3920 | −56 | 0xdb37fcf5 | ❌ |

主机端（Python，同一套初始化公式与累加定义）算出的期望值：
`C(0,0)=104, C(0,1)=224, C(15,15)=−40, fnv=0x9d5de1c5`。

## 是核的问题还是编译器的问题？—— 已排除核

| 检查 | 结果 |
|---|---|
| 32 位有符号乘（走 M 扩展 `mul`） | ✅ 正确 |
| 64 位乘（走 libgcc `__muldi3`） | ✅ 正确 |
| **普通的赋值循环**（`sw/opt_probe.c` 的构造 1/2/3/4）| ✅ **在 `-O0`/`-Os`/`-O2` 三个级别下全部与主机一致** |
| 双精度/整型 64 位累加 | ✅ 正确 |
| CoreMark 在 `-Os` 下 | ✅ CRC 逐位匹配官方值 |

**关键点**：出问题的**只有 `gemm_sw` 那一种循环形状**（`i / k / j` 顺序、
内层对 `B[k][j]` 连续取、累加到 `C[i][j]`）。同样的矩阵、同样的算法，
写成别的形状（或降级到 `-O0`）就正确。这说明**不是数据通路算错**，
而是某个优化通道在这个形状上生成了错误的代码。

## 为什么这件事值得记下来

1. **它会伪装成"CPU 有 bug"。** 症状是"矩阵乘结果错"，第一反应一定是核的
   乘法/访存有问题。实际核是干净的 —— 我一开始就把 64 位乘当成头号嫌疑，
   写了一组自检才排除掉。**遇到数值不对，先把"编译器"列为嫌疑之一。**
2. **`-O0` 通过不代表 `-Os` 通过。** 这类 bug 只在开启某个优化时出现，
   所以"我本地跑对了"可能只是因为用了默认的 `-O0`。
   本项目 `tools/build_sw.py` 默认 `-Os` —— 数值类程序必须**逐级验证**。
3. **判据要能和"独立计算"比对，不能自己和自己比。** 第一版 `checksum_ref`
   我错写成"再对 C 求一次校验和"，于是 A 与 B 恒等、`match` 永远是 1 ——
   一个**永远为真、什么也证明不了**的检查。是在把它改成"独立累加器 +
   独立乘法路径"之后，差异才暴露出来。
   **校验和必须来自一条独立的计算路径，否则它只是自证清白。**

## 处置

- `sw/opt_probe.c` 保留为**回归探针**：它把候选构造拆开、每个都算 FNV 校验和，
  期望值可由主机端复算。以后换工具链版本或改编译选项，先跑它。
- 应用场景的程序按 `-O0` 验证基线（数值正确优先），并在文档里注明这一点。
- **不把"某个优化级别下的结果"当作核的功能证据** —— 上板与 CoreMark 的证据
  之所以可信，是因为它们有**独立**的官方参考值（CoreMark 官方 CRC），
  不是自己和自己比。

## 复现

```bat
REM 三个级别各跑一次, 对比 t5 那一行
python tools\build_sw.py sw\opt_probe.c sw\portme.c -I sw --march=rv32im --opt=-O0 -o sim\prog\opt_probe.hex
python tools\build_sw.py sw\opt_probe.c sw\portme.c -I sw --march=rv32im --opt=-Os -o sim\prog\opt_probe.hex
```
