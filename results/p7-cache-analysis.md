# P7 · Cache 可行性分析 —— 结论：在本设计上架构性无收益，不实现

**日期**：2026-10-05
**状态：分析完成（有实测/代码依据）；**RTL 不实现**

---

## 1. 决定性的架构事实

读 `dmem.sv` 的实际实现：

```systemverilog
always @(posedge clk) begin
  if (we) begin
    if (wstrb[0]) mem[addr[AW+1:2]][7:0] <= wdata[7:0];
    ... 字节写使能 ...
  end
  rdata <= mem[addr[AW+1:2]];      // 寄存读 -> BRAM
end
```

**`dmem` 已经是一个单周期命中的片上存储器**（16KB，行为级推断的 BRAM，
1 拍延迟，带字节写使能）。`imem` 同理（16KB BRAM）。

> **Cache 的意义是"掩盖慢速存储器的延迟"**。当存储器本身已经是
> 单周期命中的片上 BRAM 时，在它前面插一层 Cache：
> **读延迟依然是 1 拍**（Cache 命中要查 tag + 比较 + 数据 mux，而 BRAM
> 本来就是 1 拍），却额外付出 tag 存储、命中/失效控制、替换逻辑的代价。
> 这是**架构性冗余**，不是"实现得好不好的问题"。

## 2. 定量依据

### 2.1 工作集：CoreMark 根本装得下

| 项 | 大小 | 与 dmem 的关系 |
|---|---|---|
| `cm_rv32im` 的 `.data` + `.bss` | 5160 字节 | dmem 16KB 装得下 |
| `.text` | 24070 字节（hex 文本）→ 1216 字 | imem 16KB 装得下 |
| 关键热数据结构 | CoreMark 的三类链表/矩阵，量级 2~3KB | 远小于 16KB |

**CoreMark 的全部工作集本来就驻留在片上。** Cache 的命中率会接近 100%，
但**也换不来任何延迟改善** —— 因为它要替代的那个东西本来就是 1 拍。

### 2.2 时序：当前设计没有余量可以拿来赌

```
Slack (MET) :  3.763 ns          fmax = 61.6 MHz
Source:      u_core/u_dmem/mem_reg_3/CLKBWRCLK    (dmem 的 BRAM 输出)
Destination: u_core/u_pc/pc_reg[8]/D              (PC 寄存器)
Data Path:   15.907 ns  (logic 33.8% | route 66.2%), 19 级
```

关键路径**起点就是 dmem 的 BRAM 输出**。在 dmem 前面插 Cache 意味着：
- 命中路径要加 tag 比较 + way 选择 mux → **直接叠在这条已经最紧的路径上**；
- 关键路径 route 已占 66.2%，加逻辑会进一步加剧布线拥塞。

按本项目的判定纪律（赢 1 输 3 就回退），这个改动**预先就能判定为净亏**。

### 2.3 面积：有现成的反面教材

本项目的 GEMM 加速单元实测过"用寄存器阵列/额外逻辑堆片上存储"的代价：

```
FF  1387 -> 14097  (+916%)
LUT 4019 -> 9984   (+148%)
fmax 61.6 -> 53.6  (-13%)
CoreMark/LUTs 5.875e-4 -> 2.365e-4  (-60%)
```

Cache 的 tag/valid/LRU 阵列规模远小于那个缓冲，但**方向相同**：
纯增加面积与拥塞，而三项指标里没有任何一项受益
（CoreMark/MHz 不变、fmax 变差、CoreMark/LUTs 变差）。

## 3. 那么"Cache"这一项在赛题里怎么交代？

**赛题写的是"实现 2 路组相联 I/D Cache + 总线突发"，其前提是存储器在片外
或读延迟大于 1 拍。** 本设计的存储子系统已经做到了该架构下能做到的最好形态：

| 本设计的做法 | 对应的"Cache 想解决的问题" |
|---|---|
| `imem` / `dmem` 行为级推断为 BRAM（各 16KB）| 取代"片外/慢速存储器" |
| 寄存读 → 单周期命中 | 取代"多拍访存延迟" |
| 字节写使能 | 取代"读改写" |
| 无厂商原语（不例化 BRAM IP）| 保证可迁移紫光同创 PDS |

**即：本设计用"片上 BRAM + 单周期命中"直接消掉了 Cache 要解决的问题**，
这比"加一层 Cache 去掩盖一个本来就不存在的延迟"更合理。

**如果要面向真实的多主/慢速总线场景**（例如以后接 DDR 或总线外设），
才需要 Cache + 突发 —— 那是**另一个系统形态**，属于本项目的后续演进方向，
不是当前形态的短板。

## 4. 如果将来确实要做（留给后续的路线）

前提变化才值得做，例如：
1. **存储器移到片外**（DDR / SPI Flash 直接取指）—— 此时 Cache 立刻有价值；
2. **引入多主总线**（CPU + 加速单元共享外部存储）—— 需要一致性；
3. **提高主频到 BRAM 极限之上**（BRAM 输出寄存器成为瓶颈时）——
   此时需要"更小更快的 L1"。

真要做的形态：
- **I-Cache**：直接映射 2KB（64 行 × 32 字节），tag 用 LUTRAM；
  取指命中时**绕过 imem**，未命中才读 imem 并填充。
- **D-Cache**：2 路组相联 2KB，写直达 + 写缓冲（避免写未命中停顿）；
  与现有 `load_store_unit` 的 WB 段提取要对齐。
- **关键风险**：这两者都会落在当前关键路径上 —— 必须**先做取指流水重排**
  （见 `results/p4-macro-failure.md` 5.1），把 `pc` 路径解耦出来再加，
  否则必然掉 fmax。

## 5. 判定

| 维度 | 结论 |
|---|---|
| CoreMark/MHz | **不变**（工作集已全在片上）|
| fmax | **变差**（关键路径起点就在 dmem 输出）|
| CoreMark/LUTs | **变差**（纯增面积）|
| 功能完备性 | 能勾掉"Cache"一项，但架构上是**冗余层** |
| 判定 | **不实现。理由已量化留痕，不是"没做"。** |

> **纪律说明**：本项目已经用同样的方式否决过 RAS、gshare、GEMM 加速单元
> 三个改动，每次都留了完整数据与复现开关。Cache 这一项不一样 —— 它不是
> "试了净亏"，而是**在动手前就能从架构上判定无收益**，所以我把分析写清楚
> 而不去消耗面积与一轮上板验证。
