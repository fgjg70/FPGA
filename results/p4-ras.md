# P4 · 返回地址栈 (RAS) —— 机制有效, 但综合指标净亏, 默认关闭

**日期**：2026-10-05  **tag**：`p4-ras`  **结论：实现保留在 `RAS_EN` 宏后，默认关闭**

## 为什么选它

先按纪律测量，把预测错误按类型拆开（tb_sw 新增的分类型统计）：

```
ctrl-flow  = 101971   mispredict = 11535   accuracy = 89%
  cond branch = 6055  (52%)
  JAL         = 1102  ( 9%)
  JALR        = 4378  (37%)   <- 返回, RAS 的靶子
```

**JALR 占了全部误判的 37%**，且绝大多数是函数返回 —— BTB 只记得住"上一次"的
返回地址，同一个函数被不同地方调用时目标会被反复改写。RAS 专门记调用点。

## 实现

`ras.sv`（8 项 × 32 位 + 指针，饱和不回绕）+ BTB 增加 `is_ret` 标记。

**关键设计点：前端在 IF 段无法识别返回指令**（要译码才知道哪条是 `ret`），所以：

1. EX 段解析出控制流后，除了写 BTB 目标，还写一个 **`is_ret` 标记**；
2. 下次取到同一条 PC，BTB 命中且 `is_ret=1` → 判定"这条是返回"，
   于是改用 **RAS 栈顶**作为预测目标，忽略表里存的旧目标。

即 **BTB 负责"记住这条 PC 是返回"，RAS 负责"现在该返回到哪"**。

**只在 EX 更新，不做投机压栈** —— 陷阱/预测错误会冲刷流水，投机 push/pop 后栈就脏了，
且没有廉价的回滚手段。EX 是解析点，此时该指令即将提交（被冲刷时 `upd_en` 无效），
所以栈始终精确。压栈的值就是链接值（JAL/JALR 写进 x1/x5 的 `pc+4`）。

## 踩的坑：RAS 明明在跑，却对误判毫无影响

第一版实测：**push=3253 / pop=3253 / 栈顶非空 462533 拍** —— RAS 明显在工作，
但 `ticks` 和 `mispredict` **逐位不变**。

这个"完全不变"正是"没生效"的典型信号（PITFALLS R17 的教训）。加了两条自证：
```
预测判为返回 = 0                      <- 从没被选中!
BTB 中 is_ret=1 的表项 = 0            <- 标记根本没写进表
```

真因：`is_ret[uidx] <= upd_is_ret;` **只写进了 gshare 分支，而默认走的是 Smith 分支**
—— 我改 `btb.sv` 时同时维护了两套方向预测器实现，只补了一处。

> 教训：**同一个数组在多套 `ifdef` 分支里各有一份更新逻辑时，任何字段都要每处都补。**
> 那条"BTB 中 is_ret=1 的表项数"的自证就是为这类问题加的，它一句话就定位了。

## 实测数据（修好之后）

| 指标 | 无 RAS | **有 RAS** | 变化 |
|---|---|---|---|
| **CoreMark/MHz** | 2.3611 | **2.3701** | **+0.38%** |
| **fmax** | 61.3 MHz | 59.6 MHz | **−2.8%** |
| **LUT** | 4015 | 4142 | +127 |
| FF | 1381 | 1423 | +42 |
| **CoreMark/LUTs** | 5.881e-4 | 5.722e-4 | −2.7% |
| **绝对吞吐** | 144.7 | **141.4** | **−2.3%** |

机制本身完全按预期工作：

```
JALR 误判    4378 -> 3558   (-820)
总误判      11535 -> 10715
ticks      423527 -> 421931   (-0.38%)
预测判为返回 0 -> 2500, 其中 RAS 目标 != BTB 目标 = 842
```

> 注意 **−820 与"RAS≠BTB 目标 842"几乎相等** —— 说明每一条被 RAS 纠正的预测
> 都确实少了一次误判，机制是干净的，没有引入新的错误预测。

## 判定：reject（默认关闭）

按纪律：**赢 1 项（CoreMark/MHz）、输 4 项（fmax / LUT / CoreMark-LUTs / 绝对吞吐）**。

真因是**时序**：栈顶是 `stk[sp-1]` 的 8:1 mux，而它落在**已经最紧的 `pc_target`
路径**上（预测目标 → 下一拍 PC）。用 0.38% 的周期收益换 2.8% 的 fmax 不划算。

**要救它**需要一个结构性改动：让栈顶**提前一拍**准备好（寄存 RAS top），
但那样返回目标就晚一拍、预测也就没用了；或者把 RAS 查询并进取指流水一起重排。
两条路的收益（0.38%）都撑不起改动量。

**所以保留 `RAS_EN` 宏与完整实现+数据**，等取指流水真的重排时一起处理。
