# P4 · 宏失效事故与配置回退（**必读：它推翻了 P3 的两个结论**）

**日期**：2026-10-05  **结论：P3 的"零代价优化"不成立，已回退到上板验证过的配置**

---

## 1. 发现了什么

在给方向预测器加 gshare 时, 发现改动**完全没效果**。顺藤摸瓜查出工具的一个
静默 bug (`PITFALLS` R17):

```python
# tools/fpga_workflow.py 原代码
flags = ["+" + d for d in defines]        # -> vlog -sv +IMEM_REG_READ ...
```

**`vlog` 把 `+FOO` 当未知选项, 宏根本不会被定义, 而编译"成功"**。实测最小复现:

```
vlog -sv +FOO         ->  RESULT: FOO_NOT_DEFINED
vlog -sv +define+FOO  ->  RESULT: FOO_DEFINED
```

正确写法是 `+define+NAME`。

### 为什么后果严重

综合侧走的是 Tcl 的 `-verilog_define`，**那个是生效的**。于是形成
**"综合开了宏、仿真没开宏"** —— 两边跑的不是同一份设计：

| | 综合侧（宏生效）| 仿真侧（宏**未**生效）|
|---|---|---|
| `IMEM_REG_READ` | LUT 3945 → **2656** | 一直跑组合读版本 |
| `LOAD_RESULT_REG` | fmax 65.3 → **75.0** | 一直跑组合版本 |
| 结论 | 数字是真的 | **"ticks 逐位不变、零代价"是假的** |

也就是说 `results/p3-imem.md` 与 `results/p3-load-result.md` 里
**"CoreMark/MHz 逐位不变"这条证据是无效的** —— 它测的根本不是那份设计。

## 2. 修好宏传递后的实测

```
配置                     结果      ticks
------------------------------------------------------
三个宏全关 (基线)          PASS     423527
仅 IMEM_REG_READ          FAIL     仿真 timeout (取指与 PC 配对错位)
仅 LOAD_RESULT_REG        FAIL     仿真 timeout
仅 BTB_GSHARE             PASS     449317   <- 能跑, 但比基线慢 6%
三个全开 (原默认)          FAIL     仿真 timeout
```

即：两个所谓"零代价优化"实际是**坏的**，第三个（gshare）是**负优化**。

### 为什么上板还能 PASS

因为**上板跑的是 ILA 版 bitstream**，而 `build_ila.tcl` 的 `verilog_define`
**只给了 `USE_ILA` + 两个镜像路径，没带任何架构宏** —— 也就是上板验证的是
**"三个宏全不开"** 的配置。而评分版当时默认开宏。
**"上板验证通过"并不等于"评分版通过了"**（`PITFALLS` R18）。

## 3. 处置

1. `fpga/build.tcl` 与 `tools/fpga_workflow.py verify` 的默认值**统一改成三个宏全关**，
   与上板验证过的配置一致。要用必须显式指定（`IMEM_REG_READ=1` / `LOAD_REG=1` /
   `BTB_GSHARE=1`，仿真侧 `--imem_reg_read` / `--load_reg` / `--gshare`）。
2. 三个宏都**必须在仿真里跑通 `verify` 才允许综合**。
3. 加**自证标志**：宏生效时模块 `$display` 一行（如 `[btb] GSHARE ... ACTIVE`），
   否则"改了没效果"永远分不清是算法无用还是宏没定义。

## 5. 待重做（按收益排序）

### 5.1 `IMEM_REG_READ` —— **相位配对已打通；剩一处停顿释放气泡未对齐**

**收益**：LUT −1228（占全核 31%，单项最大）。**功能收益为零**（CoreMark/MHz 不变）。

#### 5.1.1 前四轮失败的真正根因（已由逐拍实测钉死）

> **重要**：此前（含我上一轮）把根因判为"重定向 mux 选错地址"，并据此改过一版
> `imem_addr = pc_src ? pc_target : far`。**实测证明那条理论是错的** —— 去掉 mux
> 后失败点纹丝不动。真正的原因在下面。

**正确配对 = 纯延迟，一行 mux 都不能加：**

```
组合读: cycle N 内 addr=pc(N) 且 rdata=instr(pc(N))      <- 同拍
寄存读: BRAM 沿锁存 mem[pc], 下一拍才吐出。于是 cycle N+1 那拍
          imem_rdata = instr(pc(N))       <- 上一拍 pc 处的指令
          pc         = pc(N+1)            <- 下一拍要取的地址
        两者差一拍 -> IF/ID 必须用 pc 的**延迟副本**去配
        IMEM 的地址则必须接**当前 pc**（沿锁存看到的就是当拍 addr 输入）
```

前四轮全部栽在"想在延迟副本上做补偿"（①只延迟；②再用延迟 PC 查预测；
③加 stall 门控；④照抄 pc 的下一拍值）。但 `pc` 寄存器在寄存读结构下**本身就已经
是取指地址寄存器**：它的当前值就是"下一拍要被取指的地址"，重定向/停顿对它已经
天然正确。再叠一层补偿等于把作用施加两次 —— 症状就是跳转目标整体偏移。

**实测抓到的第二个错**（我自己犯的，值得记）：把 `imem_addr` 接成
`pc_src ? pc_target : pc_plus4`（即"下一拍的 pc 值"）会**提前一拍取指**：

```
cyc0 addr=0x80000004 -> cyc1 imem=instr(0x80000004) 而 pc_d1=0x80000000   <- 错开一拍
```
这与 `pc.sv` 内部 `pc <= pc_src ? pc_target : pc_plus4` 是**两件事**：那句算的是
"下一拍装什么"，这里要的是"当拍喂给存储器什么"。

#### 5.1.2 已落地的修复与实测效果

| 改动 | 位置 | 说明 |
|---|---|---|
| `pc_d1` / `pc4_d1` / `pred_taken_d1` | `core.sv` | 延迟副本，**纯延迟无 mux**；组合读下直通（逐位等价） |
| `imem_addr = pc` | `core.sv` | 当拍地址，不是下一拍 |
| `if_id.pc_in/pc_plus4_in/pred_taken_in` | `core.sv` | 改接延迟副本 |
| `pipe_release`（停顿释放气泡） | `core.sv` | **仅 `IMEM_REG_READ` 下注入**，用 `ifdef` 与组合读隔开 |

**效果**：

| 配置 | 前四轮 | 现在 |
|---|---|---|
| `--imem_reg_read` | **全部 timeout**（20000 / 5000000 拍） | **不再 timeout** |
| 11 项回归 | 0 PASS | **3 PASS**（`tb_units` / `tb_core_trap` / `tb_sw_hello`）|
| 其余 | 跑飞 | 前进到**具体功能断言**（`tohost=3` 等），不再跑飞 |

**默认配置逐位不变（已证）**：回归 `PASS 10 | XFAIL 1`；
`profile` 给出 `ticks 468659 / CPI 1.099`，与改动前**完全一致**。

#### 5.1.3 仍未闭环：停顿释放气泡的位置

注气泡的拍与组合读对不齐。逐拍证据（`basic.S` 的 load-use 组，
`0x80000038 = add t3,t2,t0`，`0x8000003c = lui t4,0xA2345E78`）：

```
comb cyc15 st=1 lu=1   if_pc=0x38                     <- 停顿中
comb cyc16 st=0        if_pc=0x38   （pc+4 领先，天然气泡）
comb cyc17 st=0        if_pc=0x3c(0xa2346eb7 lui)     <- lui 进 ID/EX，正确

reg  cyc16 st=1 lu=1   pc=0x40 d1=0x3c ifi=0x00538e33(重复)
reg  cyc17 st=0 rel=1  pc=0x40 d1=0x3c ifi=0x00538e33 <- 气泡**晚一拍**才注
reg  cyc18             if_pc=0x00000000(NOP)          <- lui 被整条丢掉
     -> 后续 0x8000004c 的 `j` 被解析成跳去 0x80000050
```

**机理（已确认）**：寄存读下 `imem_rdata` 与 pc 同拍前进，停顿期间
`pc` 冻结 → imem 输出冻结 → **IF/ID 反复重写同一条指令**；停顿释放那一拍
流水开始流动，ID/EX 会取走"那条已经在 ID/EX 里的指令"的副本 → 同一指令执行
两次、紧随其后的一条被整条跳过。

**为什么简单注气泡补不上**：气泡需要落在 cyc16（`pipe_release` 是 cyc17），
而 cyc16 时 `pipe_stall` 还是 1 —— 用 `pipe_stall` 的组合拍判定天然晚一拍。
**正解方向**：IF/ID 的写口不能只用 `!stall` 门控，必须加"数据有效"判定 ——
即知道自己要配的那条指令**是否已经从 imem 回来**（数据/地址偏斜跟踪）。
这是一个明确的、有界的目标，不要再在 `pipe_stall` 的组合拍上打补丁。

**已验证的负结果（不要再试）**：
- **统一取指地址寄存器（让 IMEM 与 IF/ID 读同一个 `pc_d1`，`pc_d1 <= pc_src?pc_target:pc_plus4`）**
  → **实测更差**：PASS 从 3 掉到 1，且 hang 在 `id_pc=0x80000030`（最早那个失败点）。
  原因：`pc_d1` 取 pc_next 时，**重定向那一拍它看到的是新地址，而 IMEM 这一拍输出仍是
  旧地址的指令** —— 比"用延迟副本配当前 pc"更严重的错位。
- 无条件注入释放气泡（不加 `ifdef`）→ **把组合读路径也弄坏**（`tohost=3`）
- `imem_addr = pc_src ? pc_target : pc_plus4` → 提前一拍取指，全错
- 在延迟副本上做重定向/停顿补偿 mux → 跳转目标整体偏移（前四轮）

#### 5.1.4 三版实测排序（本轮的裁决依据）

| 版本 | 寄存读 PASS | 说明 |
|---|---|---|
| 延迟副本配当前 pc + 释放气泡 | **3 / 11** | 当前保留，这批里最好 |
| 统一 FAR（共用 pc_d1） | 1 / 11 | 更差，已否决 |
| 前四轮（各种补偿 mux） | 0 / 11 | 全部 timeout |

**三版都做不干净的同一个结构性约束**（这是本轮的**关键结论**）：

> 寄存读把"取指地址"与"取回指令"的配对变成一条**跨周期回路**：
> `pc_d1` 既要跟 `pc` 走（停顿/顺序），又要在重定向那一拍立刻改口；
> 而 IMEM 的输出永远滞后它一拍。这两个要求**不可能靠一个寄存器同时满足** ——
> 所以要么多一个取指气泡（= 重定向惩罚从 2 拍变 3 拍），
> 要么改成"取指地址寄存器 + 取指数据寄存器"两级（= 改流水线级数）。
> 前者代价约 4.9%（重定向占比），后者违反本项目"不改级数"的约束。

#### 5.1.4 顺带修掉的工具缺陷（同族坑）

`verify` 的 `test_fingerprint()` 原来**不含宏配置**，于是跑完默认配置再跑
`verify --imem_reg_read`，11 项全部被判"缓存命中"而 **SKIP** ——
明明换了一整套架构宏、跑的根本不是同一份设计。
这与 PITFALLS R17（宏没传到 ModelSim）是**同一族**：两边跑的不是同一个东西。
已抽出 `_global_defines(args)`，`verify` 与指纹共用同一份口径。

> 教训补充：**增量缓存必须包含"配置"维度**，否则它会把配置差异伪装成"未受影响"。

#### 5.1.5 遗留的正确做法（仍然有效）

把取指口重构成标准的 **取指地址寄存器 (FAR) + 取指数据寄存器**，重定向在这一级
闭环；并把 BTB 预测寄存一级（`pc <= pred_target_r`），这样 **BTB 的组合查表也就
不在 `pc` 路径上了** —— 那才是寄存读最大的时序收益（当前关键路径 route 占 65.5%）。

**周期代价为 0**：重定向距离仍是 2 拍（相位平移，相对错误路径的领先量不变）。

### 5.3 `BTB_GSHARE` —— 实测慢 6%，需调参

已实现（`btb.sv` 的 `BTB_GSHARE` 宏，含自证 `$display`），但 6 位历史的 gshare
在 CoreMark 上**不如**纯局部 2 位 Smith（ticks 423527 → 449317）。可试：
只对条件分支记历史、缩短/加长历史、加 tournament 与 Smith 混合。
另：实测 **JALR 误判占全部误判的 37%**，RAS 是独立的收益点（历史记录 RAS+BTB128
那次是净亏，但那是**同时**改了 BTB 容量）。

> 教训：**"完全不变"往往是"没生效"的征兆，而不是"代价为零"的证据。**
