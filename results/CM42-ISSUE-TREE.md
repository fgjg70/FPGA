  回归 `verify --force` **PASS 12**。

  2026-10-23 实测 `-O2`：ticks **463,364 → 371,390**，CM/MHz **2.158 → 2.693（+24.8%）**，

- **改动**
  - `tools/build_sw.py`：`cm_defs` 的 `FLAGS_STR` 改 `-O2`；`cm_rv32im` / `cm_hw` 的 `opt` 改 `-O2`
  - `sw/` 无需改动
- **注意**：`.text` 从 9,676 B 涨到 **13,152 B**（imem 占用 59%→80%）。
  **不要同时上 `-O3`** —— 它会溢出 16 KB imem **2,404 字节**（需 ≥20 KB，见 I-2A 的 imem 扩容）。
- **验收（全部满足）**
  ```bat
  python tools\build_sw.py --all --with-hw --clk-hz auto
  python tools\fpga_workflow.py verify --force
  python tools\fpga_workflow.py synth --prog cm_hw --no-lc --fanout-limit 128 ^
      --pblock-range off --contain-routing --place-directive AltSpreadLogic_high ^
      --tag s0-o2 --record
  ```
  - `verify` 输出 **PASS 12**
  - `tb_sw_coremark.log` 里 `ticks=371390`、`CRC-valid=1`
  - `coremark.csv` 新行 CM/MHz ≥ **2.69**，LUT ≤ **3,200**

- **⚠ 陷阱：`synth` 的默认参数不是交付配方**（2026-10-23 实测踩到）
  | 配方 | LUT | fmax |
  |---|---:|---:|
  | 直接 `synth --prog cm_hw`（默认） | 2,892 | **141.9** |
  | 交付配方（上面那串） | 3,098 | **150.2** |
  **同一份 RTL、同一个镜像，差 8.3 MHz，纯粹来自构建参数。**
  默认配方开了 LUT 合并（LUT 反而更少 206 个），但 `--no-lc` + `--fanout-limit` +
  `AltSpreadLogic_high` 的组合才让频率上去。
  **⇒ 任何跨配方的 fmax 比较都无效**，必须用同一串参数才能判断"是 RTL 变了还是配方变了"。
  （这条又独立印证了一次：**LUT 数量与 fmax 无关，配置与布局才是决定因素**。）

- **本次实测记录（2026-10-23）**
  - 仿真：`PASS 12`，`ticks=371390`，CM/MHz **2.6926**
  - 权威停顿：`window stalls = 69,332`，其中 **load-use 50,540 拍 / 29,606 事件（1.70 拍/次）**
    ← 纠正了先前"76,987 / 59,742"的粗估（那是用 `cycles − fetch` 反推的，混进了 flush 与重叠）
  - **imem 余量告急**：`cm_hw.elf` 的 `.text = 15,804 B` / 16,384 B = **96.5%**，
    只剩 580 字节 ⇒ 任何给 CoreMark 加代码的动作都会溢出，imem 扩容必须先做
- **产物**：`coremark.csv` 行 `s0-o2`；上板后写采集清单
- **失败处理**：如果 LUT 涨过 3,300 或 fmax 跌出 145，记录数据后**保留 `-Os`**，直接跳 I-1c。
- **回退**：改回 `-Os` 一行即可。

### [I-1a] 7 级单发射探针（决定"能不能保频率"）

- **依赖**：I-0
- **状态**：`[ ]`
- **目的**：**只验证"拆流水"这一件事**。不改发射逻辑、不加 ALU、不做双发射。
  回答一个问题：把 5 级摊到 7 级，fmax 能不能到 130+？
- **改动范围**
  - `core.sv`：EX 段拆成 `E1`（地址/运算）、`M`（LSU）、`E2`（结果回写）
  - 新增两个流水寄存器模块（或扩展现有 `ex_mem_reg.sv`）
  - `hazard_unit.sv`：停顿信号需要适配新级数
  - **不要**新增 ALU，**不要**改发射宽度
- **验收**
  - `verify` **PASS 12**（功能不能坏）
  - `synth --tag s1-7stage --record`：**fmax ≥ 130**，CM/MHz 不降于 2.65
- **门 G1a**
  | fmax | 结论 |
  |---|---|
  | ≥130 | 通过，I-2A 可继续 |
  | 120~130 | 勉强，需先查新 top-1（`tools/path_hotspot.py`）再决定 |
  | <120 | **停止双发射路线**，转 I-2C（单发射保频） |

- **❌ 实测判负（2026-10-23 23:43，tag `i1a-probe`）—— `[/]`**
  **方法**：隔离分支（`exp/i1a-probe`）上做**物理探针**——只在 `前递 mux` 与 `ALU` 之间插一级
  操作数寄存器，把当时 top-1 的链条切断，**故意不保功能**，只跑 `synth` 测 fmax。测完回退分支。

  | 项 | 现状 | 探针 | 变化 |
  |---|---:|---:|---:|
  | fmax | 150.2 | **151.8** | **+1.1%** |
  | LUT | 3,098 | 2,988 | −110 |
  | 被切断的 top-1 | `u_mem_wb/pc_plus4_reg → 前递 mux → ALU(4×CARRY4) → u_ex_mem/alu_out_reg/D`，**6.663 ns（logic 1.970 / route 4.693 = 70.4%）** | | |

  **结论：切掉 top-1 只换来 1.1%（1.6 MHz）。**

  **为什么**：这条路径 route 占 **70.4%**，切掉的是那 29.6% 的逻辑，**布线延迟不会消失**——
  其他路径立刻接班。这正是 `PITFALLS` **R47** 说的"top-N 是**一堵墙**时，RTL 逻辑重排期望≈0"，
  也是 `CHANGELOG §13.2`"10 个族全挤在 +0.026~+0.119 ns"的同一现象。

  **⚠ 连带推翻的假设（重要）**：
  1. **"加深流水能保频率"不成立** —— 拆流水只是把逻辑分段，**布线距离不变**，
     在 route 占 70% 的设计上收益极小；
  2. ⇒ **7 级双发射不会有"流水加深"的频率补偿**。原估 95~110 MHz 必须下调
     （双发射增加逻辑 + 增加布线，却无补偿）⇒ 实际可能只有 **80~95 MHz**；
  3. ⇒ 绝对吞吐 `4.2 × 85 ≈ 357`，**低于现状 404** ⇒ **4.2 @ ≥100 MHz 基本不可达**。

  **⇒ 门 G1a 触发"<120"分支：I-2A 与 I-2B 的双发射前提消失，转 I-2C。**
- **失败处理**：若功能坏，用 `tools/trace_diff.py` 与基线逐拍比对，定位第一处分歧。
- **产物**：`coremark.csv` 行 `s1-7stage`；`fpga/timing_paths.rpt` 的新 top-1

- **要做的事（按顺序，单变量测量）**

  4. 每项都单独记录精度与 fmax

- **产物**：精度-配置对照表；`coremark.csv` 对应行

### [I-2A] 猜后验证（SweRV 式，主攻路线）

- **依赖**：I-1a、I-1c
- **状态**：`[ ]`
- **核心机制**：详见 `CM42-IMPL-DESIGN.md` §3。一句话：
  **load 数据没到不停顿，指令按预测继续，在 E2 用第二个 ALU 补算并验证分支。**
- **为什么值得做**：实测 59.1% 的 load-use 消费者是**分支**，所以问题不是"晚点算"，
  而是"让分支不必等数据"。
- **改动范围**
  | 文件 | 改动 |
  |---|---|
  | `core.sv` | E1 加 `opnd_ready` 门控；E2 加第二组 ALU + 分支验证 + 重定向重排 |
  | `hazard_unit.sv` | 新增 `opnd_ready` / `e1_invalid` 语义；**移除** C-2 的 2 拍气泡 |
  | `ex_mem_reg.sv` | 扩宽：携带操作数到 E2 |
  | `imem.sv` | 16 KB → **24 KB**（`-O3` 需要），同时输出 64 位 |
  | `alu.sv` | 例化 ×2（不改内部） |
  | `regfile.sv` | 4R2W，参考 `RAM16X1D` 方案 |
- **验收（分两小步，别一次做完）**
  - **A1**：单发射 + 猜后验证 → 停顿 ≤ **45,000**，CM ≥ **3.0**，PASS 12
  - **A2**：加宽到双发射 → IPC ≥ **1.0**，CM ≥ **3.6**，fmax ≥ **100**
- **最高风险 R1（正确性）**：E1 在 `opnd_ready=0` 时**绝不能有副作用**
  （不写寄存器/内存、不触发异常、不更新 BTB）。
  → 必须写仿真断言：`!opnd_ready → (reg_we & mem_we & trap & btb_upd) == 0`
- **失败处理**：A1 不达 3.0 就检查"分支验证是否正确产生了额外重定向"——
  用 `tb_sw.sv` 的停顿构成计数，看是不是**误判数变多了**（说明预测被更早推翻）。
- **产物**：`coremark.csv` 行 `s2a-verify` / `s3-dual`；新 top-1 路径；LUT 数字

### [I-2B] load 前递（biRISC-V 式，对照组）

- **依赖**：I-1a
- **状态**：`[ ]`
- **核心机制**：把 load 数据放回 WB→EX 前递路径，load-use 回到 1 拍气泡（经典做法）。
- **为什么作为对照组**：biRISC-V 用这个 + `SUPPORT_LOAD_BYPASS` 做到 4.1 CM/MHz，
  但只承诺 50 MHz。**它代表"用频率换 IPC"的另一端**，正好和 I-2A 对照。
- **改动范围**：`hazard_unit.sv` 的 `pre_wb_*` 去掉 `!ex_mem_mem_read` 门控；
  同步调整 `load_use` 的拍数；`core.sv` 的 `wb_data` 前递源补齐。
- **验收**：CM ≥ **3.1**（单发射）；同时记录 fmax 掉了多少
- **预期**：CM 上升、fmax 显著下降（因为重新接上那条 route 76% 的墙）
- **判据**：如果 **fmax < 110**，说明这条路在我们的工艺上不成立（印证 C-2 的历史判断）
- **产物**：`coremark.csv` 行 `s2b-bypass`；关键路径对比

### [I-2C] 单发射极限（保频路线，最稳）

- **依赖**：仅 I-0
- **状态**：`[ ]` ← **建议先做这一条，它与双发射完全解耦**
- **核心思路**：不碰架构，把单发射的 IPC 从 0.79 推到接近 1.0 的上限，同时保住 150 MHz。
- **要做的事（按 ROI 排序）**
  1. RAS + 预测器调优（与 I-1c 共用成果）
  2. `muldiv` 完全流水化（消除 `busy` 冻结，当前占约 3%）
  3. 减少重定向惩罚（`C-11` 已经做到 1 拍，检查是否还有空间）
  4. **不开** load 前递（那是 I-2B，会掉频）
- **验收**：CM ≥ **3.2**，fmax ≥ **145**
- **天花板**：单发射 IPC ≤ 1.0 ⇒ CM/MHz ≤ **3.40**（指令数 294,403 时）。
  **这条路线到不了 4.2，这是算术事实**，但它的**绝对吞吐**可能最高：
  `3.40 × 145 = 493` vs I-2A 的 `4.20 × 100 = 420`。
- **产物**：`coremark.csv` 行 `s2c-single-max`；四项指标齐全

### [I-3] 组合优化（可选，G2 之后）

只在"单条路线差一点"时做：

| 组合 | 内容 | 预期 |
|---|---|---|
| A + C | 猜后验证 + RAS/预测调优（C 的 1、3 项） | +3~5% |
| A + `-O3` | 猜后验证 + imem 24KB + `-O3` | +10~15%（指令数再降） |

### [I-4] 上板闭环（任何选型之后都要做）

## 5. 给执行者的三条提醒

1. **先做 I-0 和 I-2C**。它们零风险、不依赖任何人，能立刻把 CM/MHz 从 2.16 抬到 3.0+，
   而且万一后面全失败，你已经有一个可以交付的结果。
2. **I-1a 是整棵树的枢纽**。它只做一件事（拆流水），但只要它不通过，I-2A 和 I-2B 全都不用试。
   花半天跑它，比花两周写双发射再发现频率上不去划算得多。
3. **每完成一个 ISSUE 就往 `coremark.csv` 记一行、往 `results/` 写一段**。
   本仓库的历史教训是：没有记录的优化会在下一轮被当成"没做过"重新试一遍
   （`PITFALLS` R1 的全部 51 条都是这个形态）。
