# 主频差距的核实与结论（RVCoreP-32IM vs 本核）

> 2026-10-13 编写。**本文只写"核实到的事实"与"实测到的数字"**，推测一律标注为推测，
> 并给出可复核的来源（论文页码/行、XPR 选项、本地 CSV 行、报告文件）。
> 目的：在动手之前，先把"他们到底多快""我们到底能到哪"钉死。

---

## 1. 核实：「他们能跑多少」——逐条带来源

### 1.1 论文里的权威数字（唯一有完整条件的表）

来源：`arXiv:2010.16171` **Table I**（抽文 `2010.16171.txt` L413-468；论文 PAGE 6）
条件（论文原文 L400-408）：**xc7a100tcsg324-1（Artix-7 speed grade -1，即最慢档）**、
**Xilinx Vivado 2018.3**、logic synthesis 用 `Flow PerfOptimaized high`、
place&route 用 `Performance ExplorePostRoutePhysOpt`；频率取法是
"the clock cycle constraint in the 1MHz scale，取 timing slack 仍为正的最高频率"（L470-472）。

| 配置 | 4KB | 64KB | Slice LUT(4K/64K) | Slice register | Slice | DSP |
|---|---|---|---|---|---|---|
| RV32I | **174** | 164 | 958 | 647/641 | 391/396 | 0 |
| RV32IM(radix-4) | 169 | 162 | 1456/1457 | 970 | 548/565 | 0 |
| **RV32IM(DSP)** | **169** | **162** | **1331/1338** | **901/903** | 487/539 | **4** |
| VexRiscv(RV32IM) | 153 | 143 | 1367/1394 | 1044/1013 | 533/503 | 4 |

⇒ **他们最快的配置是 174 MHz（RV32I、4KB），RV32IM(DSP) 是 169/162 MHz。**
⇒ 注意：**他们的存储器是 4KB 或 64KB 两种极端**，不是任意值。

### 1.2 他们官方 Wiki 的说法

来源：`https://www.arch.cs.titech.ac.jp/wk/rvcore/doku.php?id=start`（Kise Lab, Tokyo Tech）
- "By default, the **operating frequency of the processor is set to 160MHz**."（FPGA 实现段）
- 支持板：**Nexys 4 DDR**（`xc7a100tcsg324-1`）与 **Arty A7-35T**（`xc7a35ticsg324-1L`，更小的 35T、-1L 更慢）
- 推荐工具：**Vivado 2019.2**；源码只有 5 个 `.v`：`top.v main.v uart.v debug.v proc.v`

### 1.3 他们的生产配方（我们从 `main.xpr` 逐条抄出）

`synth_1` 的 Run Description 原文（XPR L201）：
> "Higher performance designs, **resource sharing is turned off**, the **global fanout guide is set
> to a lower number**, **FSM extraction forced to one-hot**, **LUT combining is disabled**,
> **equivalent registers are preserved**, **SRL are inferred with a larger threshold**"

对应 XPR 选项：`ResourceSharing=2(off) / RepFanoutThreshold=400 / FsmExtraction=one_hot /
NoCombineLuts=1 / KeepEquivalentRegisters=1 / ShregMinSize=5 / Directive=7`；
实现策略 = **`Performance_ExplorePostRoutePhysOpt`**。

### 1.4 ⚠ "230+ MHz" **无法核实**

我查了三处，**都没有 230 这个频率**：
1. 论文全文（`2010.16171.txt`）—— 只有 Table I 的 174/169/162 与 CoreMark 分数；
2. 官方源码包（`.rvcorep_scratch/rvcorep_ver046`、`rvcorep_ver053`）—— `result.txt` 里的 "230"
   是 `branch prediction hit : 23082568`（**命中次数**，不是频率）；`.v/.xdc/.rpt` 里没有频率声明；
3. 官方 Wiki 主页与它的修订记录 —— 只有 160 MHz。

⇒ **请提供"230+ MHz"的出处**（哪篇论文/哪个页面/哪个版本）。在此之前，我按
**"他们的主频等级 = 162~174 MHz @ speed grade -1"** 来做比较与定目标。

### 2.2 冲 150 的过程（每一步都单变量实测）

| 档 | 配置 | WNS | 结论 |
|---|---|---|---|
| 134.375 | A+C（当前树） | **−0.081** | 只差 **1~2 跳布线**（48/49 条同族 = DSP 级联） |
| 150 | A+C | −0.770 | 差 0.77 ns |
| 150 | 只搬 `-directive`（默认） | −0.770 | 基线 |
| 150 | **搬他们整套 `Flow_PerfOptimized_high`** | **−1.621** | **明确负结果**：配方不可移植 |
| 150 | 不要 Pblock | −1.164 | 更差（Pblock 有用） |
| 150 | `place Default` | −0.759 | 与默认同档 |
| 150 | + C-12c（操作数寄存） | −0.852 | 机制成功（DSP 族消失）但**净负** |
| 150 | + 复位网 `max_fanout` | −1.341 | **明确负结果**，已回退 |
| 134.375 | route `HigherDelayCost` | −0.097 | 更差 |
| 134.375 | route `NoTimingRelaxation` | −0.081 | 同默认 |
| 134.375 | route `Explore` | −0.227 | 更差 |
| 134.375 | Pblock `X0Y1:X2Y3` | −0.178 | 更差 |
| 134.375 | Pblock `X1Y1:X3Y3` | −0.091 | 更差 |
| 134.375 | Pblock `X0Y0:X2Y2` | −0.195 | 更差 |
| 134.375 | **现状 Pblock `X0Y1:X2Y2`** | **−0.081** | **所有试过的物理旋钮里最优** |

⇒ **结论：134.375 档差的 0.081 ns，用尽"配方 / 路由指令 / 放置指令 / 区域约束"四类旋钮都补不上。**
它确实是"物理尺度"的差距（1~2 跳布线），但**已经没有免费旋钮可用**；要继续只剩结构改动。

**记录缺陷（已修）**：以上这些"时序门失败"的点，此前**完全不进 `results/coremark.csv`**
（`cmd_synth` 在 `BUILD_TIMING=FAIL` 处直接 `return 1`，早于 `parse_reports/append_csv`），
所以冲 150 的全部失败点只留在会被下一次构建覆盖的 `fpga/timing.rpt` 里 —— **负结果台账残缺**。
2026-10-13 已修：失败点现在也会解析报告、打印**达成值**，并以 **`status=timing_fail`** 入台账
（明确标注"这不是可交付结论，只是达成 fmax"），因此既不会被当成 keep 锚点，也不丢证据。

**关键观测**：150 档的绑定族是 **DSP 级联**（44~49/50 条），逐跳只有 3 级：
```
ex_mem/ctrl_reg[wb_src] → LUT4(0.105 logic/0.789 route) → LUT5(0.105/0.586)
  → **DSP48E1 内部 A→M→P 3.397ns** → prod_uu_reg/PCIN
```
DSP 内部链占 6.247 ns 的 **54%**；前端逻辑只有 0.21 ns 但布线 1.375 ns。

## 3. 差距分析：他们为什么快（按证据强度排序）

### 3.1 【强证据】设计规模是我们的 1/2
| | 我们 | 他们(RV32IM DSP, 64KB) | 比值 |
|---|---|---|---|
| Slice LUT | **2789~2848** | 1338 | **2.1×** |
| Slice register | 1393~1447 | 903 | 1.5× |
| DSP48E1 | 8 | 4 | 2× |
| RTL 文件 | **23 个 `.sv`（约 4.7k 行）** | **5 个 `.v`（`proc.v` 一个文件装下整核）** | — |

我们多背的东西（他们都没有）：**Zicsr/CSR 文件、A 扩展(AMO)、GEMM 加速器、
ILA/调试钩子、两级流水 BTB(512)+PHT(8192) 预测器、完整的 trap/中断机制**。
⇒ 逻辑多一倍 ⇒ 拥塞与布线更长。**这是最可能的主因，但它不是"能靠改几行解决"的东西** ——
要减就得砍功能，而那会掉 IPC 与功能覆盖。

### 3.2 【强证据】存储器几何
- 我们：**imem 16 KB + dmem 16 KB**（`rv32_pkg.sv:311-313`），**Block RAM Tile 9.5**（RAMB18×3 + …）。
- 他们：**4 KB 或 64 KB**（论文明确只做这两种）。
- **本仓库自己的对照实验**（ref5 参照核，`.ref5_scratch` + `ref5/REPORT.md`）：
  同 RTL、同 Pblock/place/route/phys，**只把存储器从 4KB 改成 16KB ⇒ 137.25 → 118.57 MHz（−18.7 MHz）**。
- 论文自己也说关键路径里 "**BRAM blocks input/output has routed**"（L492-493）。
⇒ **这是量级最大的单一杠杆（~19 MHz）**，但**用户已明确要求 BRAM 留够**，故**不做**。
（若将来允许：imem 16→12KB 只需 2437 词，dmem 16→12KB 也够用；真正省 BRAM 要挪 `TOHOST_ADDR` 与链接脚本。）

### 3.3 【中证据】绑定路径的性质不同
- **他们**：关键路径 = "register bypassing from the write back stage to execute stage
  propagates through AGU for memory load/store"（论文 L488-491）—— **路由主导**，他们接受它并跑到 162。
- **我们**：C-2 把那条等价路径**拿掉了**（load 出前馈、load-use 2 拍），现在撞上的是
  **DSP 级联**（DSP 内部 3.4 ns 占 54%）。**我们走得更远，但撞上了另一堵墙。**
- 换句话说：**不能拿"我们的墙"和"他们的墙"直接比快慢**；他们的 162 是在"还带着那条路由墙"的情况下拿到的，
  而我们的墙是"把那条墙拆掉之后露出来的新墙"。

### 3.4 【弱证据/未量化】工具版本
他们用 **Vivado 2019.2**，我们用 **2018.3**（本机只装了这一个）。版本间的 QoR 差异真实存在，
但**未量化**，且**用户已决定不换**（要往盘古迁移）。

### 3.5 【已排除】"没抄对他们的工具选项"
实测把他们的整套 `Flow_PerfOptimized_high` 搬过来：**150 档 −0.770 → −1.621（更差 0.85 ns）**。
⇒ 该配方是为 1338 LUT 的扁平设计调出来的；对我们 2789 LUT 的设计，`-no_lc`/`-fanout_limit 400`/
`-keep_equivalent_registers` 反而增加拥塞。**这条路已排除，不要再试。**

### 3.6 速度等级要换算
他们在 **-1**（最慢档）上拿 162~174；我们在 **-2** 上拿 128~134。
粗略换算（同一 netlist，-2 约比 -1 快 15~20%）：**把我们的设计放到 -1 上，大约只有 110~117 MHz。**
⇒ **同工艺档位下，他们的核比我们的快约 40%** —— 这才是诚实的差距表述。

## 5. 目标与计划（待你确认后执行）

**门槛约束（你已明确）**：① 不换工具链（2018.3，往盘古迁移）；② 不缩 BRAM；③ 能到 150 最好，不行则接受现状。

### 计划 A（推荐，低风险）：把交付档钉到"能过门的最高档"
1. 完成 134.375 的 **Pblock 细化**（正在跑，3 个区域变体）；
2. 若能过门 ⇒ **重建镜像（4700 迭代，15.88 s ≥10 s ✓）+ ILA 流过门 + 上板验证** ⇒ 交付 **134.375 MHz**（+6.25 MHz）；
3. 若 Pblock 也不行 ⇒ 接受 **128.125 MHz**（已上板验证），停止。

### 计划 B（若要冲 150，需你批准"结构战役"）：
按证据，150 需要接连解决三族，且必须逐项单变量实测：
1. **DSP 级联族（48~49 条）**：唯一已知可行手段是 C-12c（操作数寄存），代价 ticks +2.08%；
2. **`alu_out_reg/D` 族（22~31 条）**：C-12c 之后接班的新墙，需要新的结构抓手（未研究）；
3. **复位网族（最多 16 条）**：在 150 档才露头；已试 `max_fanout`（更差），需换手段（复位缓冲树/同步复位重构）。
**预期**：即使三项都做成，150 也只是"刚好过门"；**风险**：每项都可能像 C-12c 一样"消掉一族、墙转移"。
**我的建议**：先做计划 A 把 134.375 落袋，再决定是否投入计划 B。

### 明确不做（已排除，避免重复劳动）
- 换综合/实现配方（实测更差）；
- 换 route/place/phys_opt 指令（实测无收益或更差）；
- 去 Pblock（实测更差）；
- 缩 BRAM（你的要求）；
- 换 Vivado 版本（你的要求）。

## 6. 诚实结论

1. **"230+ MHz" 无法核实** —— 论文、官方源码、官方 Wiki 三处都没有；请给出来源。
2. **他们的真实水平 = 162~174 MHz @ -1**（最慢档）；换算到 -2 约 190~200 MHz。
3. **我们的真实水平 = 128.125 MHz（已上板）**，同档位下约为他们的 **60%**。
4. **差距的主因（按证据强度）**：① 我们的设计**大一倍**（多了 CSR/AMO/GEMM/ILA/两级预测器/trap）；
   ② 存储器几何（16KB+16KB vs 4KB/64KB，本仓库对照实验值 **19 MHz**，但你要求不动）；
   ③ 绑定路径性质不同（我们拆掉了他们的墙，撞上了 DSP 内部 3.4 ns）。
5. **150 MHz 不是"再调几个旋钮"能做到的**：它是三族联合作战，且每一项都有"墙转移"风险；
   **134.375 MHz 只差 1~2 跳布线，是性价比最高的下一档。**
