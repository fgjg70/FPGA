## 1. 时间线：正面成果（每项都是"单变量 + 实测"）

> 判据统一为 **绝对吞吐 `CM/MHz × fmax`**（因为各档频率不同，只看 fmax 或只 look IPC 都会骗人）。

### C-2 · 把 load 数据移出前递路径（论文 §III.A 的核心手法）
- **改动**：`hazard_unit.sv:80-96` 新增 `load_use_mem`、`load_use = ex ∪ mem`（load-use 由 1 拍改 2 拍）；
  `core.sv:610-623` 的 `fwd_wb_data` 三个分支全部从**寄存器**出发；`core.sv:236-249/299-303`
  `pc_flush` 优先于停顿；EX 段副作用门控由 `!pipe_stall` 改 `!hold_mem`。
- **为什么**：论文原文 "the data forwarding path becomes the critical path" +
  "we did not include the load data into the forwarding path from the write back stage"。
  我们当时的 top-1 源端是 `u_dmem/mem_reg_0/CLKBWRCLK`（RAMB36 时钟脚）——数据存储器
  通过组合前递环挂在取指地址脚上。
- **结果**：fmax **76.2 → 83.6 MHz**（+9.7%），**LUT 2734 → 2531（−203）**，
  ticks 413,070 → 449,854（**+8.905%**），绝对吞吐 184.4 → 185.8（+0.8%）。
- **判据**：CSV 行 `c2-loaduse2`；盈亏平衡 82.98 MHz，实测 83.6 ⇒ 净赚。
- **最该学的一点**：**代价必须实测**。推理算出的是 +6.917%，实测是 +8.905% ——
  因为 `load_use_mem` 把"距离 2 的消费者"也纳入了停顿，而旧语义下距离 2 完全免费。
  低估 22% 的教训：**"每次多 1 拍"这类推理会漏掉"事件数变了"**。
- **差点漏掉的正确性问题**：2 拍语义破坏了"C-2 之前 `pipe_stall=1` 只可能是 EX 是 load 或硬冻结"
  这条隐含不变量，若不把 EX 副作用门控拆成 `hold_mem` 口径，会**静默丢掉**
  ①load 后距离 2 的 CSR 写 ②EX 里非法指令/ecall 的精确陷阱 ③与 load 无关分支的重定向 ④BTB 更新。

### C-10 · 前递选择改在 ID 段预选
- **改动**：`core.sv:146` 新增 4 位并行 FF `id_ex_fwd_a/b`；`hazard_unit.sv:144-160`
  改判据为"本拍 ID 看到的产生者位置"（下一拍 EX/MEM 的产生者 = 本拍 ID/EX，下一拍 MEM/WB = 本拍 EX/MEM），
  输出 2 位 one-hot；`core.sv:620-623` 前递 mux 的选择端改用寄存器输出。
- **为什么**：C-2 之后的 top-1 源端是 `u_ex_mem/rd_addr_reg[4]`（**地址不是数据**）⇒
  "地址比较"可以在**更早一拍**算好。这正是参照核 ref5 的 V4 配方（"ALU 操作数在 ID 预选"）。
- **结果**：fmax **83.6 → 87.8 MHz**（+5.0%），**ticks 逐位不变**，LUT +123。
- **判据**：CSV 行 `c10-fwdpre`。
- **最该学的一点**：**"把组合链搬到寄存器前面"往往比"把链变短"更有效** ——
  因为瓶颈常常不是逻辑深度，而是"晚到的信号还要穿过一整套选择逻辑"。

### C-11 · 把"分支误判重定向"寄存一拍（切环）
- **改动**：`core.sv:203-208/852-925` 只寄存**分支误判**：`br_redir_eff = redirect && !trap_redir`，
  `br_redir_r <= br_redir_eff`、`br_tgt_r <= actual_target`；`redir_flush = br_redir_eff || br_redir_r`
  冲 ID/EX 与 IF/ID 两拍；**trap/mret 保持组合**（R-01/R48 的不变量不动）。
- **为什么**：C-10 之后 top-1 是**一堵墙**（50 条最差路径同族、Δ(top1,top2)=0.007 ns、route 75.6%）
  ⇒ 按 PITFALLS R47，逻辑重排没有空间，**唯一出路是把环切开**。
- **结果**：fmax **87.8 → 92.6 MHz**（+5.5%），ticks +2.324%，绝对吞吐 195.1 → 201.2（+3.1%）。
- **判据**：CSV 行 `c11-rebuilt-ctl`；重定向冲刷实测 2.00 拍/次。
- **最该学的一点（机器化判据的威力）**：这条改动唯一可能的致命错误是"错路指令提交"，
  所以作者加了一条**每拍检查的断言** `if (!rst && id_ex_valid && (br_redir_r || br_redir_r2)) $error(...)`
  —— 它在**整个回归的每一拍**上检查，0 次触发。**"能否证明没坏"比"跑过没坏"强一个量级。**
- **事故与被销毁后重建**：这份 RTL 曾被 `git checkout` 抹掉（见 §6.10），
  重建后用 `sha256_tree()` 逐位复核与事故前**完全相同**（`a7248c31…`）。

### C-14 · JALR 目标比较改成单链
- **改动**：`core.sv:994` 在 **ID 段**预算 `id_jr_p = if_pred_target - id_imm`；
  EX 段只算 `ex_jr_diff = ex_rs1 - id_ex_jr_p` 并判 `ex_jr_diff[31:1] == 0`。
- **为什么**：原来是"加法器 → 32 位比较器"两条链串联（8 个 CARRY4）。
  把减法挪到 ID（两个操作数在 ID 都是寄存器），EX 只剩 31 位 OR 归约树。
- **结果**：**ticks 逐位不变**（纯结构）；等价性由新增断言（`pred_target[1:0]!=0 ⇒ $error`）钉住。
- **最该学的一点**：`A == B ⟺ (A−B) 的高位为 0` 这类**代数改写**能把"比较链"换成"归约树"，
  代价是加一条断言把"对齐假设"变成机器化判据（不能靠"本来就字对齐"）。

### C-15 · registered flush（让"组合冲刷"整体消失）
- **改动**：误判拍 N 不组合冲 ID/EX；N+1 用寄存器 `br_redir_r` 冲 ID/EX 与 EX/MEM，
  并用它门控错路影子 X0 在 EX 的**全部副作用**（`csr_we/exc_req/irq_take/mret_req/btb_upd_en/redirect_raw/muldiv.op`）。
- **为什么**：C-11 只切掉了尾巴的"PC/取指地址"那一半，链条改挂到**使能端**（`any_redir` fo=122）。
- **结果**：fmax 87.8 → 92.6 档上 **+1.2 MHz**（**远低于预测的 +2.07 ns**）；
  **但族被治好了**：该族 7.791 → 6.795 ns。ticks 逐位不变。
- **最该学的一点（本轮最重要的认知纠正）**：**瓶颈是"族"，不是"某条路径"。**
  治好 top-1 不等于整族消失。这也是本 session **第 3 次"预测收益 >> 实测"**，
  直接催生了工具 `tools/path_families.py`（按族统计，而不是只看 top-1）。

### C-1 · 两级流水 gshare 预测器（BTB 512 / PHT 8192）
- **改动**：`btb.sv` 重写（512 项 + 两级流水口 `p2_pc → q_*`）；新增 `bht.sv`（PHT 8192 项、
  `ram_style="block"` → 1 块 RAMB18）；`core.sv:378-393` 接线；旧 `pred_*` 口保留但恒"不预测"。
- **为什么**：T 拍只用 `pc_next` 当**查表地址**，T+1 拍 `q_*` 已是寄存器输出 ⇒
  BRAM 的 1 拍读延迟被"提前一拍给地址"吸收，**零气泡**。
- **结果**：ticks 460,311 → **453,942（−1.38%）**；误判 11,530 → **8,020（−30.4%）**；
  精度 88.43% → **91.95%**；JAL 误判 1,102 → **190**。
  代价：**LUT +181、FF +91、BRAM +1**。
- **判据**：CSV 行 `deliv117` / `cB-128`；报告 `results/p4-c1-2stage-gshare.md`。
- **最该学的一点**：`q_taken` **刻意不寄存** —— 再打一拍预测就晚于对应的 PC，
  每个 taken 分支多 1 气泡，ticks 必崩。**"哪里不能再打拍"和"哪里必须打拍"同样重要。**

### C-12a · muldiv 操作数直取 rs1/rs2
- **改动**：`core.sv:750-759` 的 `u_muldiv` 例化由 `.a(ex_a)/.b(ex_b)` 改为 `.a(ex_rs1)/.b(ex_rs2)`。
- **为什么**：此时 top-1 正是 `mem_wb/ctrl_reg[wb_src] → u_muldiv/prod_ss_reg/PCIN`，
  操作数经两级 mux 才进 DSP（第二个 LUT6 就是它）。等价性依据：`control_unit.sv:57-98`
  M 扩展走 `OPC_REG` R 型路径 ⇒ 恒有 `ex_a ≡ ex_rs1`、`ex_b ≡ ex_rs2`（逐位等价）。
- **结果**：@131.25 档 WNS **−0.437 → −0.077**，绝对吞吐 273.5 → **286.2（+4.6%）**，
  且 **DSP 输入族从 top-1 消失**。ticks 逐位不变。
- **最该学的一点**：同一个改动**换一个上下文会变号**（见 §5 的 C-12a 负交互），
  所以"上次否掉它"不能直接当结论 —— 必须回测。

### 候选 B · 删掉 C-10/C-14 寄存器块的"清 0 条件"（本轮最大单笔收益）
- **改动**：`core.sv:1140-1152`。原来
  `if (any_redir || id_ex_bubble) 清 FWD_REG; else if (!pipe_stall) 装 fwd_*_pre;`
  ⇒ **EX 重定向组合锥（7×CARRY4）同时进了 D 端 mux 和 CE**。改成 CE 只留 `!pipe_stall`。
- **为什么**：作者用新工具 `tools/path_families.py` 读了 top-50，发现
  **37/50 条路径的终点都是同一个结构**（`id_ex_jr_p_reg/CE` 24 条 + `id_ex_fwd_a_reg[*]_rep/D` 13 条）。
- **结果**：
  - 评分流 @128.125：+0.062 → **+0.090**；原 37/50 条那个族**从 top-50 消失**；
  - **ILA 流 @128.125：−0.434 → +0.000 PASS** ⇒ **交付档从 118.75 提到 128.125 MHz**；
  - ticks **逐位 453,942 不变**（纯时序）。
- **判据**：CSV 行 `cB-128`；上板证据 `results/ila_done.csv` 最后一行。
- **最该学的一点（等价性论证的"干净度"）**：作者先给了一个"顺手修 MRET 潜在 bug"的故事，
  **10 分钟后自己查代码撤回**（`core.sv:1045` 的 `trap_redir` 本就含 `mret_taken`，
  MRET 当拍就冲 ID/EX）。撤回后论证只剩**一条 don't-care 论证**（清 0 生效的四种来源里，
  T+1 进 EX 的槽位永远是气泡或被杀的 X0），**反而更稳**。
  ⇒ **"顺手修了个 bug"式的论证要格外警惕；先查代码事实，再谈机制。**

## 3. 方法论教训（可迁移到任何时序优化工作）

1. **瓶颈是"族"，不是"某条路径"。**
   治好 top-1 不等于整族消失。先看 **top-50 的族分布**：单一大族 ⇒ 值得做结构改动；
   分散 ⇒ 转物理/约束。工具：`python tools\path_families.py`。
2. **同一改动在不同上下文会变号。**
   C-12b' 孤立测 −0.37 ns，在 C-14+C-1 的上下文里 +0.45 ns（值约 6 MHz 达成频率）。
   ⇒ **孤立测量不能用于组合决策**；决策要用"在当前树上的实测值"。
3. **预登记判据把负结果变成干净的科学结论。**
   C-18a 事先写明"若 DSP 数不增而族仍在 PCIN ⇒ 判负回退"，实测 100% 命中 ⇒
   它是一条**结论**，不是一次失败。对比：事后解释容易变成自我辩护。
4. **"能撞上的测试"必须先建模 kill/flush 语义。**
   一条断言"mret 紧邻的消费者要读到前递值"——而那条指令**永远被冲掉**（这正是 MRET 精确性要求）
   ⇒ 它会是一条**永久假警报**，诱导后人去改**本来正确**的 RTL。**比没有测试更糟。**
5. **闸门必须进"判据"，不能只进"提示"。**
   我给 31 位上限加安全余量时第一版只改了提示文本，判据没变 ⇒ 4730 仍被放过。
   "闸门看着在、其实没拦"比没有闸门更危险。
6. **两个流程/配置对比前，必须先对齐所有已知变量。**
   我曾断言"ILA 流比评分流差 0.5 ns = 调试核开销"；对齐策略后实测残差只有 **0.090 ns**
   —— 我把"策略缺失"记成了"调试核开销"。（真正的 ILA 耦合确实存在，但只有周期的 0.7%。）
7. **不要用 shell 正则对 RTL 做文本手术。**
   我用 PowerShell `-Raw` + `-replace` 改时钟，把 `.CLK_HZ` 行与下一行**合并**，
   Vivado 报 `Synth 8-2715`，白跑两个点。改用 Python 并加三条护栏：

## 7. 2026-10-13 · 冲 150 MHz 的一轮（含一条"工具崩溃"的诊断）

起点：**128.125 MHz 已上板验证**（§0 的表），目标是 150 MHz ⇒ 需要再省 **1.14 ns**
（周期 7.805 → 6.667 ns）。

### 候选 A · 把"停顿锥"从 BTB 查表数据路径搬到 CE 端（三泳道同一次落盘）
- **改动**：`btb.sv`/`bht.sv` 新增 `p2_pc`（去掉 `fetch_hold` 的快地址）+ `p2_hold`（只当 BTB
  输出寄存器的 CE）+ `p2_pc_pht`（= 老的 `pc_next`，**只喂方向表**）；`core.sv` 加 2 条 wire + 3 个连接，
  **`pc_next` 与 `imem_addr` 一行不改**。
- **为什么**：C-1 用 `pc_next`（含 `fetch_hold`）当 BTB 查表地址，于是"指令译码 + load-use 冒险判定 +
  停顿/重定向优先级"整锥（3.72 ns，其中 **83% 是布线**）被拉进 BTB 的 D 端。ILA 流的绑定路径就是它。
- **结果（实测）**：**机制生效** —— `u_btb/q_vld_reg/D` **+0.000 → +0.046**、
  `q_cond_r_reg/D` +0.064 → **+0.167**，**该族离开 top-50** ✓；
  但评分流总 WNS **+0.090 → +0.013（−0.077 ns）**，因为 **C-11 的 `br_tgt_r_reg/CE` 族从 13 条 +0.090
  变成 32 条 +0.013** —— 瓶颈只是**转移**了。
- **最该学的一点（`rtl-pred` 用 trace 二分抓出来的）**：
  "用 `p2_hold` 冻结**整条**预测链"看起来与老实现等价，实测 **ticks 453,942 → 454,996、误判 +537**；
  二分证明**是冻结本身**（只冻结、地址不改 = 同样数字），逐拍 trace diff 定位到
  **首个分歧 cycle 8283（停顿中冻结 PC=0x80000e6c，`pred_taken` 1→0）**：
  > 停顿期 **GHR 仍被 EX 里刚解析的控制流推动**，老实现的 PHT 索引 = `冻结PC ^ 当前GHR`
  > ⇒ 同一 PC 的方向预测会被用漂移后的 GHR **刷新一次**。**这条刷新本身是现有 ticks 的组成部分。**
  ⇒ **"看起来多余的重复计算"可能是行为的一部分；先 trace 二分，再谈等价性。**
  最终方案因此是**不对称的**：BTB 输出冻结 + PHT 继续吃老地址（bht 一律不冻结）。
- 另外把"trace 没差所以等价"加强成"**可证（除一个窗口）**"：穷举四类停顿来源后，
  唯一残余窗口 = `load_use_mem ∧ EX 是控制流 ∧ (index,tag) 别名`（只影响预测、不影响正确性），
  并写明"**绝不门控更新口**（会永久少写表项）"。这条边界写在 `btb.sv` 文件头，可审计。

### 候选 C · 删掉 `br_tgt_r` 的 CE（**1 行**）
- **改动**：`core.sv:1085`，`if (br_redir_eff) br_tgt_r <= actual_target;` → `br_tgt_r <= actual_target;`
- **为什么**：候选 A 暴露出的新支配族是 `br_tgt_r_reg/CE`（32 条）。CE 端必须等完整条
  `pred_ok → redirect_raw → redirect → br_redir_eff`（4 跳 ≈ **1.23 ns**）；而 D 端在加法器之后就结束了。
- **等价性（干净的一行论证）**：`br_tgt_r` 的唯一消费点 `pc_flush_pc` 只在 `pc_flush = trap_redir || br_redir_r`
  时才装进 PC，而 `br_tgt_r` 被**读取**当且仅当 `br_redir_r=1`（trap/mret 各取自己的地址）；
  又 `br_redir_r(T+1) = br_redir_eff(T)` ⇒ T+1 消费到的值 = T 沿捕获的 `actual_target`
  = CE 版捕获的**同一个值** ⇒ 逐位等价（ticks 逐位 453,942 实测确认 ✓）。
- **结果**：该 32 条族**从 top-50 消失** ✓；ticks 逐位不变；四配置全绿。
- **最该学的一点**：**"等一个晚到的使能"往往可以被"无条件做 + 让消费端门控"替换** ——
  只要证明"消费端在被使能时才读"。这一行省下的是**整条使能锥的到达时间**（1.23 ns）。

### 附带的重大发现 · Vivado 在"几乎不可行的目标"上会确定性崩溃
- **现象**：150 MHz 档 `Abnormal program termination (EXCEPTION_ACCESS_VIOLATION)`，
  rc=3221225477，在 `Phase 11 Incr Placement Change`（≈300~340 s）；`hs_err_pid*.log` 是 **0 KB**（无调用栈）。
  同一 RTL 在 128.125 档正常跑完 ⇒ 与**约束紧度**相关；换 `phys_opt` 指令**也崩**。
- **诊断**：当时最紧的族 slack 只有 **+0.013 ns** ⇒ 放置器在"几乎不可行"的目标上反复迭代最容易踩。
  **候选 C 把该族缩短 ≈1.2 ns 之后，150 档从"不可行"变"可行"，崩溃随之消失**（617 s 正常跑完）。
- **最该学的一点**：**工具崩溃有时是"设计不可行"的症状，而不是工具坏了。**
  先看"当前有多紧"（family slack），再决定是绕工具还是改设计 —— 我们这次是**改设计把工具治好了**。

### 150 档的瓶颈解码（新的结构性结论）
```
Source : u_ex_mem/ctrl_reg[wb_src][1]_replica_3/C     ← 48/49 条同源
Dest   : u_muldiv/prod_uu_reg__2/PCIN[0]
  LUT4 0.105 + route 0.789  →  LUT5 0.105 + route 0.586  →  DSP48E1 内部 A→M→P 3.397ns
  前端逻辑只有 0.21ns, 但布线 1.375ns; DSP 内部链占 6.247ns 的 **54%**
```
⇒ **"操作数 → DSP → 积寄存器"已经塞不进一个 150 MHz 周期**（DSP 内部 3.4 ns + 前端布线 1.4 ns
+ FF/建立/时钟开销 ≈ 6.2 ns）。**这不是修前端能解决的，必须把这条链断开**
（把 muldiv 操作数先寄存一拍，即 C-12c 的思路；它在旧上下文里被实测为净负，
但当时绑定族是 BTB/CE 族 —— 现在绑定族**就是** DSP 级联，属于"同一改动随上下文变号"，
**必须在当前树上重测**）。

```
ila_ctrl = 0xC2 (locked/done/pass=1, fail/illegal=0) ; score_result bit31=1 有效
tick = 2,128,330,451  (预期 2,131,483,600, 偏差 0.148% << 0.5% 门限)
```

### 本段最值钱的四个教训
1. **"墙转移"是 150 档的常态**：C-12c 消掉 DSP 族 ⇒ trap/CE 锥接班；D′ 消掉 `alu_out/CE` ⇒

   真正的出路是**一次砍掉一族共享的根源**（E′ 砍 `trap_enter` 锥 ⇒ 同时治好三族）。
2. **论证不成立时必须收窄方案**：我把"去掉 `irq_take` 的 `!pipe_stall`"批给作者，他逐条论证后
   判定"在途 muldiv"与"AMO/跨字访存"**不安全** ⇒ 改成 `!hold_mem`（保留安全门、只放掉
   `load_use` 气泡那一段）——**既达到同样的锥缩短，又不改语义**。这是"预登记判据"之外的另一种自律。
3. **测试通过 ≠ 已覆盖**：`tb_soc_timer_irq` 加 `+irq_trace` 实测中断只接受 2 次且**两次 `stall=0`**

   最终用 **4600 迭代**（tick 2,131,483,600，占用 99.3%）。

1. **Vivado 工程流的综合选项真名是"查"出来的**：先猜 `STEPS.SYNTH_DESIGN.ARGS.MORE OPTIONS`
   两种拼写全被拒（`Common 17-170`）；最后用 `list_property` 把 `synth_1` 的属性全打出来，
   发现它们本来就是**一等属性**：`STEPS.SYNTH_DESIGN.ARGS.NO_LC` / `...ARGS.FANOUT_LIMIT`
   ⇒ 两条流终于能带同一批选项 ✓。**教训：属性名不要猜，`list_property` 打出来。**
2. **调试核变轻 ⇒ 交付档余量翻 15 倍**：`C_DATA_DEPTH 2048→1024` + `C_INPUT_PIPE_STAGES 2→4`
   ⇒ ILA 流在 138.75 档从 **+0.010 提到 +0.150**（判读只读最后一行，深度对证据无贡献，
   却要 ~6 块 RAMB36 的布线）。**顺带纠正**：IP 只接受深度 ≥ **1024**（写 512 报 `IP_Flow 19-3461`）。
3. **候选 F 的双面结论**（`ex_mem_fwd_data` 的组合 mux → EX/MEM 派生寄存器）：
   - **正确性**：等价性成立（ticks 逐位 463,366），且**硬件上行为逐位中性** —— 138.75 两次采集

   - **时序**：**墙只是换了终点** —— `fwd_data_reg/D` 自己成了新族（24 条 −0.255）✗。

   要看**该布线在数据流里的位置**：若它本来就在寄存器边界前，搬进去只是换个终点。

### 怎么破的：**验证手段本身是瓶颈的一部分**
整场 150 战役里最反直觉的一条：**带 ILA 的那份网表在 150 过不去（−0.293~−0.514），
而评分流只差 0.172**。也就是说 —— **不是核不够快，而是"用来观察它的调试核"在吃掉那 0.17 ns。**

```
--pblock-range CLOCKREGION_X0Y1:CLOCKREGION_X2Y3   (比原 X0Y1:X2Y2 高一行)
--contain-routing                                  (给 Pblock 加 CONTAIN_ROUTING)
--fanout-limit 128                                 (全局扇出指导)
--no-lc                                            (禁 LUT 合并)
=> WNS **+0.000 MET**（刚好压线）
```

`X2Y3+contain+flim128` = **+0.000 ✓** ／ `X2Y3` = −0.068 ／ `contain` 单独 = −0.164 ／
`flim160` = −0.192 ／ `flim96` = −0.324 ／ `X2Y4`、`X3Y3` = −0.068。
⇒ **Pblock"高度 +1 行"是这次的关键**（改变布局密度与走线长度），而**组合**才把它推过线。

### 教训
1. **"验证手段"要算进时序预算**：调试核/探针/日志通道都不是免费的；设计贴到极限时，
   **换一条更轻的观测通道**（UART）比继续优化 RTL 有效得多。
2. **WNS=+0.000 也是合格**（Vivado 判 MET 并写 bitstream），但这是"压线交付"——
   上板必须用**独立通道**交叉验证（这里用了 UART 的 CRC 自检 + tick 与 138.75 档逐位一致 ✓）。
3. **同一份网表在不同 Pblock 下差 0.1~0.3 ns**：Pblock 不是"限制"，是**布局密度的调参手段**。

## 13. 合法 150 MHz 达成 + "留余量"的完整否证（2026-10-17 晚）

### 13.1 重大发现：**交付档的越界 Pblock 其实从未生效**
用户要求"别让 150 压线、试改 RTL"，同时提出"MMCM 换 PLL 也许更好"。两条都试了，都判负；
但**在排查过程中发现了一个更重要的事实**：

```
越界 Pblock X0Y1:X2Y3 触发 CRITICAL [Vivado 12-4433] "Constraint ranges extend outside the device"
=> 意味着 resize_pblock **失败、整个 pblock 没被应用**
=> 交付档实际用的是「无 Pblock + contain-routing + AltSpreadLogic_high」
=> 显式改成 `--pblock-range off` 后：**WNS +0.007、MET、构建日志 0 个 Critical Warning**
```
⇒ **合法 150 MHz 成立** ✓（`--no-lc --fanout_limit 128 --pblock-range off --contain-routing
--place-directive AltSpreadLogic_high`），评分 bitstream `794b50e6…`、SPIx4 镜像 `ef3c970a…`，
已烧进 QSPI 并通过 **16 MB 读回逐字节校验** ✓。

**教训（写进纪律）：CRITICAL 约束警告不能"看着它过了"就放过 —— 它可能意味着那条约束根本没生效，
而你以为的"调参结果"其实是"没调参"的结果。**

### 13.2 "给 150 留余量"——8 组实验全部判负（诚实清单）

| 尝试 | WNS@150 | 判读 |
|---|---|---|
| 交付档（无 pblock + contain + AltSpread） | **+0.007** | 设计极限 |
| 换 **PLLE2**（VCO 1200/8，因 PLLE2 的 VCO 区间是 800~1600，原 1050 非法） | −0.421 | ✗ **clock uncertainty 与 MMCM 完全相同（0.043 ns）** ⇒ 换原语无效 |
| RTL：`id_ex` 控制网（fo=132）加 `max_fanout` | −0.276 | ✗ 第 5 个"墙转移"（新长 `id_ex/rs1|rs2_data_reg/CE` 族） |
| RTL：bht `align` 自证链在综合视图移除 | −0.006 | ✗ **机制完全成功**（原 top-1 整条消失）但墙转到 EX 数据通路 ⇒ 第 6 个"墙转移" |
| 合法 Pblock `X0Y0:X3Y2` / `X0Y0:X2Y2` / `X0Y1:X2Y2` @150 | −0.348 / −0.467 / −0.131 | ✗ |

### 13.4 **CoreMark 分数口径纠正：328 → 324.20**（2026-10-17 晚）

