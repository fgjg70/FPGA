# 4.2 CoreMark/MHz 攻坚计划

> 编制：2026-10-23　｜　基线：`sys_clk_core` @150 MHz，CM/MHz **2.1581**，fmax **150.2 MHz**（WNS +0.007）
> 目标：CM/MHz **≈4.2**（+94%），fmax **≥100 MHz**（硬下限 80 MHz）
>
> **本文的证据分级**（每条数字都标注来源，请按级引用）：
> - `[实测]` = 本次在 ModelSim 上真跑出来的（`verify --only tb_sw_coremark`）
> - `[归档]` = 引自 `results/` 与 `fpga/timing.rpt` 的既有记录
> - `[估算]` = 基于上述数据的推算，**未经验证**，不可对外宣称

---

## 0. 结论先行（三句话）

1. **单发射到不了 4.2，数学上封顶约 3.4** —— 唯一出路是双发射。这不是选择，是算术。
2. **已经实测到一个零成本的 +24.8%**：CoreMark 编译选项 `-Os` → `-O2`，CM/MHz **2.1581 → 2.6930**，
   370 万组 LSU 等价性与 CRC 全部通过 `[实测]`。这一步不碰 RTL 一行代码。
3. **4.2 的真实门槛是 IPC 1.24**，即双发射效率 **62%** —— 不是直觉上的 85%。
   这个门槛比想象的低，因为 `-O2` 已经把指令数砍掉了 19%。

## 1. 现状诊断：钱花在哪了

### 1.1 一次 CoreMark 迭代的账 `[实测]`

| 量 | `-Os`（当前） | `-O2` | 说明 |
|---|---:|---:|---|
| ticks（窗口周期） | 463,364 | **371,390** | MMIO_MARK → MMIO_RESULT |
| 取指条数（指令数） | 364,634 | **294,403** | **−19.3%** |
| CPI（窗口） | 1.271 | 1.261 | **几乎没变** |
| IPC | 0.787 | 0.793 | **几乎没变** |
| CM/MHz | 2.158 | **2.693** | **+24.8%** |
| `.text` 大小 | 9,676 B（59% imem） | 13,152 B（80% imem） | `-O3` 溢出 **2,404 B** |

**关键读法**：`-O2` 的收益 **100% 来自"指令变少了"，CPU 的执行效率一点没变**（CPI 1.271 → 1.261）。
这有两个含义：
- 好消息：现有微架构没有被编译器"喂饱"，之后每一项 IPC 改进都能整份吃到；
- 坏消息：**指望编译器继续送分是不行的**，`-O3` 连 16 KB imem 都装不下。

### 1.2 停顿构成 `[实测，-Os 基线]`

窗口内停顿 **84,217 拍 = 总周期的 18.2%**，构成：

| 来源 | 拍数 | 占比 | 折算 |
|---|---:|---:|---|
| **load-use** | **65,369** | **77.6%** | 36,791 次事件 × **1.77 拍/次** |
| 重定向（分支/JAL/JALR 误判） | ≈11,500 | 13.7% | 精度 91.95% |
| muldiv busy | ≈7,300 | 8.7% | 除法 84 条 × ~34 拍 |

> **load-use 一项就吃掉 77.6% 的停顿**。这是本核当前最大的、也是唯一值得动手术的单点。
> 它之所以是 1.77 拍而不是整数，是因为 C-2 决策把它设计成 **2 拍气泡**（`load_use_ex` + `load_use_mem`），
> 部分事件因相邻非 load 指令只触发其中一拍。

### 1.3 当前的物理余量 `[归档]`

| 项 | 值 | 含义 |
|---|---|---|
| fmax | 150.2 MHz @6.667 ns，WNS **+0.007** | **压线**，任何 RTL 改动都可能塌 |
| LUT / FF / BRAM / DSP | 3098 / 1447 / 9 / 8 | 100T 有 63,400 LUT / 135 BRAM / 240 DSP ⇒ **面积不是约束** |
| 关键路径 route 占比 | 65~76% | 布局布线主导，纯 RTL 重排收益≈0（PITFALLS R47） |

**这张表决定了后续所有工作的性质**：面积随便用，**频率是唯一硬约束**。

## 2. 目标拆解

```
目标 CM/MHz 4.2  ⇒  ticks = 1e6 / 4.2 = 238,095 拍/迭代
起点（-O2 后）    =  371,390 拍
需要再快          =  371,390 / 238,095 = 1.56×
```

若 `-O2` 的指令数 294,403 不变：

| 方案 | 需要 IPC | 需要 CPI | 评价 |
|---|---:|---:|---|
| 单发射 | **1.24** | 0.808 | **物理不可能**，单发射 IPC ≤ 1.0 |
| 双发射 | **1.24** | 0.808 | 发射效率需 **62%**（1.24 / 2.0） |

### 2.1 为什么单发射必然失败（把话说死，免得后面再试一遍）

单发射最好情况 = IPC 1.0 且 **零停顿**：

```
ticks_min = 指令数 = 294,403
CM/MHz_max = 1e6 / 294,403 = 3.40
```

即便再叠加 `-O3`（需先把 imem 扩到 24 KB）把指令再砍 10%：

```
ticks = 265,000  ⇒  CM/MHz = 3.77  <  4.2  ✗
```

**结论：4.2 一定需要每拍执行 >1 条指令。以下所有方案都必须围绕双发射设计。**

| 核 | 类型 | 流水级 | CoreMark/MHz | 依据 |
|---|---|---|---|---|
| **本核（现状）** | 单发射顺序 | 5 | 2.16（`-Os`）/ 2.69（`-O2`） | `[实测]` |
| RVCoreP-32IM | 单发射顺序 | 5 | 2.33（论文自述，口径存疑） | `[归档] rvcorep-vs-ours.md` |
| ARM Cortex-M4 | 单发射 | 3 | 3.42 | 公开数据 |
| **ARM Cortex-M7** | **双发射顺序** | **6** | **5.29** | 公开数据 |
| **biRISC-V** | **双发射顺序** | **6/7** | **4.1** | 开源 Apache-2.0 |
| WD SweRV EH1 | 双发射顺序 | 9 | ~4.9 | 开源 |
| SiFive E76 | 双发射顺序 | 8 | ~4.9 | 商用 |

### 3.1 最直接的参照：biRISC-V

这是**开源、可完整读源码**、且目标性能几乎就是我们要的数字的核：

- 32-bit RV32IMZicsr，**双发射顺序（in-order superscalar）**
- **6 或 7 级**流水（`EXTRA_DECODE_STAGE` 参数可选第 7 级）
- **64 位取指**（一拍取两条），32 位数据访问
- **2 × ALU**（含分支），**1 × LSU**，1 × 流水外除法器
- gshare/BTB/RAS 分支预测
- **CoreMark 4.1 CM/MHz**，Dhrystone 1.9 DMIPS/MHz
- 明确面向 Artix-7，目标「不占满 LUT、综合 >50 MHz」

**它的发射规则（照抄即可起手）**：

| 指令类型 | pipe0 | pipe1 |
|---|:--:|:--:|
| ALU | ✓ | ✓ |
| Load/Store | ✓ | ✗ |
| Branch | ✓ | ✓ |
| Multiply | ✓ | ✓ |
| Divide | ✓ | ✗ |
| CSR | ✓ | ✗ |

规则：第 1 条必须进 pipe0；第 2 条类型须支持 pipe1；两条之间无 RAW/WAW/资源冲突。

> **重要提醒**：biRISC-V 在 Artix-7 上的宣言只是「>50 MHz」。也就是说 **4.1 CM/MHz 并不以高频率为代价前提**。
> 我们要的「4.2 + 100 MHz」比它更苛刻 —— 这必须靠**流水级数**（6→7）换回来。

## 4. 四阶段路线

```
P0 编译选项  ──►  P1 吃掉停顿  ──►  P2 双发射  ──►  P3 频率回收
  +24.8%           +10% 左右         核心工程          找回落差
  已实测            1 周             3~4 周            1 周
  2.16→2.69         →3.0             →4.2              fmax→100+
```

### P0：编译选项（**已完成验证，0.5 天落地**）

| 项 | 内容 |
|---|---|
| 改动 | `tools/build_sw.py` 的 `cm_defs` 与 `opt`：`-Os` → `-O2`（`FLAGS_STR` 同步） |
| 实测收益 | CM/MHz **2.1581 → 2.6930（+24.8%）**；CRC-valid=1，`RESULT : PASS` |
| 代价 | `.text` 9,676 → 13,152 B，imem 占用 59% → **80%**（余量 20%，**已接近红线**） |
| 风险 | 低。但必须重跑全量 `verify`（12 项）+ 重烧上板验证 CRC |
| 附带收益 | 指令数 −19.3%，为双发射减少了绝对工作量 |

**同期验证（可选，需要先扩 imem）**：`-O3` 让 `.text` 溢出 2,404 B ⇒ 需要 imem ≥ **20 KB**。
建议把 imem 一次性扩到 **24 KB**（6 × RAMB36），给 `-O3` 和后续双发射留空间。**记为 P0b。**

> ⚠️ **踩坑预警**：`imem` 扩容本身会降 fmax（ref5 同 RTL 4 KB→16 KB 实测 **−18.68 MHz**，纯布线代价）。
> 所以 **P0b 必须与 P2 一起做**，不要单独为了 `-O3` 先扩 imem 再回头——那次频率损失要付两遍。

### P1：吃掉停顿（1 周，中风险）

目标：把 18.2% 的停顿压到 10% 以内，为双发射准备"干净的"基础 CPI。

| # | 动作 | 预期 | 依据 | 风险 |
|---|---|---|---|---|
| P1-1 | **打开 RAS**（`RAS_EN`） | ticks −0.36% | `[归档] p4-c1-2stage-gshare.md`：453,942 → 452,288，JALR 误判 3,650 → 2,796 | 需重测 fmax；旧"净亏"理由已被 C-1 动摇 |
| P1-2 | **提升方向预测精度 92% → 95%+** | 约 +2~3% | 当前误判 8,020 次、精度 91.95% | 中。可试：循环预测器 / 更长历史 / 双模态 TAGE-lite |
| P1-3 | **降低分支惩罚**：C-11 已把重定向寄存一拍，评估能否再省 | 每省 1 拍 ≈ +2% | 每次重定向实测占 1 拍（已最优） | 低 |
| P1-4 | **load-use 1.77 → 1.0 拍/次** | **+7~8%** | 65,369 拍 = 18.2% 中的 77.6% | **高，且与 C-2 直接冲突**（见下） |

**P1-4 是整个计划最需要判断的一点。** 两种做法：

- **(a) 恢复 load 前递**（回到 1 拍）：IPC 立刻赚回 7~8%，但会把 `dmem BRAM → 前递 → 分支 → PC → imem`
  这条实测 top-1、route 占 76% 的墙重新接上 ⇒ **fmax 大概率跌破 100**。**不建议在 5 级架构上做。**
- **(b) 留到 P2 解决**：在 6 级流水里，load 数据在 MEM 段末尾拿到时，消费者还在 EX 的前半段，
  前递窗口天然变宽。**这是正解** —— 用流水级数买回前递机会，而不是用频率买。

**⇒ P1-4 在 5 级架构上冻结，标记为「P2 的子任务 P2-5」。**

P1 结束时预期：**CM/MHz ≈ 3.0**（2.69 × 1.10），fmax 维持 150 附近（除 P1-1 需复测）。

### P2：双发射（3~4 周，高风险，核心工程）

这是唯一能把 3.0 推到 4.2 的动作。

#### 2.1 流水级规划（5 级 → **6 级**）

| 新流水级 | 职责 | 对应现结构 |
|---|---|---|
| **F1** | PC 生成 + BTB/PHT 查表 | 现 IF 段的 pc/btb |
| **F2** | **64 位取指**（BRAM 读），指令对齐/打包 | 现 imem 输出寄存器 |
| **D** | **双译码** + 发射判定 + 分支判定 + regfile 读 | 现 ID 段 |
| **E** | **2 × ALU**，地址计算，前递 | 现 EX 段 |
| **M** | LSU（含非对齐拆分、AMO） | 现 MEM 段 |
| **W** | 写回（2 写口） | 现 WB 段 |

- **分支判定移到 D 段末**（而非现在的 EX）⇒ 误判惩罚 **3 拍**（F1/F2/D 冲刷）。
  这一条很关键：6 级 + EX 判定 = 4 拍惩罚，在 92% 精度下要付 `8% × 4 = 0.32` 的 CPI，
  直接吃掉一半收益。**D 段判定 + 精度 95% ⇒ 0.15 CPI，可接受。**
- 若时序仍不够，按 biRISC-V 的做法把 D 拆成 D1/D2 ⇒ **7 级**，代价是分支惩罚变 4 拍。
  **7 级是最后的保频率手段，不要一上来就用。**

#### 2.2 发射规则（起手版，直接对齐 biRISC-V）

| 指令类型 | slot0 | slot1 |
|---|:--:|:--:|
| ALU / LUI / AUIPC | ✓ | ✓ |
| Branch / JAL | ✓ | ✓ |
| JALR | ✓ | ✗（目标需 rs1，时序紧） |
| Load / Store | ✓ | ✗（单 LSU） |
| Multiply | ✓ | ✓ |
| Divide | ✓ | ✗（多周期） |
| CSR / SYSTEM / AMO | ✓ | ✗ |

同时发射条件（全部满足）：① slot0 合法；② slot1 类型允许；③ 无 RAW/WAW；④ 不争用同一功能单元；
⑤ 两条都在同一 64 位取指包内且顺序正确。

#### 2.3 关键结构改动清单

| # | 模块 | 改动 | 面积估算 |
|---|---|---|---|
| P2-1 | `imem` | 16 KB → **24 KB**，输出 64 位 | +2 RAMB36 |
| P2-2 | `regfile` | 2R1W → **4R2W**，或复制成 2 份（写广播） | +150~250 LUT |
| P2-3 | **新增 `issue_unit`** | 依赖检查矩阵 + 类型配对 + 气泡注入 | +250~400 LUT |
| P2-4 | `alu` | ×2 例化 | +120 LUT |
| P2-5 | **load-use 处理** | 在 6 级下重设计：load 数据在 M 段出，M→E 前递 | 0（复用） |
| P2-6 | `hazard_unit` | 前递网络 ×2，跨 slot 依赖 | +250~350 LUT |
| P2-7 | `id_ex_reg` / `ex_mem_reg` | 束宽 ×2（双份控制束） | +800 FF |
| P2-8 | `btb` / `bht` | 预测粒度改为 **2 条/拍**（一次查 2 个 PC，或只预测 slot0） | +50 LUT |

**面积总增：约 +1,500~2,000 LUT / +900 FF ⇒ 4,600~5,100 LUT / 2,400 FF。**
100T 完全装得下（63,400 LUT）。**BRAM 约 12~13 块**（135 可用）。

#### 2.4 双发射对**指标**的影响（不要只看 CM/MHz）

| 指标 | 现状 | P2 后（估算） | 变化 |
|---|---|---|---|
| CM/MHz | 2.693（-O2） | **4.2** | +56% |
| fmax | 150.2 | **100~120** | −20~33% |
| **绝对吞吐** | **404**（2.693×150） | **420~504** | **+4~25%** |
| CoreMark/LUTs | 8.69e-4 | **8.0~9.1e-4** | −8% ~ +5% |

> **算清这一笔**：绝对吞吐在 100 MHz 时是 420，仅比现在的 404 高 4%。
> **双发射的真正价值必须靠 fmax ≥110 才能体现**。这是 P3 存在的理由，也是最大风险点。
>
> `CoreMark/LUTs` 的临界点：**LUT 必须 < 6,023** 才不比现在差（4.2 / 6,023 = 6.97e-4）。
> 这给 P2 的实现加了一条硬约束：**面积预算 6,000 LUT，超出就输一项指标。**

## 5. 里程碑与验收标准

| 里程碑 | 交付 | 验收（**必须全部满足才算过**） |
|---|---|---|
| **M0** | `-O2` 设为默认 + 全量回归 + 上板 | `verify` **PASS 12**；CRC 逐位匹配；CM/MHz ≥ **2.69**；fmax ≥ 145 |
| **M1** | RAS + 预测器调优 | 预测精度 ≥ **94%**；CM/MHz ≥ **2.95**；fmax 不降超 2% |
| **M2** | 6 级单发射（先不双发射） | 功能全过；**fmax ≥ 130**；CM/MHz 不降（验证流水加深本身不吃性能） |
| **M3** | 双发射（slot1 只允许 ALU） | 功能全过；**IPC ≥ 1.0**；CM/MHz ≥ **3.6** |
| **M4** | 双发射（放开 Branch/Mul） | **CM/MHz ≥ 4.1**；**fmax ≥ 100**；LUT ≤ **6,000** |
| **M5** | 上板闭环 | 采集清单 `rtl_sha256` 覆盖全部 `.sv`；CRC 匹配；CoreMark 规范分 ≥ **400** |

> **M2 是一个独立的、极有价值的探针**：它把"流水加深"与"双发射"两件事分开。
> 如果 M2 就把 fmax 做到了 150，那 M4 的 100 MHz 底线就非常安全；
> 如果 M2 只有 120，说明 6 级拆分本身不干净，**先修 M2 再谈双发射**（否则后面会误判是双发射的锅）。

## 6. 风险登记与回退

| 风险 | 概率 | 影响 | 应对 / 回退 |
|---|---|---|---|
| 双发射后 fmax < 80 | 中 | 绝对吞吐跌破 336 | 先升 7 级（D1/D2）；仍不行则回退到 M2 状态（单发射，CM 3.0） |
| LUT > 6,000 导致 CM/LUTs 恶化 | 中高 | 输一项指标 | 发射判定简化（slot1 仅 ALU）；regfile 用分布式 RAM |
| 分支惩罚吃掉收益 | 高 | CPI 回升 | D 段判定 + 预测精度 95%+；必要时加循环预测器 |
| load-use 在双发射下更严重 | 高 | IPC 上不去 | **P2-5 必须与 P2 同批做**，不要留到最后 |
| `-O2` 与赛题编译规则冲突 | 低 | P0 收益作废 | CoreMark 官方允许 legal options；`FLAGS_STR` 会如实打印在输出里 |
| imem 扩容拖累频率 | 高 | −10~18 MHz | 与 P2 合并做，只付一次 |

**总回退点**：任意阶段失败，都能退回到 **M0 状态（CM/MHz 2.69，fmax 150）**，
这已经是相对今天 **+24.8%** 的净收益，且零 RTL 风险。

## 7. 需要补充的调研（P2 开工前必做）

1. **精读 biRISC-V 源码**（`src/core/biriscv_issue.v` / `biriscv_frontend.v` / `biriscv_mem_ctrl.v`），
   重点是它的 **slot 选择逻辑**与 **load bypass 路径**——这两块正是我们最缺的。
2. **SweRV EH1 的双发射 9 级**如何分配流水级，它的"early ALU / late ALU"是什么做法
   （4 个 ALU，2 早 2 晚）——这可能比对称双 ALU 更容易保频率。
3. **CoreMark 的分支特征**：用现有 `trace_diff.py` 统计本核 CoreMark 的分支类型分布
   （循环回边 / if-else / 函数返回），决定循环预测器的形状。
4. **指令配对率实测**：写一个离线分析器，对 `-O2` 的 CoreMark 二进制统计
   "相邻两条指令满足发射规则"的比例 —— **这是双发射 IPC 的物理上限**，
   必须在动 RTL 之前测出来。若配对率 < 55%，双发射到不了 4.2，整个计划要改。

> **第 4 条是 go / no-go 判据。** 建议在 P1 期间用 Python 写这个统计（基于 `.elf` 反汇编 +
> 控制流，不需要跑 RTL），成本一天，但能决定几周的工作是否值得投入。
