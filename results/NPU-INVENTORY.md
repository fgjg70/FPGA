## 0. 先回答"当前 NPU 什么级别"

**一句话：板上那个是「高端 MCU + 硬件卷积协处理器」级别，仓库里最强的那个是「边缘 FPGA NPU 下沿」级别，两者差 78 倍，而且不在同一条路上。**

| | 板上实际在跑的 | 仓库里最强的 |
|---|---|---|
| 实体 | `vision_npu` **4-lane**（`build/dual_j11/rtl/vision_npu.v`） | `nn_conv_engine` **128 MAC**（`feat/ai-accel` 分支） |
| 峰值算力 | **0.400 GOPS** | **31.29 GOPS** |
| 实测有效算力 | **0.356 GOPS** | **4.68 GOPS**（YOLO）/ **14.76 GOPS**（瓶盖） |
| MAC 阵列 | 4 | **128** |
| 折 TOPS | **0.0004 TOPS** | **0.031 TOPS** |
| 在哪个分支 | `main`（交付主体） | `feat/ai-accel`（**未合入 main**） |
| 上板了吗 | 位流已烧（`hardware_tested: false`） | **从未上板** |

**换算成一句人话**：
- 板上那个是每秒 **4 亿次乘加**，大约等于一颗 Cortex-M7 @480 MHz 跑 CMSIS-NN 的水平；
  它跑的是 64×64、单通道、六层、**0.86 MMAC/帧** 的网络——这是 2016 年 MNIST-CNN（LeNet-5 约 0.4 MMAC）的量级。
- 仓库里最强的是每秒 **156 亿次乘加**（@122.22 MHz），约等于 Xilinx DPU B512 的下沿；
  它能跑 224×224、2.05M 参数、**2.27 GMAC/帧** 的 MobileNetV2-FPN 检测器——但只有 3.25 fps，而且从未上过板。

**行业标尺**（公开标称值，非本项目实测，仅作量级参照）：

| 档 | 峰值 int8 | 代表器件 | 本项目落点 |
|---|---|---|---|
| A. TinyML / MCU | 0.01 ~ 1 GOPS | Cortex-M7+CMSIS-NN（~0.3 GOPS 有效） | ★ **vision_npu 4-lane（0.4 GOPS）** |
| B. 边缘 FPGA NPU | 10 ~ 100 GOPS | Xilinx DPU B512~B1152 | ★ **nn_conv_engine（31.3 GOPS）** |
| C. 边缘 SoC NPU | 1 ~ 16 TOPS | Coral Edge TPU 4T / 旭日3 5T / Ascend310 16T | 未达（差 32~500×） |

> 最锋利的一条对比：**ARM Ethos-U55 也是 128 MAC**，它跑 1 GHz ⇒ 256 GOPS；
> 我们同样 128 MAC，跑 122.22 MHz ⇒ 31.3 GOPS。**差 8 倍全部来自 FPGA 的频率天花板，不是架构。**
> 这决定了 FPGA 上的 NPU 只能靠"堆 MAC"换算力，而堆 MAC 会撞 BRAM 和布线（见 §6.4）。

## 2. 逐一详述

### 2.1 ① `vision_npu` 单 lane（185 行，`main` 主 RTL）

| 项 | 值 | 出处 |
|---|---|---|
| 并行度 | **1 MAC/拍** | `reg signed [31:0] accumulator;` 单累加器 |
| 数据类型 | INT8 × INT8 → INT32，算术右移 requant + 饱和 + ReLU | `scaled = accumulator >>> shifts[i]` |
| 支持算子 | **只有 conv**（k=1/3，stride=1/2，隐含 pad）+ bias | 无 pool/add/copy 原语 |
| 网络结构 | **硬编码 6 层**，改模型必须改 RTL | `SETUP` 状态的 `case (layer_index)` |
| 权重存储 | `weights [0:65535]` = **64 K 字节**寄存器数组 + `biases[0:511]` | `$readmemh("model/weights.hex")` |
| 激活缓冲 | `activation_first[0:8191]` + `activation_second[0:8191]` = 16 KB | 同上 |
| 控制 | 7 态 FSM：IDLE/SETUP/BIAS_REQ/BIAS_LOAD/REQUEST/MAC/STORE | — |
| 模型 | 64×64×1 → 32×32×8 → 16×16×16 → 8×8×24 → 4×4×32 → 4×4×32 → 4×4×27 | `SETUP` 的六行参数 |
| MAC/帧 | **861,696** | 逐层 `oh·ow·oc·ic·k²` 求和 |
| 周期 | **1,769,238** | 推导 = 1,769,238（**差 0**）；`tb_npu.v` 有硬断言 `if (cycles != 1769238) $fatal` ⇒ **E1 实测** |
| 频率 | 50 MHz | `build_summary.json: npu_clock_hz` |
| 帧时间 | **35.38 ms**（28.3 fps 计算上限） | 1,769,238 / 50e6 |
| 峰值算力 | **0.100 GOPS** | 1 MAC × 50 MHz × 2 |
| 有效算力 | **0.049 GOPS** | 861,696 × 2 / 35.38 ms |
| **MAC 利用率** | **48.7%** | 每 tap 走 REQUEST+MAC **两拍**，只有一半时间在做乘法 |

**每输出通道的周期账**（这就是 48.7% 的来源，可复算）：
```
BIAS_REQUEST 1 拍 + BIAS_LOAD 1 拍 + N_tap×(REQUEST 1 + MAC 1) + STORE 1 拍
= 2·N_tap + 3
⇒ 每一层 Σ = 输出通道数 × (2·N_tap + 3)
```
逐层代入得 172,032 / 602,112 / 446,976 / 222,720 / 296,448 / 28,944，加 6 次 SETUP = **1,769,238**。

> **这就是"1 lane 版本的真实水平"**：0.05 GOPS 有效。它连"MCU 级"都算不上，属于"教科书级示范"。

### 2.2 ② `vision_npu` 4-lane（199 行，**板上实际**）

与 ① 的差异（逐条 diff 得出）：

| 改动 | ① 单 lane | ② 4-lane | 带来的效果 |
|---|---|---|---|
| OC 并行 | 1 个累加器 | `generate for (lane<4)`，**4 个独立 `accumulator`**，各带一份 `weights[0:16383]` | **4×** 吞吐 |
| 权重分 bank | 单数组 64 KB | 4 × 16 KB = **64 KB**，由 `output_channel[5:2]` 选 bank | 同上（每个 lane 管一组 OC） |
| tap 流水 | `REQUEST → MAC → REQUEST`（2 拍/tap） | `read_enable = REQUEST \|\| (MAC && !mac_last)`，读算重叠 ⇒ **1 拍/tap** | **1.83×** 吞吐 |
| 模型选择 | `model_select` 1 bit | **2 bit**（`< 2` 有效）+ `input_channels = active_model ? 1 : 3` | 支持 RGB 三通道与单通道两组权重 |
| 输入地址 | 12 bit（4 K） | **14 bit**（16 K）+ `< 12288` 保护 | 装得下 64×64×3 = 12,288 B |
| 结果索引 | `results[output_index[8:0]]` | 同 + `+ store_lane` | 4 lane 分别写 |
| 行数 | 185 | 199 | — |

**性能（E1 实测，非推导）**：

| 项 | 值 | 出处 |
|---|---|---|
| 周期 | **242,310** | `build/dual_j11/xsim_26008.backup.log:23`：`PASS soc_hand ... cycles=242310` |
| 推导 | 242,310 | `tools/npu_inventory.py`（**差 0**） |
| 帧时间 | **4.846 ms**（206 fps 计算上限） | 242,310 / 50 MHz |
| 峰值算力 | **0.400 GOPS** | 4 MAC × 50 MHz × 2 |
| 有效算力 | **0.356 GOPS** | 861,696 × 2 / 4.846 ms |
| **MAC 利用率** | **88.9%** | 4 通道组 × (2 + N_tap + 1 + STORE) |
| 相对 ① 加速 | **7.30×** | 1,769,238 / 242,310 |

> **7.30× 的拆解值得记住**：`4×（OC 并行） × 1.83×（tap 流水 ≈2 拍→1 拍）`。
> 两个优化**乘起来**，不是加起来。只做 4 lane 而不做流水，只有 4×；
> 单看"lane 翻 4 倍"会低估，单看"每 tap 少一拍"会低估，必须一起算。

**4-lane 的周期账**（可复算，末组不足 4 通道时 STORE 少几拍）：
```
每个 4-通道组 = BIAS_REQUEST 1 + BIAS_LOAD 1 + (N_tap + 1) + STORE×lanes
逐层：32,768 / 80,896 / 57,984 / 28,544 / 37,760 / 4,352，加 6 次 SETUP = 242,310
```

**资源（Pango 报告，整机口径，NPU 未单独拆分）**：

| 项 | 值 | 说明 |
|---|---|---|
| 器件 | PG2L100H FBG676 **-6** | |
| LUT | 9,980 / 66,600（15%） | 整机 = **双发射 CPU + 视频链路 + LCD + NPU** |
| FF | 6,573 / 133,200（4.9%） | 同上 |
| DRM（BRAM） | 99 / 155（**64%**） | 主因是 64K×16 帧缓冲；NPU 的 64 KB 权重另占 |
| APM（乘法器） | 13 / 240（5.4%） | **4 个 8×8 只用掉 2 个 APM**（`system/accelerator/N52`、`N84`），另 2 个落 LUT |
| 功耗 | **≈1.02 W**（整机） | `multiseed_summary.csv` / `report_power/` |
| 时序 | 全约束满足；CPU 域 WNS **+0.493**（周期 10.526 ns ⇒ fmax 99.7） | `place_route/*_timing_summary_after_hold_fix.txt` |

> **4 个 8×8 乘法只映射 2 个 APM** —— 这是 INT8 卷积在 FPGA 上的一个反直觉事实：
> 8×8 乘法器太小，用 DSP 反而亏（DSP 有自己的 I/O 和布线资源），综合器会主动落 LUT。
> 这也解释了为什么"堆 MAC"在这个规模上不吃 DSP（见 §6.4）。

### 2.3 ③④ `nn_conv_engine`（1,574 行 + 3,555 行配套，`feat/ai-accel`）

这是仓库里唯一"可编程"的 NPU。与 ② 的本质区别：② 是**固定 6 层的 FSM**，④ 是**微码 ROM 驱动的通用卷积引擎**。

| 项 | 值 | 出处 |
|---|---|---|
| 并行度 | **128 MAC/拍** = `OC_LANES=16` × `PX_LANES=8` | `nn_conv_engine.sv:47-48` |
| 阵列形态 | `acc[px][oc]` 8×16 二维累加器阵列；激活**广播** × 16 组权重 | `a_pipe[px][oc] <= win_sel[px][sel_byte_base +: 8]`（dense 路径下 16 个 oc 取同一字节） |
| **dense 与 dw 的差异** | dense conv 吃满 16 lane；**dw/pool/copy/add 只激活 lane 0..7** | `(oc < 8) ? win_sel[px][oc*8 +: 8] : 8'sd0` |
| 数据类型 | INT8×INT8→INT32，requant（32×16 乘 + 右移 + zp + 饱和）+ leaky/ReLU | 5 级 requant 流水 |
| 算子 | conv / dwconv / maxpool / copy / upsample / add（含 ADD_R per-tensor 源 requant） | `nn_pkg` 的 4 个 `NN_OP_*` + 7 个 `NN_F_*` |
| 权重存储 | **320 KB BRAM**（80×BRAM36）+ **Q 48 KB LUTRAM** | `NN_W_BYTES=320K` |
| 激活存储 | A 96 KB + B 32 KB = 128 KB | `NN_A_BYTES` / `NN_B_BYTES` |
| 控制 | **微码 ROM 128 项 × 256 bit**；双模：`MODE_CPU`（CPU 逐 op）/ `MODE_AUTO`（`nn_seq` 自主跑完） | `nn_rom_t` |
| 双模等价性 | **两种模式 NPU 周期完全相等**（1,167,368 @v0.7 / 1,191,020 @wpipe） | `[yolo] auto_npu_cycles` = `npu_cycles` |
| 频率 | 交付 **100 MHz**（WNS +0.136）；最高已验证 **122.22 MHz**（+0.058）；125 MHz 两次构建确定性 −0.077 | `impl/ai{100,115,120,122}/` |

|---|---|---:|---:|---:|---:|---:|---:|---:|
| YOLO-Fastest v1.1（A5e） | 128×128×3 | 112 | 20.07 M | 1,191,020 | 11.91 ms | 9.74 ms | 4.12 GOPS | **13.2%** |
| YOLO-Fastest v1.1（**A7a**） | 128×128×3 | 112 | 20.07 M | **1,049,089** | 10.49 ms | **8.58 ms** | **4.68 GOPS** | **14.9%** |

### 2.4 ⑤⑥⑦ `gemm_accel`（249 / 249 / 193 行，三副本，**已判失败**）

这一族**不是"第三个小 NPU"，是"一次失败的尝试"**。必须讲清楚，否则会误以为我们有三个可用加速器。

| 项 | 值 |
|---|---|
| 算力 | **1 MAC/拍**，纯 LUT 实现（`use_dsp` 明确禁用，注释写着"int8×int8 乘法器很小"） |
| 峰值 | 1 × 150 MHz × 2 = **0.300 GOPS** |
| 实测 | 16×16×16 GEMM = 4,096 MAC / **4,608 拍** ⇒ 0.889 MAC/拍（利用率 88.9%），有效 0.267 GOPS |
| 加速比 | 42.59×（纯计算 vs 软件 196,264 拍）/ 5.38×（端到端含搬运） |
| 规模 | `MAXD=32`，窗口 2 KB（A 64 字 + B 64 字 + C 256 字） |

**为什么判失败**（`results/p5-ai-accelerator.md` §0，全是实测）：

| 指标 | 无加速单元 | 含加速单元 | 影响 |
|---|---|---|---|
| LUT | 4,019 | **9,984** | **+148%** |
| FF | 1,387 | **14,097** | **+916%** |
| fmax | 61.6 MHz | **53.6 MHz** | **−13%** |
| CoreMark/LUTs | 5.875e-4 | 2.365e-4 | **−60%** |
| 绝对吞吐 | 145.4 | 126.5 | **−13%** |

**两个真因**：
1. **A/B/C 三个缓冲落成触发器阵列**（约 1.3 万 FF）而不是 BRAM —— `c_buf[256]` 这种"寄存器数组 + 组合多路读"综合器不会推断成 BRAM。
2. **功能本身有 bug**：C 读回只有前 ~16 个字正确（`C[0]=104` ✅ / `C[1]=224` ✅ / `C[255]=0` ❌），诊断为 `aoff = addr[9:2]` 只有 8 位，装不下 C 的高半部分（`0x5FC>>2 = 383` 被截成 127）。两版修法都失败（X 传播 / timeout）。

**当前状态**：`GEMM_EN` 宏门控，`build.tcl` 与 `build_ila.tcl` 都**不定义**该宏 ⇒ **评分版与 ILA 版均不含该单元**，交付实测已完全恢复（LUT 4,019 / FF 1,387 / fmax 61.6 / ticks 423,527）。

> **结论：⑤⑥⑦ 应从"NPU 资产"清单里划掉。** 它们保留在仓库里只为记录踩过的坑。
> 唯一可继承的经验：**缓冲要写成 `always @(posedge clk) rdata <= mem[a]` 才会推断 BRAM**，
> 这条在 ④ 里被彻底贯彻（320 KB W 全 BRAM，0 意外 FF）。

## 3. 横向对比总表

### 3.1 算力与效率

| 实体 | MAC/拍 | 频率 | 峰值 GOPS | 实测有效 GOPS | **利用率** | 模型 MAC/帧 | 帧时间 |
|---|---:|---:|---:|---:|---:|---:|---:|
| ① vision 1 lane | 1 | 50 | 0.100 | 0.049 | **48.7%** | 861,696 | 35.38 ms |
| ② vision 4 lane | 4 | 50 | **0.400** | **0.356** | **88.9%** | 861,696 | **4.846 ms** |
| ④ conv YOLO A7a | 128 | 122.22 | 31.29 | 4.68 | 14.9% | 20.07 M | 8.58 ms |
| ④ conv slim | 128 | 122.22 | 31.29 | 5.86 | 18.7% | 15.65 M | 5.34 ms |
| ④ conv 瓶盖 | 128 | 122.22 | **31.29** | **14.76** | **47.2%** | 2,271.97 M | 307.9 ms |
| ⑤ gemm_accel | 1 | 150 | 0.300 | 0.267 | 88.9% | 4,096 | 0.031 ms |

**读法**：`利用率` 这一列比 `峰值` 更有信息量。
- ①②⑤ 的利用率高（48.7%~88.9%），因为**任务形状固定**（固定网络 / 固定 GEMM），硬件是量身定做的；
- ④ 的利用率低（14.9%），因为**要兼容多种算子**，depthwise 路径只用一半 lane、requant 还有 5 级流水开销；
- ④ 跑大模型时利用率回升到 47.2%，因为 dense conv 占比高 —— **同一个引擎，利用率是模型的函数**。

## 4. 三个家族的架构取舍（为什么会长成这样）

| 取舍 | ② vision_npu | ④ nn_conv_engine | ⑤ gemm_accel |
|---|---|---|---|
| **为什么这个并行度** | 六层小模型 + 50 MHz 固定时钟 ⇒ 4 lane 刚好 4.8 ms/帧，够 30 fps；再多 lane 会撞 50 MHz 时序 | 要跑 2 GMAC 级模型 ⇒ 必须 128 MAC；16 OC × 8 px 是"权重读 128 bit 刚好 16 字节"的自然对齐 | 先做对接口与时序，1 MAC 是保守起点（注释自承"扩展路径"） |
| **模型可变吗** | ❌ 硬编码 6 层，换模型要改 RTL 重新综合 | ✅ 微码 ROM + 描述符，换模型只换 ROM/权重 | ✅ M/K/N 软件可配（但只支持 GEMM） |
| **存储策略** | 权重放**寄存器数组**（64 KB），靠 LUTRAM/DFF，不占 DRM | 权重放 **BRAM ROM**（320 KB）+ Q 放 LUTRAM，激活 ping-pong | 片上 2 KB 缓冲，CPU 用 MMIO 搬 |
| **控制复杂度** | 7 态 FSM，无微码 ⇒ **极简、可读、好验证** | 28 态 FSM + 微码 ROM + band/tile 循环 ⇒ **复杂但可编程** | 极简（一次触发算完） |
| **失败边界** | 换模型即废；无 pool/add 原语 ⇒ 只能表达"纯卷积堆叠" | 单张量激活 > 96 KB 就要 DDR3 流式；IC/OC > 256 触发限制 | 只支持 GEMM，且缓冲落错 |

> **一个容易被忽略的事实**：② 的"6 层硬编码"不是偷懒，是**在 50 MHz 固定时钟下把延迟做到确定性**的必然选择。
> 文档里那句"要确定性延迟"是真话——固定 FSM 每帧 242,310 拍，一拍不多一拍不少；
> ④ 的微码虽然灵活，但每帧周期随模型变化，且 band/tile 循环引入额外不确定性。

## 5. 行业定位：把 78 倍差距量化

### 5.1 峰值算力的差距

| 对照对象 | 峰值 int8 | 本项目 ② | 本项目 ④ | 倍数（④/对方） |
|---|---:|---:|---:|---:|
| Cortex-M7 @480 MHz + CMSIS-NN | ~0.3 GOPS（有效） | 0.356 | — | — |
| **Kendryte K210 KPU** | **230 GOPS** | — | 31.29 | **0.14×** |
| ARM Ethos-U55（128 MAC @1 GHz） | 256 GOPS | — | 31.29 | **0.12×** |
| Xilinx DPU B512（Zynq7020） | ~460 GOPS | — | 31.29 | 0.07× |
| Coral Edge TPU | 4,000 GOPS | — | 31.29 | 0.008× |
| Ascend 310 | 16,000 GOPS | — | 31.29 | 0.002× |

（竞品为公开标称 int8 峰值，非本仓库实测；K210/Ethos-U55 均为"int8 MAC×2×频率"同口径换算。）

**最该记住的一条**：
> **同样是 128 MAC，Ethos-U55 跑 1 GHz = 256 GOPS，我们跑 122.22 MHz = 31.3 GOPS。**
> 8.2 倍的差距**全部来自时钟**。FPGA 上想把算力提到 TOPS 级，唯一的路是堆 MAC（比如 PX16 把 128→256），
> 而堆 MAC 立刻撞上 BRAM（132/135，97.8%）与布线（关键路径已是纯 route 8.88 ns）。

### 5.2 模型规模的位置

| 模型 | MAC/帧 | 行业同类 | 位置 |
|---|---:|---|---|
| ② vision 6 层 | 0.86 M | LeNet-5（0.4 M）/ MobileNetV1-224（569 M） | **比 LeNet-5 大一倍，比 MobileNet 小 660 倍** |
| ④ YOLO-Fastest 128 | 20.1 M | YOLOv5s-640（7.2 G）/ YOLOv3-416（65.9 G） | 手机端轻量检测器的 **1/360** |
| ④ slim 瓶盖 96 | 15.7 M | MobileNetV1-96（~100 M） | 约 1/6 |
| ④ 瓶盖 224 | **2,271.97 M** | MobileNetV2-224（300 M）/ ResNet-50（4.1 G） | 是 MobileNetV2 的 **7.6 倍**，ResNet-50 的 **55%** |

> 所以"NPU 什么级别"要分两问：
> **"能跑多大的模型"** —— ④ 能跑 2.27 GMAC 的 224×224 检测器，这是**真正的中等规模边缘模型**，不是玩具；
> **"跑多快"** —— 3.25 fps @122.22 MHz。够做"静态品检"（一个瓶盖停住看一眼），不够做"流水线实时"（30 fps）。

### 5.3 一句话定位

| | 定位 |
|---|---|
| **② vision_npu 4-lane** | **"RISC-V SoC 里的一颗 TinyML 协处理器"**。算力不值一提（0.4 GOPS），价值在**集成度**：CPU + NPU + 摄像头 DVP + LCD + 跨时钟桥全在一片 PG2L100H 上，1.02 W。这是一个**完整的边缘视觉 SoC 演示平台**，不是一颗强 NPU。 |
| **④ nn_conv_engine** | **"一颗 2018 年水平的边缘 FPGA NPU"**。31.3 GOPS 峰值 / 4.7~14.8 GOPS 有效，能跑 224×224 的 MobileNetV2-FPN。架构（微码 + 描述符 + 双模 + 权重流式）是对的，落后的是**频率**（FPGA 天花板）和**未上板**。 |
| **⑤ gemm_accel** | **"一次有价值的失败"**。证明了"1 MAC + 寄存器阵列缓冲"在 FPGA 上是纯负收益（+916% FF / −13% fmax）。 |

## 6. 五个结构性结论

### 6.1 板上的与仓库里最强的，差 78 倍，且不可互换

```
板上（② 4-lane）     0.400 GOPS 峰值 / 0.356 有效   ← 能演示、能上板、模型固定
仓库最强（④ A7a）    31.29 GOPS 峰值 / 14.76 有效   ← 不能演示（未上板）、模型可换
                     ─────────────────────────
                     78.2× 峰值差 / 41.5× 有效差
```

**这不是"一个强一个弱"，是两条不同的技术路线**：
- ② 走"专用 FSM + 寄存器权重"，好处是简单、确定、塞得进 15% 的 LUT；
- ④ 走"通用引擎 + BRAM 权重 + 微码"，好处是可编程，代价是吃掉 58% LUT + 98% BRAM。

**能否迁移？** ④ 依赖 320 KB BRAM，而 PG2L100H 有 155×36Kb = 697.5 KB（比 Artix 多 15%），
BRAM 装得下；但 ④ 是 SystemVerilog + 大量 `struct`/`interface` 风格，Pango PDS 对 SV 支持有限（② 全线是 Verilog-2005），
**移植需要重写而非搬家**。这条已在 `results/bottlecap/reports/CPU-NPU-DECOUPLE.md` 里作为 S2/S3 议题。

### 6.2 利用率是模型的函数，不是常数 —— 所以"算力"必须带口径

| 模型 | depthwise 情况 | 实测利用率 |
|---|---|---:|
| YOLO-Fastest v1.1 | dwconv 占 38.6% 周期，且只用 8 lane | 14.9% |
| SlimMobileNet | 39 conv / 18 dwconv | 18.7% |
| EnhancedMobileNetV2-FPN | head tower 是 51.5% MAC 的 dense 3×3 | **47.2%** |

**根因**（RTL 层面）：`nn_conv_engine` 的 dw/pool/copy/add 路径写死了 `(oc < 8)`，
即**只有 8 个 lane 工作**，dense 路径才有 16 个。所以：
- 说"128 MAC/拍"只在 dense conv 上成立；
- 说"31.29 GOPS"是**理论上限**，实际拿到 4.7~14.8；
- 对外写成绩时，**必须写成"XX 模型 @ XX fps，对应有效 XX GOPS，峰值利用率 XX%"**，单写 "31 GOPS" 属于虚标。

### 6.3 精度瓶颈不在 NPU，在模型与数据

同一引擎、同一 int8 量化流程：
- slim 瓶盖 **99.92%** 框匹配（F1 0.9976）
- YOLO-Fastest **81.8%**
- vision 手势 **35.14%**

⇒ 换上 slim 之后，④ 立刻从"勉强"变成"可交付"。**这比任何 RTL 优化都值钱**。
反过来说，② 就算把 lane 从 4 提到 16（算力 4×），手势识别率还是 35.14% —— **加算力救不了模型**。

### 6.4 BRAM 与布线是这条路线的两道硬墙

| 墙 | 现状 | 后果 |
|---|---|---|
| **BRAM** | ④ 整机 **132 / 135 = 97.8%**；引擎 OOC 124/135 | 再想放大权重（比如换 320×320 输入）必须走 DDR3 流式；瓶盖 2M 模型已走这条路（`vision_ddr3_*` 433 行，但 `MEMORY_ENABLE=0`、顶层未例化、FDC 0 条 DDR 引脚） |
| **布线** | ④ 关键路径 `u_nn/u_eng/wa_r[*] → u_nn/u_mem/w_cur_*`：**route 8.881 ns，logic 0 级** | 纯物理距离。提频只能靠 pblock/floorplan 把 engine 与 BRAM 放同区，不是再拆流水 |

> 这两条墙解释了为什么"PX16 把 128 MAC 提到 256"的收益有限：
> `PX16-STUDY.md` 算出 21.59 M 拍（5.66 fps）vs 当前 37.63 M（3.25 fps），**1.74×**，
> 但 PX16 会让 BRAM 与布线压力同步上升 —— 而 BRAM 只剩 3 块。

### 6.5 证据级别的分裂，是提交前最大的风险

| 想说的话 | 手上有的证据 | 差什么 |
|---|---|---|
| "板上 NPU 242,310 拍 = 4.85 ms" | E1 仿真（`soc_hand PASS`）+ 位流已烧 | **`hardware_tested: false`** ⇒ 缺一份带 `rtl_sha256` 的上板采集清单 |
| "NPU 加速 401.9×" | E1 精确探针（K=112，473,254,313 拍） | 分母是 CPU 逐点实现；**从未上板** |
| "31.29 GOPS" | E2 综合 WNS +0.058 @122.22 | 峰值推算，非实测吞吐 |
| "瓶盖检测 99.92%" | E1 端到端位精确 | 从未上板，且原模型 106-op 全链路 E2E 未完（剩 Path A） |

> 按 `results/RTL-DISCIPLINE.md` 的红线二：**E2/E1 的数字不能说成"实测"**。
> 当前能安全对外宣称的只有：② 的"板上演示 + 仿真周期"，④ 的"仿真位精确 + 综合可用"。
