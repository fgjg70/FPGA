# P3 存储侧规格：C320 DDR3 激活 + BRAM Tile Cache（T-mem-R4）

> 交付人：T-mem。日期：2026-11-01。分支：`feat/ai-accel`。任务：task-10。
> 背景：NPU 128 MAC 版 112-op 双模 E2E 已 PASS；125MHz 全实现在跑。C320（320×320）要把
> **中间激活张量放 DDR3**（MODEL-FREEZE D2：DDR3 双用 = 视频帧缓冲 + 320 激活），BRAM 只做 tile 缓存。
> **本文只是规格/分析，不改任何 RTL**（nn_mem / nn_conv_engine / nn_subsys 一律不动）。

## 1. 数据来源与口径

- 模型：`sim/prog/yolo320/plan.json`（format `yolo-fastest-v1.1-int8-plan-v0.6`，**112 op**：
  conv 56 / dwconv 28 / add 18 / copy 6 / pool 3 / upsample 1），输入 320×320×3。
- 张量字节（NHWC **8 通道块紧凑布局**，`pad8(c)=ceil(c/8)*8`）：
  - 输入：`ih*iw*pad8(ic)`；**conv0 PACKED3** 例外 = `ih*iw*3`（3B/像素 packed）；
  - 输出：`oh*ow*pad8(oc)`；**copy 例外 = `oh*ow*pad8(ic)`**（copy 只搬 ic 个通道，dst 的 `oc` 字段是拼接后总通道数）。
- flags 编码注意：`plan.json` 用模型侧 flag（PACKED3=4、ADD_R=8、DEPTHWISE=1、LEAKY=2），
  与硬件 `nn_pkg` 的 bit5/bit6 不同；集成侧由 T-model/Lead 的转换脚本处理（本报告按语义统计）。
- 统计脚本（可复现）：`%TEMP%\p3_stats3.py` / `p3_stats4.py` / `p3_b.py`（临时脚本，
  核心命令为 python 读 plan.json 求 Σ）。
- **权威交叉源**：T-model task-11 已产出 `sim/prog/yolo320/arena_map.json`（95,313 B，
  format `c320-ddr3-arena-map-v1`）与 `results/ai-accel/P3-320-ARENA.md`：
  - 唯一张量 **7,077,600 B（91 个张量）**、峰值并发/最小 arena **819,200 B**、16B 对齐；
  - 帧流量 read **7,978,400** + write **7,268,000** = **15,246,400 B/帧**（与本报告独立计算一致）；
  - arena 基址 **`0x0100_0000`（16MB 偏移）**，预留 2MB 窗口，实际用 0.819MB（2.56× 余量）；
  - **ROM 宽度决定：21-bit byte（Lead 拍板）**；conv0 模型侧按 8 行带流式读，20 bands、halo 18,240B。
  本报告 §2 的"逐 op 表"用于带宽/tile 尺寸推演；**地址值一律以 arena_map.json 为准**。

## 2. C320 激活数据量统计

### 2.1 总量

> 权威值取自 T-model `sim/prog/yolo320/arena_map.json.summary`（`plan.json` sha256 `71745e5f…` 冻结）；
> 本报告独立求和与之**逐字节一致**（流量），唯一张量按 91 个张量（add 原地写、copy 写进同一 concat 张量 → 去重后 91 而非 113）。

| 指标 | 数值 |
|---|---|
| 模型输入（320×320×3 packed3） | **307,200 B** |
| **唯一张量总和（91 个张量，16B 对齐）** | **7,077,600 B = 7.08 MB(1e6) = 6.75 MiB** |
| **每层 in+out 流量（理想，每个张量读 1 次写 1 次）** | **15,246,400 B = 15.25 MB/帧**（读 7,978,400 + 写 7,268,000） |
| 最大单张量 | **614,400 B（600KB）**：op8 conv 160×160×24 |
| **生命周期峰值并发 = 可复用后最小 arena** | **819,200 B = 0.819 MB**（interval-graph 0 碎片；16B 对齐） |
| plan 虚拟 arena `alloc` | peak_A=768,000 B / peak_B=204,800 B / peak_total=819,200 B（与最小 arena 相同） |
| 按 kind 的流量占比 | conv 8.04 MB / dwconv 5.50 MB / add 1.49 MB / copy 0.13 MB / pool 0.03 / upsample 0.05 |

> 峰值并发 819,200 B 由"最大张量 600KB + 同窗口内相邻张量"构成；**arena 布局/逐张量地址以
> `arena_map.json` 为准**（base `0x0100_0000`，预留 2MB，实际 0.819MB）。C320 是"链式为主 +
> 少量 skip"的图：绝大多数张量只有 1 个消费者，skip 让 op3 的 B[0] 活到 op7（4 op）。

### 2.2 两种调度模型的 DDR 流量（关键结论）

| 模型 | 读 | 写 | 合计 | 相对理想 |
|---|---|---|---|---|
| **A. band-outer + tile cache（推荐）**：输入每个 band 只从 DDR 读一次，OC 块在 band 内循环 | 7.978 MB | 7.268 MB | **15.246 MB/帧** | 1.00× |
| 同上 + 行 halo 重读（B=8 行带，模型侧 arena_map 口径） | 8.62 MB | 7.27 MB | 15.88 MB/帧 | 1.04× |
| 同上 + 行 halo 重读（B=4 行带） | 9.27 MB | 7.27 MB | 16.54 MB/帧 | 1.08× |
| 同上 + 行 halo 重读（B=2 行带） | 10.57 MB | 7.27 MB | 17.84 MB/帧 | 1.17× |
| **B. 当前引擎调度（OC-block 外层，无 tile 缓存）**：输入按 OC 块重读 `ceil(oc8/16)`（dense）/`oc8/8`（dw/pool）次 | **33.66 MB** | 7.27 MB | **40.93 MB/帧** | **2.68×（读放大 4.22×）** |

> **结论：P3 必须做 band-outer tile 调度**（引擎外层循环改成"输出行带 → OC 块"）。
> 否则 30fps 需要 1.23 GB/s，逼近甚至超过 DDR3 有效带宽，且延迟/突发效率更差。

## 3. DDR3 带宽预算

### 3.1 需求侧（band-outer + halo）

| 行带 B | MB/帧 | 15fps | 20fps | **30fps** |
|---|---|---|---|---|
| 1（不推荐） | 20.43 | 0.31 GB/s | 0.41 GB/s | 0.61 GB/s |
| 2 | 17.84 | 0.27 | 0.36 | **0.54** |
| 4 | 16.54 | 0.25 | 0.33 | **0.50** |
| **自适应（B=4/2/1 混合，推荐）** | **17.26** | 0.26 | 0.35 | **0.52** |
| 8 | 15.88 | 0.24 | 0.32 | 0.48 |

### 3.2 供给侧（32-bit DDR3，2 片 ×16bit）

| 配置 | 理论带宽 | 典型有效（70–85%） | 说明 |
|---|---|---|---|
| DDR3-400（400MT/s，32-bit） | 1.6 GB/s | **1.1–1.36 GB/s** | 低功耗/低端板卡常见 |
| DDR3-800（800MT/s，32-bit） | 3.2 GB/s | **2.2–2.7 GB/s** | 常见 7-series 板卡 |
| 任务给定预算区间 | — | **1.6–2.2 GB/s** | 本报告用该保守区间做判据 |

### 3.3 结论

1. **带宽可行**：30fps 需 **0.48–0.56 GB/s**（模型侧 B=8 口径 15.88 MB/帧 = 0.48；推荐 tile 自适应
   = 0.52 GB/s），仅为有效带宽的 **24–35%**；即使按任务给的保守下限 1.6 GB/s 也有 ~3× 余量。
   交叉验证：T-model `arena_map.summary` 的帧流量 15,246,400 B 与本报告独立求和逐字节一致。
2. **余量可容纳 DDR3 其它用途**：320×320 RGB888 帧缓冲写+读 @30fps ≈ 0.018 GB/s；
   VGA 640×480×16b@60Hz 显示读 ≈ 0.037 GB/s；加上 CPU/预处理的零头，合计 <0.1 GB/s。
3. **但 30fps 的天花板不是 DDR3，是 NPU 算力/时序**：C320 粗估 **7.3M 拍**
   （6.25×C128 的 1.167M），@125MHz ≈ **58ms = 17fps**；dw16+conv0 loader 优化后 ~6M 拍
   ≈ 20–21fps@125MHz；**30fps 需要 ≤3.33M 拍@125MHz**，要 PX16/更高频/更大并行（见 PX16-STUDY）。
   所以 P3 的存储目标应写成"**在 NPU 能达到的任何帧率下不成为瓶颈**"，本文已证明成立。
4. 若沿用现调度（40.9 MB/帧）：30fps=1.23 GB/s（占 1.6GB/s 的 77%，突发/仲裁后危险）；
   20fps=0.82GB/s、17fps=0.70GB/s 仍可行 —— 但延迟余量小，且 OC 重读会放大行激活开销。
   **所以 band-outer 调度是 P3 必做项，不是优化项。**

## 4. Tile 缓存设计（BRAM）

### 4.1 可用 BRAM

- 器件 135 tiles；当前整机 = nn_mem 112（W80 + A/B32 + Q0）+ 核心 ~9.5 ≈ **121.5/135**（R3 实测）。
- ⇒ **tile 缓存可用 ≈ 13.5 tiles ≈ 60.75KB**（若 MIG/互联不吃 BRAM；见 §6 风险）。
- **⚠ 显性风险（Lead 要求保持可见）**：推荐 tile cache 设计 = **12.4 tiles（56KB）**，
  整机余量只剩 **~1.1 tiles（~5KB）**。**若后续上 MIG（或其它 IP 吃 BRAM/LUT），必须重算 BRAM 预算**：
  MIG 7-series 控制器本身通常不吃 BRAM（但 AXI 互联/FIFO/调试可能吃），且 MIG 会吃 LUT/MMCM；
  一旦 BRAM 不够，tile cache 需降级到 §4.2 的方案 2（8.9 tiles，B 选择更保守，流量 18.5MB/帧仍带宽安全）
  或进一步缩到单缓冲（牺牲 DMA/计算 overlap）。**结论：tile cache 尺寸要在"MIG 资源实测后"复核，不能先定死。**
- C128 的 A/B 窗口（96KB+32KB，物理 32 tiles）在 P3 模式下即为"片上直通模式"保留兼容；
  P3 模式复用同一块 A/B 物理阵列作为 tile cache（见 §4.4 方案 B），或新增独立 tilecache 模块（方案 A）。

### 4.2 Tile 尺寸（行带）

引擎每拍处理 8 px × 16 OC lane；C320 各层宽度/通道差异大。按"输出行带 B 行 × 全宽 × 全通道"评估
（per-op 自适应 B；见 §4.3 选择规则）：

| B（输出行） | 最坏单 op 工作集（IBUF+OBUF） | 双缓冲 2× | 大 row 层（op9/op50, iw=160 ic=24） |
|---|---|---|---|
| 1 | 15.4 KB | 30.0 KB | in 11.5KB/out 1.9KB |
| 2 | 23.0 KB | 45.0 KB | in 19.2KB/out 3.8KB |
| 4 | 42.2 KB | **82.5 KB（超预算）** | in 34.6KB/out 7.7KB |
| 8 | 80.6 KB | 157.5 KB | 超预算 |

- **输入带行数** = `(B-1)*stride + k`（conv/dw/pool；halo = k−stride 行重叠），
  行字节 = `iw*pad8(ic)`（packed3 = `iw*3`）；**输出 tile 行字节** = `ow*pad8(oc)`。
- 8 通道对齐：所有张量按 8ch 块（8B）对齐；行字节天然是 8 的倍数；DMA 以 **16B** 为一个 beat
  （=16 个 int8 lane，正好 2 个 8ch 块），16B 对齐由行首对齐保证（packed3 行 960B 也是 16B 倍数）。
- **conv0（PACKED3，模型侧 8 行带）**：每带输入 17 行 × 960B = **16,320 B < IBUF 16,384 B ✓**
  （band0 裁顶部 pad 后 15,360B）；20 bands、halo 合计 18,240B（+5.9%），精确的 20 个
  `in_byte_range` 已在 `arena_map.conv0_streaming.bands` 给出，可直接做 DMA 张量表。
- 因此方案 1 的 IBUF=16,384B 同时覆盖 conv0 的 8 行带与通用 conv/dw 的自适应 4 行带；不需要为 conv0 单独扩缓存。
- 推荐缓存预算（**方案 1，12.4 tiles**）：
  - **IBUF：2 银行 × 16,384 B = 32KB**（单带最大 16,384B）
  - **OBUF：2 银行 × 12,288 B = 24KB**（单 tile 最大 12,288B）
  - 合计 **56KB = 12.4 tiles**（4.5KB/BRAM）；留 ~1 tile 余量。
- 保守（**方案 2，8.9 tiles**）：IBUF 2×12KB + OBUF 2×8KB = 40KB，B 选择更保守（11 层用 B=1），
  混合流量 18.50 MB/帧（30fps 0.56 GB/s，仍远低于 DDR 上限），给 MIG/其它留 4.6 tiles。

### 4.3 自适应 B 选择（写进 SW/ROM 的 tile 描述符）

规则（方案 1：IBUF=16KB、OBUF=12KB）：从 B=4 起试，`band_in(B) ≤ IBUF 且 band_out(B) ≤ OBUF` 即选该 B。
实测分布（112 op）：**B=4: 95 层、B=2: 15 层、B=1: 2 层（op9/op50 dwconv）**；
混合流量 17.26 MB/帧（30fps 0.52 GB/s）。方案 2 为 62/39/11，流量 18.50 MB/帧。

### 4.4 tile DMA 读写口契约

两条独立 SDP（简单双口）通道，天然 1 写 + 1 读，**不需要复制 BRAM**：

| 通道 | 数据流 | 端口 |
|---|---|---|
| **fill** | DDR3 → IBUF | DMA 写口：`128b + 16B 字节使能`（同现有 b_wstrb 语义），地址 = tile 内 16B 序号；行跨距/通道步长来自寄存器 |
| **flush** | OBUF → DDR3 | DMA 读口：`128b`，每次 16B（1 beat），地址 = tile 内 16B 序号；输出长度由行数/通道数寄存器算 |

- **引擎侧**：`a_*`（读 IBUF）与 `b_*`（写 OBUF）**端口语义/位宽不变**，只把地址从"整个窗口的绝对偏移"
  改成"tile 内偏移"（tile 窗口基址由寄存器给出）；`a_rdata/b_wdata` 位宽 128b 不变。
- **双缓冲**：IBUF 两组银行 ping-pong（fill 下一带 / 引擎读当前带）、OBUF 两组（引擎写当前 / DMA 冲上一带）；
  用 `credit/empty/full` 握手（各 1 bit × 2 银行），引擎在 band 边界等 `IBUF ready`、DMA 等 `OBUF valid`。
- **halo**：band 边界输入行重叠 `k−s` 行（k=3,s=1 → 2 行；k=5,s=2 → 3 行）；IBUF fill 直接按"本带覆盖的
  DDR 行区间"重复读（流量已计入 §3.1 的 halo 放大）。
- **stride/padding**：stride=2 时输入带行号 = `(oh_band_start*2 - pad + ky)`；越界行整行填 `zp_in`
  （通过"行有效"标志位让引擎按现有 padding 语义处理，不需要 DMA 预填）。
- **copy/concat 的部分通道写**：copy 写 48/192 通道，flush 时按 8ch 块拼 burst（行内 stride = `ow*pad8(oc)`，
  block 大小 = `pad8(ic)*1B`），需要一个 `dst_row_stride / dst_ch_off` 寄存器对；建议 DMA 每 beat
  只搬"连续 16B"，跨通道/跨行由地址生成器 + 命令队列完成。
- **packed3 conv0 流式输入**：输入 320×320×3=307,200B 在 DDR 按原 packed 布局；tile 行字节 960B，
  fmt 标志让 engine 走 PACKED3 读取（3B/px，stride2 → 输出 160×160）。

### 4.5 与现有 nn_mem 端口的关系 / 最小改动方案

**方案 A（推荐）：新增独立 `nn_tilecache.sv` 模块，nn_mem 零改动**
- 新模块：IBUF/OBUF 两组 BRAM + DMA fill/flush 端口 + 与引擎 a/b 直连的读/写端口 + band 寄存器组。
- nn_subsys 在 P3 模式下把引擎的 a/b 口切到 tilecache（C128 模式仍接 nn_mem，双模兼容）；
- 优点：nn_mem 的 tb（47,146 checks）/资源/时序全部不动；缺点：+1 个模块与 2 组端口 mux（LUT 少量）。

**方案 B（若坚持并入 nn_mem）：最小端口增量**
- 复用现有 A/B 阵列做 IBUF/OBUF（P3 模式下 A/B 窗口尺寸变大 96KB/32KB → 实际配置改为 IBUF/OBUF 大小），
  新增：`dma_fill_we/dma_fill_addr/dma_fill_wdata[127:0]/dma_fill_wstrb[15:0]`（写 IBUF）、
  `dma_flush_re/dma_flush_addr/dma_flush_rdata[127:0]`（读 OBUF）、`tile_mode/tile_bank` 控制寄存器；
- **风险**：现有 A/B 是 1R+1W 的 SDP；加 DMA 写 IBUF 与引擎读 IBUF 已是 1R1W ✓，但 OBUF 的
  "引擎读（ADD 的 dst 读）+ 引擎写 + DMA 读" 是 2R1W → 会复制 BRAM（+32 tiles，不可接受）；
  必须把 ADD 的 dst 读也走 IBUF（先把 dst tile fill 进 IBUF），才能保持每块 1R1W。这一步改变了 ADD 的
  数据流，影响引擎（add 的 src/dst 都要从 tilecache 读），所以**方案 B 实际也要动引擎**，不划算。
- 对 tb_nn_mem 的影响：默认 C128 模式行为不变，新增 P3 模式需扩 TB；对引擎影响：a/b 地址口径改为
  tile-relative（ROM 里要加 tile base 字段）。

**结论：走方案 A**（独立 tilecache，nn_mem 不动、引擎端口不动，只改 nn_subsys mux + 新增 ROM tile 字段）。

## 5. 125MHz 时序评估（act 读/写地址寄存）

> **2026-11-01 15:4x 修正（实测发现，重要）**：Lead 最初判断"最差路径是 act_mem **写**地址"，
> 但方案 A（写命令打拍）实测后最差路径的源寄存器仍是引擎 `x_ld`，而不是新加的 `npu_wr_idx`
> ⇒ `ADDRBWRADDR` 是 A/B 阵列的**读地址口**（Vivado 把 read 映射到 port B）。因此：
> **方案 A 单独对该路径无效**（pipe@8ns WNS 只 +1.299ns，data 6.298→6.136ns）；
> 真正对症的是 **方案 B：act 读地址打一拍**（读时延 1→2，+2.2% 周期；CPU 窗口读也 +1 拍），
> 或 **方案 C：引擎侧预寄存 a_addr**（周期可 0）。详见 `proto/mem/ACTWR-PIPE.md`（含契约变更与
> 三个变体的功能自证 PASS 记录）。

### 5.1 现状证据

- T-accel 的 engine+mem OOC（`proto/engine/synth100_timing.rpt`，`create_clock 10ns`）：
  **WNS +3.137ns**，worst path：
  `u_eng/x_ld_reg[1] → u_mem/act_mem_reg_0_0/ADDRBWRADDR[10]`，
  data 6.298ns（logic 1.856 / **route 4.442 = 70.5%**），9 级逻辑（CARRY4×2 + LUT3×2 + LUT4 + LUT6×4）。
  源是引擎 load/pad 列逻辑 ⇒ 该端口实为 **act 阵列读地址（a_addr）** 路径。
- 同一 RTL 加 8ns 约束后（`synth125_timing.rpt`）最差路径变为 ADD_R 的
  `src_word_q → ad_mul`（+0.031ns）——说明在**综合网表**里 act_mem 路径在 8ns 下还有 ~1.1ns 余量；
  但**全实现**里该路径 route 占 70%，布线后会成为最差路径，所以要先治它。
- 另一条相关：nn_mem 单独 OOC @125MHz **WNS +3.846ns**（§6）⇒ 问题在"引擎→mem 的跨模块长组合路径 +
  布线"，不在 mem 内部寄存器（mem 内部 reg→reg 余量充足）。

### 5.2 方案与代价（实测修正后）

| 方案 | 做法 | 合同/功能影响 | 周期代价 | 实测/预期收益 |
|---|---|---|---|---|
| A. NPU act **写**命令寄存 | nn_mem 内对 NPU 侧 `b_*` 打一拍（CPU 写不打拍） | b 写延迟 1→2 拍 | **0 拍** | **实测无效**：pipe@10ns +3.299 / @8ns +1.299；最差路径不变（源仍是 x_ld）。仅作 A+B 组合项 |
| **B. act 读地址寄存（对症）** | nn_mem 内对 `act_rd_idx` 打一拍（NPU 与 CPU 共用读口） | **a 读 1→2 拍**；**CPU 窗口读也 1→2 拍** | **+1 拍/块**：C128 +25,200 拍 = **+2.2%**；C320 同样 2.2% | 预期 @8ns **+3.2～+4.1ns**（收益 +1.9～+2.8ns），@150MHz 有机会；功能自证已 PASS（TB a/cpu 读 +1 拍） |
| **C. 引擎侧预寄存 a_addr** | 在 S_NEXT 提前算好 a_addr，或把 pad/load 选择寄存 | 无 mem 合同变化（CPU 窗口保持 1 拍） | 可能 0（用现成空拍） | 效果同 B 且无 CPU 读 2 拍副作用；属于 T-accel 域改动（推荐与 B 二选一） |
| A+B 组合 | A+B 同时 | 写 2 拍 + 读 2 拍 | 读侧 +2.2% | 预期与 B 接近（A 增量 <0.2ns），留作 150MHz 余量 |

- **建议顺序（修正）**：先看 125MHz 全实现结果；若差 ≤0.5ns 且 CPU 窗口 2 拍可接受 →
  **方案 B**（proto 已就绪，功能 PASS，可直接落）；若 CPU 2 拍不可接受 → **方案 C**（T-accel 引擎预寄存）；
  A 单独不解决问题，作为 B/C 之后的余量手段。
- 合同文档更新项：SPEC §3 的 **a 读时延（B 时 1→2）**、**b 写时延（A 时 1→2）**、CPU 窗口读时延（B 时 1→2）、
  tb_nn_mem 等待、engine 的 LD 相位（B 时 +1 拍/块）与 done/next-op 间隔（A 时写 2 拍仍安全）。
- 已就绪的 proto 材料：`nn_mem_pipe/piperd/pipeab.sv` + 对应 TB（PASS）+ OOC wrapper/tcl/bat +
  `ACTWR-PIPE.md`；三档（100/125/150MHz）× 四变体的 OOC 对比等 Lead 的"125 全实现跑完"信号后执行。

## 6. nn_mem 单独 OOC @125MHz 证据（交付 2）

**结论：nn_mem 自身不是 125MHz 的瓶颈，112 BRAM36 合规，WNS 余量 3.846ns。**

```bat
rem 一键复现（纯 ASCII）：
results\ai-accel\proto\mem\run_synth_125.bat
rem 输出：%TEMP%\nn_mem_v07_synth\v07_125_util.rpt / v07_125_timing.rpt
```

实测（Vivado 2018.3，`create_clock -period 8.000 [get_ports clk]`，随机内容镜像 `--seed 20261101`）：

| 指标 | 数值 |
|---|---|
| WNS（8ns 约束） | **+3.846 ns（MET，0 failing endpoints）** |
| Block RAM | **112 tiles**（RAMB36=112、RAMB18=0：W80 + A/B32 + Q0） |
| Slice LUTs | 7,186（其中 Q ROM ≈6,981） |
| Slice Registers | 1,260（u_dut 内 85） |
| DSP | 0 |
| 最差路径 | `u_dut/act_mem_reg_4_0/CLKBWRCLK → probe_reg[0]/D`（取证顶层的观测寄存器，数据 4.016ns，3 级）——**不是 mem 内部 reg→reg 路径** |

⇒ 全实现要把 125MHz 做上去，重点在引擎内部（ADD_R 乘法器/requant）与**引擎↔mem 的跨模块写地址路径**（§5），

## 7. 风险清单

| # | 风险 | 影响 | 建议 |
|---|---|---|---|
| R1 | **`nn_rom_t.src/dst` 19 bit（512KB）不够 C320 arena** | arena 实际用 819,200 B（0.819MB）、预留 2MB 窗口；19-bit byte 地址只有 512KB；另外若存 **DDR3 绝对地址**（base `0x0100_0000`=16MB）则需要 25 bit | **Lead 已拍板：21-bit byte 地址（arena 相对，硬件加 base 寄存器）**：nn_rom_t 200→208 bit（src/dst 19→21），128 项 ROM 仍 1 个 BRAM36（26.6Kb<36Kb，**零 BRAM 代价**）；C128 旧值（≤0x7FFFF）不受影响。需 Lead 改 `nn_pkg.sv`+`tools/nn_gen_rom.py` 并重生成 C128/C320 ROM；T-model 的 `nn_rom_table.json`/`arena_map.json` 已按此口径（见 `P3-320-ARENA.md` §rom_width） |

| R6 | **halo/stride2/padding 的行边界** | band 边界重复读行（B=8 时 +4%，B=4 +8%）；stride2 的跨带行号易错位；conv0 首/末 band 需裁 pad 行 | B 选择规则按 §4.3 固化到 ROM 描述符；band 边界行直接多读整行（流量已计入）；conv0 用模型侧 8 行带（20 bands，halo 18,240B，`arena_map.conv0_streaming` 已给出 20 个 band 的精确字节区间） |

| R10 | **arena 地址源** | plan 的 src/dst 是**虚拟 A/B 口径**（A=0/B=0x400000），不能直接进 DDR3 | **以 T-model `arena_map.json` 为唯一地址源**（arena base `0x0100_0000`，预留 2MB，0 碎片，16B 对齐，每张量 `arena_off` 已给）；ROM 存 21-bit arena 相对偏移 + 硬件 base 寄存器 |
