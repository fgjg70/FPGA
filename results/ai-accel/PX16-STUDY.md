# PX_LANES=16 设计研究（T-accel-R3，仅评估，不动 RTL）

> 目的：回答"把像素并行从 8 提到 16（16 OC lane × 16 px = 256 MAC/拍）能拿多少，代价是什么"。
> 依据：当前 v3（128 MAC）实测/综合数据 + 公式外推。**所有数字是估算，需实做验证**。
> 结论先行：**PX16 单独不值得做**（写口带宽先饱和，小层无收益；DSP 需 256 超 160 预算）；**只在"dw16 + requant 缩减"之后再考虑**，且 C320 也只能到 ~24–27fps，仍不够 30fps；30fps 更可靠的路径是 **≥125MHz 主频** 或 320 档改用按行 tile 的更大并行（见 §5）。

## 1. 当前 v3 基线（已实测）
| 项 | C128（112-op plan） | 备注 |
|---|---|---|
| 周期估算 | **1,167,368 拍**（@100MHz 11.67ms，85.7fps） | `full_model_estimate_v3.md` |
| 其中 conv | 672.5k 拍 | 56 个 conv（含 conv0 PACKED3 129k） |
| 其中 dwconv | 449.2k 拍 | 28 个 dw 仍是 **8-lane**（128 MAC 未用上） |
| 其中 add | ~40k 拍 | 18 个 ADD_R（本轮 +1 拍/字流水） |
| 其余 pool/copy/up | ~14k 拍 | — |
| OOC 100MHz | WNS/资源见 `synth100_*.rpt` | LUT ~32.6K（含 Q ROM ~7K）、FF ~13.9K、DSP ≤160 目标、BRAM 112 |

C320 粗推：周期 ≈ 6.25× C128（空间×2.5²）≈ **7.3M 拍 → 73ms@100MHz ≈ 13.7fps**（目标 30fps 需 3.33M 拍）。

## 2. PX16 的结构改动（engine 内部，端口不变）
1. **band/window**：`abuf[~40]`/`bshift[~40]` 64b（16 px × stride2 + K−1 = 35–37 字）；`win_sel[16]`；`a_pipe[16][16]`。
2. **MAC 阵列**：16 px × 16 oc = 256 个 8×8 乘加。DSP 预算 160 ⇒ 最多 160 个进 DSP，**其余 96 个必须 LUT 实现**（每个 8×8≈26 LUT ⇒ +2.5K LUT；或 96×"2 MAC/DSP"打包，复杂）。
3. **acc**：16×16×32b = 8K FF（v3 是 4K，+4K FF）。
4. **requant**：每拍处理 16 lane×1 px 的流水不变，但像素数×2 ⇒ 每 block 的 requant/write 拍数**翻倍**（8→16 beat 或 16→32 beat）；若保持"每像素 16B 单 beat"，block 写拍 16。
5. **写带宽**：每 block 输出 = 16 px × 16B = 256B = **16 个 128b 写 beat**；A/B 物理写口只有 1 个 128b/拍 ⇒ 每 block 至少 16 拍写。
6. **周期**：MAC 拍数/block 不变（sub·8K），但 block 数减半（NB 减半）⇒ MAC 部分 ×0.5；**但 block 内写/requant/装载拍数不变** ⇒ 小层（ic 小、K=1）没有收益，甚至写口成为瓶颈。

## 3. 收益估算（C320 @100MHz）
| 方案 | C128 周期（估） | C320 周期（×6.25） | C320 帧时 @100MHz | fps |
|---|---|---|---|---|
| 当前 v3（128 MAC，dw 8-lane） | 1.17M | 7.3M | 73ms | 13.7 |
| +dw16（必修） | ~0.96M | 6.0M | 60ms | 16.7 |
| +dw16+requant 单 beat/conv0 优化 | ~0.90M | 5.6M | 56ms | 17.9 |
| **+PX16（在 dw16 之后）** | ~0.62–0.68M | 3.9–4.3M | 39–43ms | **23–26** |
| +PX16+125MHz 主频 | — | — | 31–34ms | **29–32**（需 OOC 125MHz 收敛，PX16 下风险高） |

前提/风险：
- DSP：PX16 需要 256 个 MAC；预算 160 ⇒ 96 个 LUT MAC（+2.5K LUT、时序风险）。若允许 240 DSP 上限，则 DSP 256 仍超（器件 240），必须 LUT 补 16+。
- LUT：v3 已 32.6K（含 Q ROM ~7K，不含 Q ~25.6K）；PX16 预计 +6–9K LUT ⇒ 整机可能超 63.4K（视频链路未加）。
- FF：13.9K → 预计 24–27K。
- 时序：requant 16 像素串行流水已占 REQ 16–24 拍/block；PX16 后 REQ 32–48 拍/block，**写口/REQ 成为主要瓶颈**，100MHz 下需再切流水（可能 +1–2 拍/像素），实际收益低于线性。
- 结论：PX16 的"峰值 256 MAC"只在 K≥3 或 ic≥16 的层接近达标；对 YOLO-Fastest 大量 1×1（ic=8/16/24）层，写口吞吐限制使收益折半。

## 4. 与 dw16 的叠加
- dw16 独立于 PX16，应**先做**（收益 38.6% 周期 → ~25%，且不改 MAC 阵列规模/DSP 预算）；
- PX16 在 dw16 之后再看：预计 C320 从 16.7fps → 23–26fps（仍 <30）；
- 两者叠加后 DSP/LUT 都逼近上限，视频链路（显示/帧缓存）还没算进去，风险高。

## 5. 更可靠的 30fps 路线（供拍板）
1. **主频优先**：把全实现从 100/87.5MHz 提到 **125–150MHz**（D4 目标本来就是 ≥100）；C320 16.7fps@100 → 25fps@150（+dw16/其它优化可到 30+）。代价：时序收敛难（当前 100MHz OOC 仍 WNS 负，需继续拆），但比 PX16 的 LUT/DSP 风险小。
2. **320 档按行 tile + DDR3**：320 输入中间激活本来就要进 DDR3（P3 规划）；把 320 推理改成"行块流水"可让 MAC 效率不随层变小而塌（每 tile 的 Q/REQ 开销摊薄），配合 dw16 有望 100MHz 达 20–25fps。
3. **PY: 只做 128 档 30fps 演示 + 320 档 15–20fps**（若用户接受"320 是预期不是硬指标"）。
4. PX16 建议作为"最后手段"：先做 dw16+写带宽优化，拿实测；若仍不够再评估 PX16（需重跑布局布线风险）。

## 6. 建议决策问题（给 Lead/用户）
1. 优先级：**30fps@320** vs **100MHz 稳定 + 完整链路（视频/DDR3）**？（当前我按后者推进）
2. 若保 30fps：接受 **PX16（LUT/FF 大、时序风险高）** 还是 **提频（125–150MHz）**？
3. 是否允许把"引擎 DSP 上限"从 160 放宽到 **200**（PX16 的 LUT MAC 可减半）？
