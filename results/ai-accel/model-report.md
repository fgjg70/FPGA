## 1. 生命周期与复现命令

```powershell
python tools/yolo/download_assets.py            # cfg+weights（尺寸校验）
```

全链确定性：输入图为公式 `q[y][x][c] = int8((x*13 + y*7 + c*29 + seed) & 0xFF)`（seed=12345）；权重/校准/量化无随机数。重复运行 `plan.json`/`checksums.txt`/`yolo_wq.hex` 逐字节一致。

## 2. 模型结构与权重读取（①）

- cfg：131 个 layer（84 conv 中 **28 depthwise**，18 shortcut，3 maxpool，5 route，18 dropout，2 yolo）；输入 3×320×320 训练分辨率。
- 官方 `.weights` 的**前 20 B 是 AlexeyAB darknet 头**（3×int32 + uint64 seen），去掉后 346062 floats 与 cfg 逐层参数个数（含 BN 的 bias/scales/mean/var）**精确相等**。这是本任务最容易错的一步，`load_weights()` 内置字节数 assert，任何偏移都会直接 fail。
- 数值抽查（layer 0/2）：权重 std 0.527/1.135、absmax 1.788/4.534；BN gamma 0.83~4.17、所有 BN 层 var>0。
- BN 折叠：`W'=W·γ/√(var+ε)`、`b'=β-mean·γ/√(var+ε)`（官方权重里 BN 层的 conv bias 即 β，注意 darknet 对 BN 层不再训练单独 conv bias，实测文件里就是这样）。

**关键发现（需同步 CONTRACT §3）**：v0.3.1 原计划 A=0x60000(64KB)/B=0x70000(64KB) **放不下 128 输入**：layer 9 的输出张量（24ch@64×64）单张量就有 **98,304 B**，超出 64 KB；且该张量与残差支路输入 32,768 B 同时活跃，需要 128 KB 总活跃量。

`plan.json` / `model.json` 已按 `a_base=0x60000, b_base=0x78000` 生成；**建议 CONTRACT §3 改为此切分**（仅移动 A/B 边界，不改窗口大小）。

## 5. int8 PTQ（②）与 golden（③）

### 5.1 量化契约实现（CONTRACT v0.3.1 §5）

- 权重 per-OC 对称：`s_w[oc]=max|W'[oc]|/127`，`w_q=clamp(round(W'/s_w),-127,127)`；
- 激活 per-tensor 非对称：`s_a=(max-min)/255`，**`zp_a = -128 - round(min/s_a)`**（Lead 确认口径；[0,1] 图像 ⇒ `s_in=1/255, zp_in=-128, a_q=round(a·255)-128`）；
- 累加：`acc = Σ a_q·w_q + bias_adj`，int64；`bias_adj=round(b'/(s_a_in·s_w)) - zp_in·Σw_q`；
- requant：`M_pos=round(s_a_in·s_w/s_a_out·2^SHIFT)`；`M_neg=(M_pos·3277+16384)>>15`（引擎现算，Q 区不存 M_neg）；`y=(acc>=0?acc·M_pos:acc·M_neg)>>SHIFT`（**floor**）；`out=clamp(y+zp_out)`；
- **每层独立 SHIFT**（tail[3]，16..24）：取使 M_pos 落在 int16 内的最大 SHIFT，实测 SHIFT 直方图见下表；M_pos 范围 174..32,754（全模型），整数舍入误差 <1e-3；
- conv 边界外像素填 **zp_in**（不是 0），padding 通道权重量 0；激活 padding 通道填 `zp_a`；checksum 只覆盖真实通道；
- **residual add（v0.5）**：shortcut 改由 CPU 执行 `cpu_add`（kind code 8）。branch 张量保持自己的 per-tensor 非对称 (s_s, zp_s)，add 时按 CONTRACT §11 做源域→目标域 requant：`R=round(s_s/s_d*2^K)`、`out=clamp(q_d+(((q_s-zp_s)*R)>>K),-128,127)`（int64 中间、floor 右移、**不加 zp_d**）。plan 字段：`src/dst/ih/iw/ic/r_scale/k_add/zp_s/csum`。实测 18 个 cpu_add 的 K 全为 15，R∈[4249, 41736]（≤2^20，C 侧 s32 乘积安全）。
- 池化/上采样/route-concat：同组共享 (s_a, zp_a)，raw int8 拷贝/取 max。

### 6.1 修复前后对比（Round-1 raw residual add → Round-2 cpu_add）

| 指标 | Round-1（raw add，共享 scale） | Round-2（cpu_add） | 目标 |
|---|---:|---:|---:|
| 逐层 cos@128 均值 | 0.9767 | 0.9738 | ≥0.99 |
| 逐层 cos@128 最小 | 0.9186 | 0.9174 | ≥0.99 |
| 层数 <0.99（共 112） | 91 | 96 | 0 |

**修复内容**：18 个 shortcut residual add 从引擎 raw-int8 add 改为 CPU `cpu_add`（v0.5），branch 张量不再与 sum/identity 共享 (s_a,zp_a)。实测效果：
- branch conv 自身量化台阶从「sum 域 ±19 / 255」变为「branch 域 ±1.5 / 255」，单张量纯 roundtrip cos 从 0.93~0.96 提升到 **0.9999**；
- 但**逐层 cos 均值只从 0.9767 变到 0.9738**（目标 ≥0.99）——因为失败层的主要误差来自上游（每层输入 cos 已只有 0.96~0.98），即整条链的**累积量化噪声**，而不是 branch 单层。

### 6.2 为什么逐层 cos 卡在 0.97~0.98（定量归因）

对 CONTRACT 规定的 **per-tensor 8-bit 激活量化**，即便用理想实现（float 累加 + round 量化格点 + 量化权重）也存在理论下限，实测如下（`python tools/yolo/analyze_ceiling.py --hw 128`）：

| 模型 | 逐层 cos 均值 | 最小 | <0.99 层数 | 说明 |
|---|---:|---:|---:|---|
| 实际整数模型（floor requant，交付值） | 0.974159 | 0.917396 | 92/108 | 本报告交付 |
| 同上但 requant 改为 round | 0.982497 | 0.947017 | 80/108 | 说明 floor 偏置约贡献 +0.7% 均值 |
| **理想 QDQ（float 累加，方案上限）** | **0.988877** | **0.967025** | **58/131** | per-tensor 激活量化的理论天花板 |
| 实际整数模型（仅 conv 84 层） | 0.975050 | 0.917396 | 68/84 | — |
| 理想 QDQ（仅 conv 84 层） | 0.990178 | 0.967294 | 31/84 | 仍 <0.99 |

结论：**per-tensor 8-bit 激活量化的理论天花板就已低于逐层 cos≥0.99 的判据**（即使实现完全理想）。原因是本模型 leaky 激活的分布重尾（同一张量内典型值远小于最大值，例：sum 张量范围 ±19 而典型 |x|~0.5~2），per-tensor 步长只能按极值选，累积 ~50 层后误差方差叠加。MSE 最优裁剪校准也验证无效（83/84 组选到不裁剪，见 §6.3）。

### 6.3 尝试过但无效/不达标的其它手段
- **MSE 最优裁剪校准**（每 group 在 85%~100% 分位间搜最小 MSE 的 clip）：83/84 组最优解是**不裁剪**（分布本身没有单点 outlier），逐层 cos 0.9775（无变化）。
- **percentile 固定裁剪** 99.9%：mean 0.9820（略好），但 min 仍 0.9398；99.5% 以下明显变差。
- **requant 改 round**（会违反 CONTRACT §5 floor 口径）：mean 0.9849 / min 0.9592，端到端匹配反而下降到 320=79.1%、128=74.1%，不是有效方案。
- **固定 SHIFT / M_neg 近似 / 权重 outlier 裁剪**：均非瓶颈（roundtrip 已 0.9999）。

### 6.4 若要真正达到 cos≥0.99（需 Lead 契约决策，本报告未实施）
1. **per-channel 激活量化**（对 conv 输出逐 OC 选 s/zp）：Q 区需扩（每层多 2*OC_pad 字节），引擎读 Q 与 requant 需按 OC 选 s/zp → RTL/Q 布局变更；
2. **对约 18 个 identity/sum 链张量用 16-bit 激活**（其余 int8）：A/B 缓冲与引擎读口位宽变更；
3. **放宽判据**为均值 cos≥0.985 + 端到端框匹配≥90%（后者需真实图校准/更大评测集再验证）。

**当前交付取舍**：按 Lead 已拍板的 v0.5 cpu_add 方案交付（不改 RTL）；

**结论**：**86.1% → 73.1% 是评测集变化的假象，不是回归**。Round-1 归档数字来自「3 张真实图 + 9 个 dog 增广」的 12-case 集合；Round-2 交付数字来自「5 张真实图（新增 fruits/home，无 COCO 目标）+ 9 个增广」的 14-case 集合，且 Round-2 用 5 张真实图校准（Round-1 用 3 张）。同一 case/seed 下有：@320 R1=76.9% (40/52) → R2=73.1% (38/52)（R2 更好 1 / 持平 11 / 更差 2；差的是 fruits/home，本来匹配数 ≤2），meanIoU 0.777→0.662；@128 R1=81.8% → R2=81.8%，meanIoU 0.747→0.695。方案隔离（同一份校准数据）：calib3 下 R1=76.9% / R2=73.1%；calib5 下 R1=71.2% / R2=73.1% —— cpu_add 的效果与校准集强相关，**没有回归信号**；也没有公式 bug（18 个 cpu_add 对 fp32 参考最大 1 LSB）。

## 7. 建议输入分辨率

**建议 128×128**（给 Lead 拍板的依据；Round-2 端到端实测见 §6）：

- **容量**：128 是唯一能塞进 512 KB 窗口并保留完整 int8 权重/Q 的方案：W 312.3 KB + Q 43.2 KB + A 96 KB + B 32 KB；A/B 峰值恰好 128 KB。
- 160/320 **不可行**（按 §8 紧凑布局）：输入 packed 分别 76,800/307,200 B，最大单张量 153,600/614,400 B，超出 A/B 容量（A 96 KB，B 32 KB）；即使扩到 64K+64K 也不够（98,304 B 单张量 >64 KB 已卡死 128）。
- MACs：128 → 20.07 M（相对 320 的 125.44 M 只有 16%），96 → 11.29 M 但检测能力明显变差（float 基线 14 case 中 96 只有 18 个框，128 有 55 个）.
- 端到端：128 的 float/int8 检测仍可用（见 §6 表）；320 的 float 精度最好但装不下。

## 11. v0.6/v0.7 全硬件计划 + 微码 ROM 数据源 + C320（Round-3）

依据 `MODEL-FREEZE.md`（D1–D5）与 `SPEC-SPECIALIZED.md`：把 **CPU 辅助算子全部硬件化**，并产出 `nn_seq` 微码 ROM 的数据源。**权重字节不变**（W region 与冻结 v0.5 逐字节相同）。

### 11.1 plan 结构变化（0 个 CPU 执行 op）

| 旧（v0.5） | 新（v0.6/v0.7） | 语义 |
|---|---|---|
| `cpu_conv0`（1 个） | `conv` + flags bit2 **PACKED3** | 输入 3B/像素 packed 寻址；权重仍 dense IC_pad=8（后 5 个 IC 权重=0）；Q 块沿用 conv 标准布局 |
| `cpu_add`（18 个） | `add` + flags bit3 **ADD_R** | `out=clamp(q_d+(((q_s-zp_s)*R)>>KADD),-128,127)`；Q 块 16B（见 11.2）|
| `cpu_concat`（2 个） | **6 个 `copy`**（每源张量 1 条） | engine copy：`ic`=源通道数、`oc`=目标总通道数，src/dst 字节偏移含 8 通道块偏移 |

op 统计：**112 ops** = conv 56 / dwconv 28 / add 18 / copy 6 / pool 3 / upsample 1（128 与 320 相同）。W 区仍为 **319792 B**；Q 区 = 44544 B（84 个 conv 块 44,256 B + 18 个 ADD_R 块 288 B）。

**数值不变的证明**：`make_vectors.py` 内置回归断言——v0.7 的 108 个输出（conv/dwconv/pool/upsample/add + 两个 concat 目标的完整 FNV）与冻结 v0.5 的 `checksums`**逐位相同**；`copy` 的 per-op csum 按其写入的通道切片计算，`concatL<layer>` 行给出拼接完成后目标张量的完整 FNV。

### 11.2 PACKED3 与 ADD_R 的精确语义

- **PACKED3（conv0）**：激活地址 = `y*W*3 + x*3 + c`（c<3），IC lane 3..7 填 `zp_in`；权重按 IC_pad=8 的 dense 布局（后 5 个 IC 权重为 0）⇒ 数字与原 CPU conv0 完全一致（conv0 输出 FNV 与冻结值相同，见 11.4）。
- **ADD_R（18 个 shortcut）**：Q 块 **16 B**（CONTRACT §12.3 / Lead v0.7）：
  ```
  byte[0]=zp_s  byte[1]=zp_d(debug)  byte[2:3]=R (u16 LE)  byte[4]=KADD  byte[5:15]=0
  out = clamp(q_d + (((q_s - zp_s) * R) >> KADD), -128, 127)   # int64 中间, floor
  ```
  18 个 add 的 R：C128 ∈ [3908, 29651]、C320 ∈ [3110, 28821]（全部 ≤65535，u16 安全）、KADD 全 15；R/KADD/zp_s 与 v0.5 CPU 版逐位相同 ⇒ 数值完全一致（fp32 对照误差 ≤1 LSB，见 Round-2 §6.5）。
- **copy（6 个，替代 2 个 concat）**：SPP 拼接 = 4 个源张量（各 48ch → 目标 192ch，dst 块偏移 0/48/96/144）；head 拼接 = 2 个源（96ch + 24ch → 120ch，偏移 0/96）。copy 不做 requant，源/目标同属一个量化组（共享 s/zp）⇒ 与原 concat 结果逐位相同。
