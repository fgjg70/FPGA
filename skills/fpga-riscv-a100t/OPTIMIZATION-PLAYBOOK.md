# 优化剧本 — 从"哪里慢"到"改哪里"的固定流程

> **适用**：本仓库（主核 `core.sv` 五级 RV32IM + `ref5` 参照核）、`xc7a100tfgg484-2`、Vivado 2018.3
> **统一口径**：非工程模式、`create_clock -period 20.000`、**`fmax = 1000 / (20 − WNS)`**、`Slice LUTs` / `Slice Registers` / `Block RAM Tile`
> **一句话**：本项目的 fmax 瓶颈**从来不是"某段逻辑太深"**，而是
> **布线（route 占 62~93%）+ 少数几根高扇出广播网**。所以流程必须是
> **先量 → 选一根网 → 一次只改一件事 → 至少跑 2 次 → 重新选网**。

## 1. 决策流程（按顺序执行，别跳步）

### 步骤 0 — 环境与漂移自检（10 秒，不通过就别往下走）

```powershell
cmd /c tools\doctor.bat          # 环境 + R1 漂移检测
```

**为什么**：本项目最贵的一类事故是"拿旧产物当新结果"（R1/R28/R31/R17）。
`ref5` 之所以能做出 152.11，前提是它的 A/B 两份报告来自**同一个文件、只差一个 env 开关**；
而主核历史上不止一次出现"以为测了 X，实际测的是基线"。**任何数字在自证串出现之前都不可信。**

---

### 步骤 1 — 先量 route/logic 占比：逻辑受限还是布线受限

```powershell
python tools\path_hotspot.py fpga/timing.rpt
```

输出第一屏就给你 **Top-N 的平均 logic/route 占比**、WNS、fmax、TNS、failing endpoints、WHS。

| 判据 | 含义 | 该走哪条路 |
|---|---|---|
| **route ≥ 50%** | **布线受限** | 先动**物理/结构/扇出**；"砍逻辑"的收益会被布线吃掉 |
| logic > 50% | 逻辑受限 | 逻辑级数/逻辑深度/逻辑等价改写才是抓手 |

**本项目实测（全部是 route 受限）**：

| 设计 | 阶段 | route 占比 |
|---|---|---|
| 主核 | P1 之后（61.4 MHz） | 67.3%（`10.857 / 16.125 ns`，逻辑 19 级） |
| 主核 | 冲 100 MHz 战役（69.2 MHz） | 64%（`8.926 / 13.971 ns`，逻辑 18 级） |
| 主核 | 实验 F（76.0 MHz） | **80%**（`10.037 / 12.617 ns`，逻辑只 13 级） |
| 主核 | 当前 `fpga/timing.rpt` | 68.6%（`9.497 / 13.848 ns`，逻辑 15 级） |
| ref5 | V7 基线（137.25） | 62.4%（`4.215 / 6.760 ns`，逻辑 4 级） |
| ref5 | V1 规范字面版（102.47） | 71%（`6.58 / 9.23 ns`，逻辑 5 级） |
| ref5 | V12 十六 KB（118.57） | **86%**（`7.28 / 8.46 ns`，逻辑 5 级） |

> **R36 原话**："这**不是主核特有**，而是这颗器件 + 这类设计的普遍规律。"
> 一个 852 LUT 的教科书参照核和一个 2653 LUT 的功能完整核，route 都占 62~86%。

### 步骤 2 — 从"高扇出网清单"里选这一轮的抓手

这一步是本剧本的核心。**抓手不是"名字看起来该优化"的信号，而是 timing report 里
`fo` 很大、且该跳延迟很大的那根网。**

```powershell
# 默认 fpga/timing.rpt 只有 1 条路径, 想看 top-N + 全量高扇出网要先展开报告:
#   report_timing -delay_type max -max_paths 25 -file timing_paths.rpt
python tools\path_hotspot.py fpga\timing_paths.rpt --top 10
```

工具会给出三段：**每条路径逐跳明细**、**每条路径上的高扇出网（fo 降序）**、
**全局高扇出网 + "复制候选"短名单（fo ≥ 16，按该跳延迟降序）**。

**本项目两次实测的抓手长什么样**：

| 设计 | 网 | fo | 该跳延迟 | 动作 | 结果 |
|---|---|---|---|---|---|
| ref5 **E5** | `id_ex_b[3]`（ALU 操作数 B） | **115** | **3.0 ns** | RTL 上对该寄存器加 `(* max_fanout = 16 *)` | 137.25 → **145.75（+8.50）**，FF 458 → **554（真的复制了）** |
| ref5 E1+E5 | `id_ex_a[31]_i_2_n_0` | **97** | **2.657 ns** | 已经是复制副本的 D 侧公共项 | 152.11 时的 TOP1（瓶颈已转移到这里） |
| 主核（当前） | `u_core/u_btb/any_redir` | 122 | 0.704 ns | **不是候选**（延迟小） | — |
| 主核（当前） | `u_core/u_muldiv/rst` | **1124** | **6.757 ns** | **不是功能时序**（见 §3.2 盲区 2） | 在 `**async_default**` 的 **Recovery** 路径上 |

**选抓手的三个必要条件（缺一不可）**：

1. `fo` 大 —— 说明它在驱动一片"广播"；
2. **该跳延迟大** —— `fo` 只决定"该看谁"，**延迟才决定"值不值"**
   （主核 `any_redir` fo=122 单跳只有 0.704 ns；ref5 `id_ex_a[31]_i_2_n_0` fo=97 却 2.657 ns）；
3. **驱动它的是寄存器（FDCE/FDRE/…）而不是 LUT** —— 见 §3.2 盲区 1；
   `path_hotspot.py` 会把驱动元件类型打在每一行上。

### 步骤 3 — 一次只改一件事

**这不是风格建议，是被两次实测逼出来的硬约束**：

- `ExtraTimingOpt` 单用（配 E1）= **143.31（+4.65）**，E5 复制单用 = **145.75（+8.50）**，
  两个"都有用"的一起上 = **125.47（−26.6）**。
- 实验 F：`A'` 单独 = 76.0，追加 `max_fanout` = **72.8（更差）**。
- 实验 E5（省掉 BR/JAL 目标校验，"理论上冗余"）：单看 **64.9，原 69.2 = −6.2%**。

> **机理**：布局是**全局重排**。两个局部改进各自把布局拉向不同的最优点，
> 叠加后落到第三处，比单独任何一个都差。**"组合验证"是必须步骤，不是省事的一步到位。**

一次改动 = 一个 `--tag`。改完立刻进步骤 4。

### 步骤 4 — 至少跑 2 次，确认逐位可复现

> **不跑 2 次以上、不确认逐位相同，A/B 就是噪声。**

```powershell
# 同一配置再跑一遍 (综合缓存会提示命中, 用 --force 或换 tag 强制重跑)
python tools\fpga_workflow.py synth --tag <tag>-b --record

# 用工具直接判"逐位可复现": 多份报告 -> 只打对照表 + 按 WNS/源点分组
python tools\path_hotspot.py "ref5\runs\*\timing.rpt"
```

工具的复现性模式按 **(WNS, 关键路径源点)** 分组，同组 = 逐位同一条路径。实测输出：

```
  分组 (WNS + 关键路径源点相同 = 逐位可复现):
    group 1: WNS=12.714  src=u_imem/rdata_reg/CLKARDCLK  x2  e1-base-a, e1-base-b
    group 2: WNS=13.426  src=u_imem/rdata_reg/CLKARDCLK  x3  e1-en-amf-a, -b, -c
    group 3: WNS=13.162  src=u_imem/rdata_reg/CLKARDCLK  x2  e1-en-amf32-a, -b
```

**本项目的复现力度（照抄即可）**：

| 配置 | 跑了几次 | 结果 |
|---|---|---|
| ref5 V7 基线 | 历史 3 次 + 本次 **5 次** | 逐位相同（WNS 12.714 / 6.760ns / L=4 / 852 LUT / 458 FF / 2 BRAM） |
| ref5 E1 | 3 次 | 逐位相同 |
| ref5 E5 | 2 次 | 逐位相同 |
| ref5 **E1+E5（最佳）** | **5 次** | 逐位相同（13.426 / 1029 LUT cell / 554 FF / 同一条路） |
| 主核 P8 | 2 次 | `lv4-noidid / lv4-final` 均 69.5 |

**"逐位相同"还是一个免费的照妖镜**：见 §3.2 盲区 3 ——
`phys_opt_design AggressiveExplore`、`route_design` 的 4 种 directive 里的 2 种、
`-retiming`、`CONTAIN_ROUTING=1` **全部**表现为"报告逐位相同"= **纯空转**。

### 步骤 5 — 记录（**负结果必须和自己的收益一样详细**）

```powershell
python tools\fpga_workflow.py metrics --vs <base-tag>   # 四项指标 + keep/reject 判定
python tools\fpga_workflow.py synth --tag <tag> --record # 追加一行到 results/coremark.csv
```

`results/coremark.csv` 的字段就是**必须记录的字段**：

```
date, tag, iters, ticks, coremark_per_mhz, lut, ff, bram, dsp, fmax_mhz, status, notes
```

再加三个报告里没有、但**每次都要单独记**的字段：

| 字段 | 从哪来 | 为什么必须记 |
|---|---|---|
| **WNS** | `path_hotspot.py` 第一屏 | fmax 是 WNS 的换算，WNS 才是原始量 |
| **关键路径源→目的 + logic/route 分解** | `path_hotspot.py` | 判断"瓶颈是否转移"的唯一依据 |
| **复现次数** | 步骤 4 | 复现性是可信度的前提 |

> **本项目为什么把负结果当一等公民**：`ref5/REPORT.md` 只有 195 行，其中 **§(d) "试过但没用"
> 占了 10 行 7 条**；`p3-fmax.md` 567 行里实验 D/E5/F/H/I/J **六个负结果**占了近一半。
> 这不是记录癖 —— **负结果定义了这个设计的"可行域边界"**，而边界决定了下一轮该往哪走。
> （最典型：实验 F 的 −4.8% 直接证明了"付 IPC 换 fmax 不划算"，从此不再讨论 A' 路线。）

**status 三态**：`keep`（保留）/ `rejected`（试过、净亏、已回退）/ 实验性（留开关但默认关）。
`RAS/gshare`、`radix-4`、`A_EN`、`DIV_RADIX4` 都是"保留复现开关、默认关闭"。

### 步骤 6 — 确认瓶颈是否转移，回到步骤 1

**修好一条，下一条立刻补齐**。ref5 在**一次实验里转移了三次**：

| 阶段 | 限制路径 | 数据延迟 | 端点类型 | 逻辑级数 |
|---|---|---|---|---|
| V7 基线 | 取指环：`imem DOADO → hit → pipe_stall → 地址 mux` | 6.760 ns | **BRAM 地址脚**（setup −0.490） | 4 |
| 只开 E1 | ALU：`id_ex_b[3] → 移位/结果 mux → ex_mem_alu_out` | **7.200 ns**（route 85%） | 普通 FF | 5 |
| E1+E5 | ID 段：`imem DOADO → 操作数选择 → id_ex_a` | 6.498 ns | **复制后的 FF**（D 侧 fo=97） | **2** |

而且**转移后的 TOP1 与 TOP2 只差 0.12 ns**（13.426 vs 13.547）——
设计已经进入"两条路并列"状态。**此时对任何单独一条动手，期望收益 ≈ 0**
（E1 单独做时就是这个现象：把取指环改善 0.381 ns，却把 ALU 那条路从 ≤6.58 顶到 7.200 ns，
净收益只剩 +1.41 MHz）。

⇒ **每次改完必须重新取 top 路径，别继续优化已经不在榜上的东西。**
⇒ **判据：TOP1 − TOP2 < 0.2 ns 时，必须同时处理两条，或者动它们的共性结构。**

## 2. 抓手清单（按本项目**实测收益**排序）

> 每条给：**适用条件 / 具体做法 / 实测数字 / 代价 / 陷阱**。
> "收益"一律是 `fmax` 的 MHz 变化；"净吞吐"= `CoreMark/MHz × fmax`。

### 2.1 ⭐ 高扇出**寄存器**复制 `(* max_fanout = 16 *)` — 单次收益最大

| | |
|---|---|
| **适用条件** | 从 timing report 里找到 **fo 大 + 该跳延迟大 + 驱动器是寄存器** 的网（§1 步骤 2） |
| **具体做法** | 在 **RTL 的寄存器声明处** 加 `(* max_fanout = 16 *)`（不是网表级 `set_property`，见陷阱 2） |
| **实测数字** | ref5 E5 单用：137.250 → **145.751（+8.50）**；E1+E5：**152.114（+14.86，+10.8%）**，5 次逐位相同 |
| **代价** | ref5：Slice LUT 852 → 971（+119）、FF 458 → **554（+96，全是复制副本）**、BRAM 不变。相对富余面积很小 |
| **陷阱 1** | **收益是位置特定的，不会自动迁移**。同一属性加在主核"同名同位置"（`id_ex_reg.sv` 的 `rs1_data/rs2_data`）上：**69.6 → 68.8（−0.8）**、LUT 2653 → 2684（+31）、**FF 1234 → 1234（一字不变）** ⇒ 属性被接受但**根本没触发复制**，只剩布局扰动。已回退 |
| **陷阱 2** | **网表级 `set_property MAX_FANOUT` 完全无效**：E5b 对 64 根网设属性，打印 `NETS=64` 说明被接受，但 FF 仍 458，报告与 E3 **逐位相同** ⇒ **只有 RTL 属性才有效** |
| **陷阱 3** | **与 `place -directive ExtraTimingOpt` 强负交互**：E1+E5+ExtraTimingOpt = **125.47（−26.6）** |
| **陷阱 4** | **参数有甜点**：配 E1 时 `16`（152.114）比 `32`（146.242）好 **5.87 MHz**；且 `32` 的 FF 只有 473（副本更少）⇒ 旋钮实际是"副本数"，**可直接用 FF 数标定**。只探了 16/32 两点，**别外推** |

> **取证纪律**：加完属性**先看 FF 数有没有上升**。没上升 = 空转。（PITFALLS R37-4）

### 2.2 物理区域 Pblock —— **是"定位"不是"收紧"**

| | |
|---|---|
| **适用条件** | 数据通路与存储器跨时钟区；先测真实坐标（`ref5/probe_regions.tcl`、`tools/hier_util.tcl`） |
| **具体做法** | `--pblock-range CLOCKREGION_X1Y0:CLOCKREGION_X1Y3`（**4 个区**，不是 1 个） |
| **实测数字** | 主核：无约束 62.8 → **`X1Y0:X1Y3` 69.2（+6.4）**；ref5：V1 102.47 → V2 **108.97（+6.50）**。**物理约束的贡献比逻辑改写（主核 +3.9）还大** |
| **代价** | 零面积、零 IPC |
| **陷阱** | **收紧更差**（R37-1）：ref5 收到单区 `X1Y1` = **129.20（−8）**；主核 `X1Y0:X1Y2` 66.9、`X1Y0:X1Y1` 64.2、`X1Y1:X1Y1` 67.4、`X1Y1:X1Y2` 65.0。**7 种里只有 1 种最好** ⇒ **布局自由度 > 物理距离** |

### 2.3 存储器规模 —— 注意这是**配置选择**，不是"优化"

| | |
|---|---|
| **实测数字** | ref5 **同一份 RTL**：4KB/4KB = **137.25** vs 16KB/16KB = **118.57** ⇒ **值 ~19 MHz**（主核同档是 8 块 RAMB36） |
| **代价** | 16KB 版 LUT 只多 4（852 → 856）、FF 完全不变（458）—— **就是纯粹的布局/布线代价** |
| **陷阱** | 把"LUT 少了"当成收益。**BRAM 化省 LUT 时必须同时量 fmax，方向和幅度都要实测**：ref5 是**干净的单变量对照**（同 RTL、只换存储器规模 ⇒ LUT 852 → 856、FF 完全不变，fmax **137.25 → 118.57**）；而 `results/coremark.csv` 里那些 −30.9% LUT 的跳变（`p6-a-*` 4079 → `bram-*` / `regread-*` 2820）**同时改了多件事**，不能拿来归因 |
| **更重要的一条推论** | ref5（137.25）与主核（69.6）的差距里，**至少 19 MHz 根本不是前递/预测/控制束造成的，而是存储器几何**。对比参照设计前**必须先对齐存储器规模与物理约束** |

### 2.4 逻辑等价改写 + 扇出约束（零面积、零 IPC）

| | |
|---|---|
| **具体做法** | ① `pred_ok` 直接比 `ex_pc_target`（该项本就被 `!actual_taken \|\|` 门控，**逐位等价**，但把 32 位 2:1 mux 移出比较路径）；② `(* max_fanout = 16 *)` 加在 `actual_taken`（fo=60）、`pc_src`/`redirect`（fo=34）上 |
| **实测数字** | 主核 58.9 → **62.8（+3.9）**；最差路径 16.350 → 15.276 ns；LUT/FF/BRAM **完全不变**；CoreMark ticks 423527 **不变** |
| **代价** | 0 |
| **陷阱** | "理论上冗余"≠"能从关键路径上消失"。实验 E5 省掉 BR/JAL 的目标校验（论证严密），**实测 64.9 vs 69.2 = −6.2%** —— 因为 STA 看最坏路径，**只要还有一类指令（JALR）保留该逻辑，它就在路径上**，而新加的选择项还多串了一级 |

### 2.5 结构性删冗余流水寄存器（P8：删 `if_id_reg`）—— 唯一一次三项同时改善

| | |
|---|---|
| **适用条件** | 流水寄存器前面**没有任何组合逻辑**（纯搬运），且它的存在只是为了配合同步读存储器 |
| **实测数字** | CoreMark/MHz 2.3611 → **2.4209（+2.53%）**；ticks 423,527 → **413,070（−10,457，−2.47%）**；fmax 69.2 → **69.5（+0.43%）**；LUT 2820 → **2769（−51）**；FF 1345 → **1234（−111）**；CoreMark/LUTs +4.42%；**绝对吞吐 163.3 → 168.4（+3.12%）** |
| **收益来源（必须说准）** | ❌"少了一级流水所以更快"——**错**，少一级本身不提高吞吐。✅"**去掉一个纯搬运寄存器 ⇒ 每次重定向少穿一个气泡**"——11,535 次重定向 ⇒ 10,457 拍 |
| **代价** | 0（同时省面积） |
| **陷阱 1** | 做成组合别名后**暴露出一条原本被寄存器切断的组合环**：`[Synth 8-295] found timing loop` / `[DRC LUTLP-1] 17 LUT cells form a combinatorial loop` |
| **陷阱 2** | `if_id_flush` 是**全核最晚、扇出最大（fo=125）**的信号之一，一旦串进 `id_ctrl → imm_gen → ID/EX` 的 D 端立刻变成关键路径：**69.2 → 67.5**；改成只用早期信号 `boot_done` 门控后 **67.5 → 69.5**（反超基线） |
| **通用教训（R34）** | 把一个"寄存器输出"改成"组合别名"时，要重新检查它原来是否同时充当 ①一级流水 ②**反馈环的切点** ③**晚间信号的屏障** |

### 2.6 把"某段逻辑从组合环里摘出去"（ref5 ENARDEN）—— 单看不值钱，但是**解锁条件**

| | |
|---|---|
| **具体做法** | 给 imem 加读使能口 `rd_en`，把**停顿信号从 BRAM 地址脚挪到 CE 脚**（`if (rd_en) rdata <= mem[addr]`）；`imem_addr` 只由已寄存的 pc 决定 |
| **实测数字** | 环本身 6.760 → **6.379 ns**，slack 12.714 → **13.198（+0.484 = 路径 0.381 + ENARDEN 的 setup 比 ADDRARDADDR 松 0.103）**；但**单看只 +1.41 MHz（138.658）** |
| **代价** | 0（LUT 852 → 863） |
| **陷阱 1** | **逻辑级数一级都没少**（仍 4 级）—— CE 前面也要一个 LUT 把 `redirect`/`!boot_done` 或进去。**省的是"最后一跳到 12 根地址脚"的布线 + 端点更便宜** |

| **移植到主核必须照抄三条** | ① **停顿拍 pc 仍要冻结**（否则丢 4×停顿拍数 条指令）；② `rd_en` 要**把 `redirect` 及任何"必须立刻改地址"的事件或进去**（主核还有 BTB 命中/例外）；③ 确认主核 imem 的 `ENARDEN` **真的冻结输出寄存器**而不是只关地址寄存器 |

## 3. ⭐ 思维盲区清单

> 这一节是本文件最值钱的部分。每一条都给了**本项目的实测证据**，
> 而不是"一般来说应该注意"。

### 3.1 三条最值钱的（如果只记三条，记这三条）

**① 「功能上对应的位置」≠「物理上等价的网」—— 要按 `fo` 找抓手，不按名字。**

| | ref5 参照核 | 主核 |
|---|---|---|
| 改动位置 | `id_ex_a/id_ex_b`（ALU 操作数寄存器） | `id_ex_reg.sv` 的 `rs1_data/rs2_data`（**同名、同功能位置**） |
| 结果 | 137.25 → **145.75（+8.50）**，FF **458 → 554**（真复制） | 69.6 → **68.8（−0.8）**，FF **1234 → 1234**（没复制）、LUT +31 |
| 判决 | 保留 | **已回退** |

⇒ 同一个属性、同一个功能语义，在**两个设计里一个真复制一个没复制**。
唯一可靠的判据是**物理痕迹**（FF 数）和 **report 里的 `fo`**，不是名字。
**先跑 `tools/path_hotspot.py` 找到 fo 大的那根网，再去 RTL 里找它的寄存器。**

---

**② 「属性被接受」≠「属性生效」—— 任何"你以为是优化"的动作，先找它留下的物理痕迹。**

把"生效"拆成三层，**只有第 ③ 层算收益**：

| 层 | 问什么 | 怎么查 | 本项目反例 |
|---|---|---|---|
| ① **输入生效** | 宏/属性/开关被解析了吗？ | 自证打印（`REF5_ENARDEN=`、`NETS=64`、`[muldiv] DIV_RADIX4 ACTIVE`、`BUILD_DIV_RADIX4=1`） | R17/R31：宏传递缺一处 ⇒ **静默按默认配置构建** |
| ② **物理生效** | 网表变了吗？ | **FF / LUT 数**、路径本身 | E5b 网表级 `MAX_FANOUT`：属性被接受，**FF 一个都没变** |
| ③ **时序生效** | WNS / 关键路径变了吗？ | `path_hotspot.py` 的 WNS + 源→目的 | 主核 E5 移植：①②真、③假（−0.8） |

`phys_opt_design AggressiveExplore` 是**三层全假**的典型：没有自证串、LUT/FF 逐位相同、路径逐位相同。
**"报告逐位相同"就是空转的机检特征**（见盲区 3）。

---

**③ 「单项收益 = 路径改善 − 布局扰动」—— 小改动也会重新洗牌布局，A/B 要看整体。**

| 证据 | 数字 |
|---|---|
| ref5 E1 | 取指环改善 **−0.381 ns**，却把 ALU 那条路从 ≤6.58 顶到 **7.200 ns** ⇒ 净 **+1.41 MHz** |
| 主核实验 F | 逻辑砍掉 **−2.465 ns**（5.045 → 2.580），route 反而 **+1.111 ns**（8.926 → 10.037）⇒ 净省 **1.354 ns**（13.971 → 12.617） |
| 主核实验 E5 | 省掉 BR/JAL 的比较，**JALR 那条路被顶上来** ⇒ −6.2% |

> ⚠️ 上面第二行的 1.354 ns 是**从原始报告复算**的（`13.971 − 12.617`，两份报告都在
> `.fpga-cache/reports/` 里，`tools/path_hotspot.py` 可直接复核）。
> 而 `results/p3-fmax.md` 与 PITFALLS R36 的**正文写的是"净省只有 0.81 ns"** ——
> **与它们自己同一段里的路径数字差 0.54 ns**。见盲区 14。

⇒ **不能只看被改的那条路**。而且当 `TOP1 − TOP2 < 0.2 ns`（E1+E5 的 13.426 / 13.547）时，
**对任何一条动手都可能只是把另一条顶上来，期望收益 ≈ 0**。

### 3.2 其余盲区（每条都有实测支撑）

**盲区 1 — 高扇出网的「驱动元件类型」决定了能不能用 `max_fanout` 治。**
E5 的成功建立在"`id_ex_a/id_ex_b` 是**寄存器**"这个前提上。用 `path_hotspot.py` 看 E1+E5（152.11）
剩下的候选，**全部是 LUT 驱动**：

```
fo=97  单跳 2.657 ns  u_core/id_ex_a[31]_i_2_n_0     <- 驱动: LUT6
fo=93  单跳 2.301 ns  u_core/id_imm_fmt__13[0]        <- 驱动: LUT6
fo=50  单跳 1.787 ns  u_imem/rdata_reg_5              <- 驱动: LUT5
```

⇒ 对 LUT 输出加 `max_fanout` 复制的**是逻辑**（连输入锥一起复制），机制、面积代价、收益曲线
都和复制寄存器**不是一回事**，收益通常小得多。
**用 `fo` 定位到网之后，必须再看驱动器是 FF 还是 LUT。**

---

**盲区 2 — 高扇出榜单里会混进"不该动"的网：reset / 时钟树 / 异步路径。**
跑当前主核的 `fpga/timing.rpt`，全局 fo 榜第一名是：

```
fo=1124  单跳 6.757 ns  u_core/u_muldiv/rst
```

它来自 **`async_default` 组的 Recovery 路径**（`rst_sync_reg[2]/C → u_core/u_muldiv/cnt_reg[0]/CLR`，
slack 10.840），**不是功能 setup 路径**。CI 直觉会说"fo=1124 最大，先治它" —— 但：

- 它不在 `sys_clk` 的功能 setup 组里，**优化它对评分 fmax 没有直接作用**；
- 它是**复位分发网**，`max_fanout` 的"寄存器复制"机制治不了它（要动的是复位策略本身）。

时钟树网（`clk_IBUF_BUFG` fo=557/653/1381）同理，工具已经用 `[clk-tree]` 标出来了。
⇒ **榜单必须按 `Path Group` / `Path Type` 过滤，先确认它是不是功能时序。**

---

**盲区 3 — "报告逐位相同"是空转的机检特征，可以直接把旋钮从候选表里划掉。**
本项目所有"试了等于没试"的手段，指纹完全一致：

| 手段 | 指纹 |
|---|---|
| `phys_opt_design AggressiveExplore`（V8 / E4） | WNS / 路径 / LUT / FF **一模一样** |
| `synth_design -retiming`（H） | 69.2 / 2820 / 1345 / 423527 **完全相同**（"Vivado 一个触发器都没搬"） |
| `CONTAIN_ROUTING=1`（E7） | 与不加**完全相同** |
| 网表级 `set_property MAX_FANOUT`（E5b） | 与 E3 **逐位相同** |
| `route_design NoTimingRelaxation`（G） | 69.2，与默认**完全相同** |

⇒ 配合 `path_hotspot.py` 的多报告模式，这一步是**秒级**的。
**反例要分清**：`max_fanout=32`（13.162）与 `16`（13.426）**不同** ⇒ 那不是空转，是参数甜点问题。

---

**盲区 4 — "优化"之间有强负交互，可加性假设不成立。**
两个各自都有用的东西叠起来比任何一个都差：

| 组合 | fmax |
|---|---|
| E1 单独 | 138.658 |
| ExtraTimingOpt（配 E1） | 143.308 |
| E5 复制单独 | 145.751 |
| **E1 + E5** | **152.114（超加性，1.41 + 8.50 ≪ 14.86）** |
| **E1 + E5 + ExtraTimingOpt** | **125.471（−26.6，强负交互）** |

注意这里**同时存在超加性和负交互**：布局是全局重排，两个改进可能碰巧落到同一个更好的
局部最优（超加性），也可能各自拉向不同方向（负交互）。**两种都不能用加法预测，只能实测。**

---

**盲区 5 — 参数有甜点，且「只探过的两点不能外推」。**
`max_fanout` 只探了 16 和 32：配 E1 时 `16 → 152.114`、`32 → 146.242`（**−5.87**）。
但 FF 数给出的机理很清楚：`32 → 473 FF`、`16 → 554 FF`（**阈值越小副本越多**）。
⇒ 可调旋钮实际上是**副本数**，可以直接用 **FF 数标定**，而不是把 16/32 当黑箱；
**但"16 是最优"这个结论本身只在两点之间成立，别外推到 8 或 24。**

---

**盲区 6 — 测量口径：`stall_*` / `busy` 变小 ≠ 评分变快，必须看「计时区间内」的 tick（R38）。**
radix-4 除法器（`results/radix4-result.md`，分支 `radix-4`）：

| 量 | radix-2 | radix-4 | 差 |
|---|---|---|---|
| `muldiv busy`（**全程**） | 14,415 | **12,063** | **−2,352 ✓** |
| `pipe_stall`（全程） | 45,060 | 42,708 | −2,352 ✓ |
| tb 总周期（整个程序） | 457,125 | 454,773 | −2,352 ✓ |
| **程序自测 `Total ticks`（`MMIO_MARK → MMIO_RESULT` 窗口）** | 413,070 | **413,070** | **0 ✗** |
| **上板 tick** | 536,943,384 | **536,943,384** | **逐位相同** |

机理：全程 **147** 条除法 = `MMIO_MARK` 前 **84**（init/校验）+ `MMIO_RESULT` 后 **63**（`ee_printf` 打印）
+ **窗口内 0 条**。旧注释的"0.29%"就是把 pre-mark 那 84 条当成了窗口内。
⇒ **用 `profile` 的全程计数推断评分收益会系统性高估。**

**它的孪生兄弟（方向相反）**：占比的**分母**也必须用对 ——
`results/p3-fmax.md` 开头明确记着：分母必须用 tb 的 `cycles`（468,659），
不能用 CoreMark 的 `Total ticks`（423,527），否则**系统性低估约 10%**。

---

**盲区 7 — "砍逻辑"在布线主导时会失效，而且「收益系数」本身会漂移。**

| 案例 | 砍掉的逻辑 | 净省 | **收益系数** |
|---|---|---|---|
| 主核实验 C（E1+E2，58.9 → 62.8） | 5.744 → 4.378（**−1.366 ns**） | 16.350 → 15.276（**−1.074**） | **0.79** |
| 主核实验 F（A'，69.2 → 76.0） | 5.045 → 2.580（**−2.465 ns**） | 13.971 → 12.617（**−1.354**） | **0.55** |

> 两行都是从 `.fpga-cache/reports/` 的原始报告复算的（tag 见 `results/coremark.csv`）。
> 注意第二行：文档正文写"0.81 ns"（系数 0.33），**原始数字算出来是 1.354 ns（系数 0.55）**。
> 用哪个都会得出"砍逻辑不划算"的**同一个结论**，但**系数差了 1.7 倍**，
> 拿它去做预算就会算错（盲区 14）。

⇒ **同一个设计、两天之内，"砍 1 ns 逻辑能换回多少 ns"从 0.79 掉到 0.55。**
因为 route 占比从 64% 涨到 80%。**每轮都要重新量 route 占比，不能沿用上一轮的系数做预算。**
（R36 的定性版："砍掉 2.5 ns 逻辑只换回 0.81 ns"；`p3-fmax.md` 的原话是
"每砍 1ns 逻辑只换来 0.2~0.3ns 的净收益"。）

---

**盲区 8 — "参考设计"能定位差距，但会误导：差距里有一大块是「评分要求」，不是缺陷。**
ref5 = 137.25 MHz（852 LUT，无前递/无预测/无 M·A·CSR·trap），主核 = 69.6 MHz。
那 2× 的四项来源（ref5/REPORT.md 自己列的）：

1. **数据前递网络** —— 主核最贵那条路；ref5 用"停 3 拍"换掉了它（代价是 CPI）；
2. **分支预测（BTB）** —— 有预测才敢让"分支比较 → 重定向 → 取指地址"这条路存在，预测器本身又给取指地址加一级 LUTRAM 读 + 目标 mux；
3. **宽控制束 / CSR / trap / MMIO / 中断** —— 控制束每加宽一位，就多一份要在"冒险逻辑"与"ID/EX 控制位"之间穿行的布线；
4. **存储器规模与物理约束** —— **单这一项就 ~19 MHz**（137.25 vs 118.57）。

⇒ ①②③ 是**评分需要的功能**，不是可以压掉的东西（这也是 `results/gap-analysis.md`
把"C 扩展/双发射/Cache"列进"明确不做"的依据：双发射在 route 已占 66% 的设计上
复制发射资源，"fmax 几乎必然下降"）。**对比参照核时先对齐存储器规模与物理约束**，
否则会把"存储器价格"错记到"架构价格"上，从而得出"我们的架构太差"的错误结论。

---

**盲区 9 — 失败实验的价值不在"此路不通"，而在「它逼出的那条不变量」。**
主核实验 D 想把 load 结果改成寄存器前递，结果 `PASS 11 → PASS 4`。看起来是纯粹的失败，
但它暴露了一条不变量：

> dmem 是**寄存读** ⇒ 数据比地址**晚一拍** ⇒ **"用寄存器前递"必须让"数据在锁存沿上已经是对的"成立。**

这条不变量直接判定了 A' 路线的代价（**每个 load 多占一拍 MEM = +14%**，因为 load 占指令数 15.6%），
并且指明了正解：**把访存地址提前到 EX 段送出**（dmem 在 EX 拍拿到地址，数据就在 MEM 拍有效，
提取落在 MEM 段，停顿仍是 1 拍，IPC 代价 0）。
⇒ **回退一个失败实验之前，先把它证伪/证实的那条不变量写下来**；那条不变量是下一轮设计的输入。

（同族：实验 J 的 `trap/mret` 让路"理论等价、实测失败"—— 它证伪的不是"让路"这个想法，
而是"**逐拍等价性可以用推理代替实测**"这个假设，并留下了"需要逐拍基线对照轨迹"这个方法论缺口。）

## 4. 每轮优化模板（可直接复制）

```powershell
# ============ 0) 环境 + 漂移 ============
cmd /c tools\doctor.bat
#   期望: 无 [FAIL]; [warn] 要看清理由

# ============ 1) 量当前瓶颈 (不凭感觉) ============
python tools\path_hotspot.py fpga\timing.rpt            # route/logic 占比 + WNS + fmax
python tools\path_hotspot.py fpga\timing_paths.rpt --top 10   # 有全展开报告时用这个
python tools\fpga_workflow.py profile --prog cm_rv32im  # 停顿构成 (预估 IPC 代价)
#   记录: WNS / fmax / route% / TOP1 源->目的 / 全局 fo 榜首 / 复制候选

# ============ 2) 一次只改一件事 ============
#   * 改 RTL, 只改一个抓手, 加 env/ifdef 开关, 默认路径与基线逐字相同
#   * 加自证打印 (证明这个开关真的被解析了)

# ============ 3) 功能回归 ============
python tools\fpga_workflow.py verify
#   期望: PASS 11 (含 CoreMark CRC 自校验)

# ============ 4) 综合 A (第一次) ============
python tools\fpga_workflow.py synth --tag <tag>-a --record
#   记录: fmax / WNS / LUT / FF / BRAM / key path
#   ⭐ 关键: 看 FF 数. 如果这次改动的机理是"复制", FF 没涨 = 空转, 直接停

# ============ 5) 综合 B (第二次, 复现性) ============
python tools\fpga_workflow.py synth --tag <tag>-b --record
python tools\path_hotspot.py "<报告目录A>\timing.rpt" "<报告目录B>\timing.rpt"
#   期望: 工具输出 "group 1: ... x2"  => 逐位可复现
#   若两次 WNS 不同 => 结果不可信, 先查是不是构建/宏问题 (R17/R31), 别继续

# ============ 6) 四项指标 + keep/reject 判定 ============
python tools\fpga_workflow.py metrics --vs <base-tag>
#   判据: 绝对吞吐 = CoreMark/MHz x fmax. fmax 掉得比吞吐收益多 => 净亏, 回退

# ============ 7) 记录 (含负结果!) ============
#   results/coremark.csv 一行 + 报告段落 (改了哪一行 / 为什么 / 负结果也一样写)
#   必须写的额外字段: WNS, 关键路径源->目的, logic/route 分解, 复现次数, 瓶颈是否转移

# ============ 8) 回到第 1 步, 重新取 top 路径 ============
```

### 每轮必须记录的字段

| 字段 | 来源 | 备注 |
|---|---|---|
| 版本 / tag / 日期 | 自己 | 引用任何数字都要带它（盲区 11） |
| 改动（文件:行 + 一句话） | 自己 | 一次只改一件事 |
| **fmax / WNS** | `synth` + `path_hotspot.py` | fmax 是换算值，WNS 是原始量 |
| **LUT / FF / BRAM / DSP** | `synth --record` | **FF 数是"复制是否发生"的唯一证据** |
| **关键路径 源→目的** | `path_hotspot.py` | 判"瓶颈是否转移" |
| **logic / route 分解** | `path_hotspot.py` | 判"逻辑受限还是布线受限" |
| **复现次数** | 步骤 5 | ≥2，关键组合 5 |
| **瓶颈是否转移 / 转移到哪** | `path_hotspot.py` | 决定下一轮抓手 |
| **IPC 代价（ticks 变化）** | `synth --record` | 任何"付 IPC"的改动必须先算这笔账 |
| status | `metrics` | keep / rejected / 留开关默认关 |

### 判据（一句话各自）

- **绝对吞吐 = `CoreMark/MHz × fmax`** —— 三项互相矛盾时的最终裁判。
- **fmax 掉得比吞吐收益多 ⇒ 净亏，回退**（实验 F：fmax +9.8% 但 ticks +15.4% ⇒ 吞吐 −4.8%）。
- **fmax 涨、面积不跌、ticks 不变 ⇒ 无条件保留**（实验 A/C 的 E1+E2+E3）。
- **三项同时改善 ⇒ 立刻上板验证**（P8 是唯一一次：CM/MHz +2.53%、fmax +0.43%、CoreMark/LUTs +4.42%）。
- **计时区间内的 tick 不变 ⇒ 收益为 0**，无论 `stall_*` 降了多少（盲区 6）。
- 变快之后**必须重算 `ITERATIONS`**（R35：`ITER_new = ceil(ITER_old × 10.0 / 实测秒数 × 1.05)`），
  否则上板时间 <10 s，**成绩无效**。

### 5.1 动手前（8 条）

- [ ] `cmd /c tools\doctor.bat` 无 `[FAIL]`？
- [ ] 这一轮的抓手是**从 timing report 的 `fo` + 该跳延迟**选出来的？（不是"名字看起来该优化"）
- [ ] 那根网的**驱动元件是寄存器**还是 LUT？（决定能不能用 `max_fanout` 复制）
- [ ] 它的 `Path Group` 是功能 setup 组？（不是 `async_default` 的复位/异步路径）
- [ ] 当前 route 占比量过了吗？（≥50% ⇒ 别指望"砍逻辑"）
      `TOP1 − TOP2` 是多少？（< 0.2 ns ⇒ 对单条路动手期望收益 ≈ 0）
- [ ] 这次改动**只有一件事**吗？（一个抓手 / 一个 `--tag` / 一个开关）
      默认路径与基线**逐字相同**吗？（`ifdef` 关掉后必须能复现基线）
- [ ] 如果是"付 IPC"的改动，`profile` 的账算过了吗？（load 占指令 15.6% 这类数字）
- [ ] 要引用的基线数字（fmax/WNS/LUT/FF）是**从 `results/coremark.csv` 的某个 tag 或
      从 `.fpga-cache/reports/` 的原始报告现算的**吗？（不是从某份报告的正文里抄的，盲区 14）

### 5.2 动手后（8 条）

- [ ] `verify` 是 **PASS 11**（含 CoreMark CRC 自校验）？
